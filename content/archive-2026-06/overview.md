## Простыми словами

AI Unit Test Assistant — это небольшой инструмент командной строки (CLI) на Python, который помогает разработчикам не забывать писать тесты после внесения изменений в код.

Проблема, которую он решает: когда developer создаёт Pull Request с изменениями в Python-файлах, тесты к этим изменениям часто пишутся наспех, неполно или не пишутся вовсе. Ревьюер не видит тестов, а технический долг накапливается.

Инструмент встраивается в GitHub Actions: как только открывается PR с изменёнными `.py`-файлами, он автоматически анализирует, что именно изменилось, генерирует pytest-тесты с помощью Gemini (через Vertex AI) и предлагает обновления для уже существующих тестов. Всё это появляется как артефакты PR — developer видит предложения и сам решает, что принять, что выбросить, что доработать.

Целевая аудитория — команды, которые хотят повысить тестовое покрытие без жёсткого принуждения, и individual developers, которым нужен быстрый старт для написания тестов.

Ценность проекта в том, что он не пытается заменить разработчика: он не коммитит код сам, не перезаписывает существующие тесты, не модифицирует production-код. Он выступает как черновик и подсказчик — экономит время на написание boilerplate и помогает не пропустить edge cases.

Проект намеренно простой: один линейный pipeline, 11 Python-модулей, никаких фреймворков оркестрации. Это сделано сознательно — инструмент должен быть понятен, поддерживаем и расширяем без глубокого погружения.

## Детальный разбор

### Цель проекта

Автоматизировать генерацию pytest unit tests для изменённого Python-кода в PR-workflow, при этом оставить финальное решение о качестве и применимости тестов за человеком.

### Не-цели (что проект специально НЕ делает)

- Не модифицирует production-код ни при каких условиях.
- Не перезаписывает существующие тест-файлы автоматически — только предлагает обновления.
- Не делает git commit и не открывает новые PR.
- Не является заменой code review или ручного тестирования.
- Не гарантирует корректность сгенерированных тестов — они требуют review.

### High-level workflow

```
PR открыт / обновлён (изменён хотя бы один .py-файл)
↓
GitHub Actions запускает ai-test-assistant run-pr-assistant
↓
git_utils.py: git diff --name-only → список изменённых .py-файлов
↓
Фильтрация: исключаем тест-файлы, generated-файлы, excluded_paths
↓
Для каждого production-файла:
  ↓
  source_analyzer.py: AST-парсинг → список публичных функций и методов
  ↓
  select_test_targets: выбираем только те, чьи строки попали в diff
  ↓
  Если targets пустой → статус "skipped", переходим к следующему файлу
  ↓
  test_finder.py: ищем связанные существующие тест-файлы
  ↓
  llm_client.py + prompts.py: строим prompt, вызываем Gemini (Vertex AI)
  ↓
  test_generator.py: чистим ответ LLM, валидируем Python + наличие test-функций
  ↓
  Сохраняем в tests/generated/test_<путь_к_файлу>_generated.py (имя из пути: examples/calculator.py → test_examples_calculator_generated.py)
  ↓
  pytest_runner.py: запускаем pytest на сгенерированном файле
  ↓
  Если тесты падают И repair_attempts > 0:
    ↓
    repair loop: передаём pytest output обратно в LLM для исправления
    ↓
    Повторяем не более repair_attempts раз (по умолчанию 2)
  ↓
  (если update_existing_tests=true) update_existing_tests:
    для каждого найденного существующего теста — LLM предлагает обновлённую версию
    сохраняем в reports/suggested-tests/ (НЕ перезаписываем оригинал)
  ↓
  FileResult: status passed/failed/skipped/error
↓
report.py: пишем reports/ai-test-report.md + reports/ai-test-report.json
↓
GitHub Actions: добавляем report в GITHUB_STEP_SUMMARY, upload artifacts
↓
Developer: ревьюит артефакты, вручную копирует или применяет нужные тесты
```

### Разбор компонентов

#### cli.py

Точка входа в инструмент. Использует библиотеку Typer для определения трёх команд:

- `generate-tests` — генерирует тесты для одного указанного файла (для локального использования).
- `run-pr-assistant` — основной workflow: находит изменённые файлы через git, запускает полный pipeline.
- `apply-suggestions` — копирует предложенные обновления тест-файлов поверх оригиналов (явное действие developer'а).

Параметры CLI имеют наивысший приоритет: они перекрывают environment variables и config-файл.

#### config.py

Управляет конфигурацией через dataclass `AppConfig`. Приоритет настроек (от высшего к низшему): CLI args > env variables > YAML config-файл (`ai-test-assistant.yml`) > дефолты.

Ключевые настройки: `base_ref` (с чем сравниваем, по умолчанию `origin/main`), `output_dir` (куда кладём generated tests), `suggestions_dir` (куда кладём предложенные обновления), `repair_attempts` (лимит попыток repair loop, по умолчанию 2), `gemini_model` (по умолчанию `gemini-2.5-flash`), `temperature` (по умолчанию 0.0 — максимально детерминированные ответы), `dry_run` (без реальных LLM-вызовов, для тестирования самого инструмента).

Поддерживает `.env`-файл через `python-dotenv` (если установлен).

#### models.py

Чистые dataclass-ы без бизнес-логики. Определяет все структуры данных, которые передаются между модулями:

- `ChangedFile` — путь к файлу + множество изменённых строк.
- `FunctionInfo`, `ClassInfo`, `SourceAnalysis` — результат AST-анализа.
- `TestTarget` — функция или метод, для которой нужно сгенерировать тест.
- `PytestResult` — результат запуска pytest (exit code, stdout, stderr, duration).
- `FileResult` — итоговый результат обработки одного файла.
- `PipelineResult` — итоговый результат всего pipeline (список FileResult).

#### git_utils.py

Работает с git через subprocess. Две ключевые операции:

1. `git diff --name-only <base_ref>...HEAD` — список изменённых файлов.
2. `git diff --unified=0 <base_ref>...HEAD -- <file>` — парсинг hunk headers для получения точных номеров изменённых строк.

Также содержит `is_production_python_file()` — фильтр, который отсеивает тест-файлы (`test_*.py`, `*_test.py`), generated-файлы (`*_generated.py`) и пути из `exclude_paths`.

#### source_analyzer.py

AST-анализ исходного Python-файла стандартной библиотекой `ast`. Находит все публичные функции и методы (те, чьё имя не начинается с `_`). Для каждой функции восстанавливает читаемую сигнатуру с типами, дефолтами и `async`-префиксом.

Функция `select_test_targets()` принимает список изменённых строк и отбирает только те функции/методы, которые пересекаются с диффом. Если diff пустой (команда `generate-tests`), выбираются все публичные символы.

#### test_finder.py

Ищет существующие тест-файлы, связанные с изменённым source-файлом. Использует два подхода:

1. Поиск по стандартным путям: `tests/test_<stem>.py`, `tests/<stem>_test.py`, зеркальный путь в тест-директории.
2. Полное сканирование тест-директорий с поиском импортов и упоминаний модуля или имён функций в тексте файла.

Это нужно, чтобы LLM получил контекст существующих тестов и не дублировал их.

#### llm_client.py

Тонкая обёртка вокруг `google-genai` SDK с поддержкой Vertex AI. Ключевые особенности:

- Lazy initialization клиента — создаётся только при первом вызове.
- `dry_run=True` — возвращает фиксированный stub без сетевого вызова (используется в CI самого инструмента и для локального тестирования).
- Синхронный вызов Vertex AI завёрнут в `loop.run_in_executor()`, чтобы не блокировать event loop.
- `temperature=0.0` по умолчанию — детерминированные, предсказуемые ответы.

#### prompts.py

Содержит три системных инструкции и три функции построения промптов:

- `build_generate_tests_prompt` — для генерации новых тестов: передаёт полный source code, сигнатуры targets и содержимое существующих связанных тестов (чтобы не дублировать).
- `build_repair_tests_prompt` — для починки упавших тестов: передаёт production-код, текущие тесты и вывод pytest.
- `build_update_tests_prompt` — для обновления существующих тестов: передаёт изменённый код и текущее содержимое тест-файла.

Все инструкции явно запрещают LLM модифицировать production-код и возвращать Markdown-разметку.

#### test_generator.py

Оркестрирует взаимодействие с LLM для трёх сценариев: генерация, repair, обновление. Содержит важную логику постобработки LLM-ответа:

- `clean_llm_python_response()` — удаляет Markdown code fences (LLM часто их добавляет несмотря на инструкции).
- `validate_python_test_code()` — парсит ответ через `ast.parse()` (синтаксическая валидация), проверяет наличие хотя бы одной функции с префиксом `test_` или класса с префиксом `Test`, отклоняет shell-скрипты. Бросает `ValidationError`, если проверки не прошли.

#### pytest_runner.py

Запускает pytest в subprocess через `python -m pytest -q`. Не бросает исключений при падении тестов — возвращает `PytestResult` с флагом `passed=False`. Имеет таймаут 120 секунд. Захватывает stdout и stderr для передачи в repair loop.

#### report.py

Генерирует два артефакта:

- Markdown-отчёт (`reports/ai-test-report.md`) — читаемый summary с деталями по каждому файлу; он же появляется в GitHub Actions Step Summary прямо в интерфейсе PR.
- JSON-отчёт (`reports/ai-test-report.json`) — машиночитаемый, для интеграций и автоматизации.

#### pipeline.py

Главный оркестратор. Содержит:

- `run_pr_assistant()` — полный workflow для PR: получает изменённые файлы, последовательно обрабатывает каждый, пишет отчёты.
- `run_generate_tests_for_file()` — упрощённый workflow для одного файла.
- `_generate_and_repair()` — repair loop: генерация → pytest → при падении repair → pytest → ... (лимит `repair_attempts`).
- `apply_suggested_updates()` — копирует suggested-файлы поверх оригиналов.

Обработка ошибок per-file: если один файл падает с unhandled exception, pipeline продолжает обработку остальных файлов, фиксируя ошибку в `FileResult`.

### Ключевые принципы безопасности и почему они выбраны именно так

**Human-in-the-loop обязателен.** Все сгенерированные тесты и suggested updates — это артефакты для review, а не готовые коммиты. LLM может ошибаться, генерировать тесты с неправильными ожиданиями или пропускать важные случаи. Developer должен прочитать и одобрить каждый тест.

**No auto-commit.** Коммит кода — это акт ответственности. Инструмент не должен брать на себя эту ответственность за разработчика. Это также означает, что инструмент не может случайно "сломать" репозиторий.

**No overwrite existing tests.** Существующие тесты могут содержать важные знания о поведении системы. Перезаписать их без review значило бы потенциально удалить ценную документацию поведения.

**Reviewable artifacts.** Весь вывод — файлы в `tests/generated/` и `reports/suggested-tests/` — видим в PR как GitHub Artifacts и в Step Summary. Это прозрачность: любой участник команды может посмотреть, что предлагает инструмент.

**Намеренная простота.** Линейный pipeline без сложных зависимостей проще дебажить, проще объяснять команде и проще поддерживать. Сложность добавляется только тогда, когда она оправдана.

## ❓ Вопросы и ответы

**Q:** Почему ты выбрал именно этот проект для PDP?

**A:** Проект объединяет сразу несколько направлений, которые я хотел освоить глубже: практическое применение LLM в production workflow (а не просто эксперименты в ноутбуке), интеграция с GitHub Actions, AST-анализ Python-кода и проектирование инструментов с продуманным safety-дизайном. Это также реальная, а не учебная задача — тестовое покрытие — проблема, которая существует в большинстве команд. Наконец, проект достаточно мал, чтобы быть полностью понятым и поддерживаемым в одиночку.

**Q:** Это production-ready инструмент?

**A:** Версия 0.1.0 — это MVP с продуманной архитектурой, но не полностью готовый к production. Есть unit tests на ключевые компоненты, корректная обработка ошибок, dry-run mode для безопасного тестирования. Для реального production потребовалось бы: более широкое тестовое покрытие (особенно integration tests), обработка rate limits Vertex AI (retry с exponential backoff), поддержка нескольких Python-версий в pytest runner, возможно cache для idempotent runs. Но главное — архитектурные решения сделаны правильно с самого начала: human-in-the-loop, no auto-commit, reviewable artifacts. Это не надо переделывать при масштабировании.

**Q:** Что добавишь в следующей версии?

**A:** В первую очередь — retry/backoff для Vertex AI вызовов и parallel обработку файлов (сейчас sequential). Далее: поддержка конфигурируемых pytest-плагинов (например, pytest-mock), PR-комментарий с кратким summary прямо в GitHub (через GitHub API). Долгосрочно интересно добавить coverage-aware targeting — запускать инструмент только для файлов, у которых coverage упала ниже порога, что даст более точечное применение.

**Q:** Почему нет auto-commit?

**A:** Это принципиальное архитектурное решение. LLM генерирует вероятностный вывод — даже с `temperature=0.0` и repair loop тест может технически проходить pytest, но при этом тестировать неправильное поведение или содержать неверные ожидания. Commit кода — это явное утверждение разработчика «я проверил это и беру ответственность». Инструмент не может взять на себя эту ответственность. Кроме того, auto-commit в PR-workflow создал бы проблему: чей коммит это, как его откатить, как отследить источник. Разделение «предложить» и «принять» — это правильный safety-паттерн для любой AI-assisted automation.

**Q:** Чем это отличается от GitHub Copilot или готовых генераторов тестов?

**A:** Copilot работает inline в редакторе и генерирует тесты по запросу разработчика — то есть требует его активного участия. Этот инструмент работает автоматически в CI для любого PR, не требуя действий от разработчика. Готовые генераторы тестов (например, утилиты на базе ChatGPT) обычно не знают, что именно изменилось в PR, анализируют весь файл целиком и не интегрированы с git diff. Ключевые отличия этого инструмента: знание контекста diff (генерируем тесты только для изменённых функций), awareness существующих тестов (не дублируем, предлагаем обновления), repair loop (пробуем починить если pytest упал), интеграция с GitHub Actions как нативный CI-шаг.

**Q:** Что если LLM сгенерирует плохой тест — тест, который проходит, но тестирует не то?

**A:** Это главный известный риск. Инструмент использует несколько уровней защиты: `temperature=0.0` для детерминизма, явные системные инструкции запрещающие over-mocking pure functions и тестирование implementation details, repair loop корректирует синтаксические и runtime ошибки. Но семантическую корректность (правильные ли ожидания) инструмент гарантировать не может — это именно та причина, по которой обязателен human review. Developer должен прочитать сгенерированный тест и убедиться, что он проверяет правильное поведение. Инструмент — черновик, а не финальный ответ.

**Q:** Сколько стоит запускать этот инструмент?

**A:** Стоимость зависит от модели и объёма PR. Для `gemini-2.5-flash` (используется по умолчанию) стоимость существенно ниже, чем для Pro-моделей. Грубая оценка для типичного PR с 2–3 изменёнными файлами и несколькими функциями: 10 000–50 000 токенов на входе (source code + existing tests) плюс 1 000–5 000 токенов на выходе. При частых PR-ах в активном репозитории это может быть несколько долларов в месяц. `dry_run=true` полностью исключает LLM-вызовы для тестирования самого pipeline. Также можно ограничить запуск workflow через `paths` фильтр в GitHub Actions — что уже сделано (запускается только при изменении `.py` файлов).

**Q:** Как инструмент аутентифицируется в Vertex AI в GitHub Actions?

**A:** Используется Workload Identity Federation — современный и безопасный способ без долгоживущих service account ключей. В workflow прописаны `permissions: id-token: write` и `contents: read`. GitHub Actions выпускает короткоживущий OIDC-токен, который обменивается на Google Cloud credentials через Workload Identity Pool. `GOOGLE_CLOUD_PROJECT` и `GOOGLE_CLOUD_LOCATION` передаются через GitHub Secrets. Это соответствует best practices для CI/CD интеграции с GCP.

**Q:** Почему используется `ast` вместо запуска кода или использования type checker?

**A:** `ast` — стандартная библиотека, работает статически (не требует установки зависимостей файла, не запускает код), достаточно быстра для CI и предоставляет всё необходимое: имена функций, сигнатуры, аннотации, номера строк. Type checkers (mypy, pyright) дали бы больше семантической информации, но добавили бы зависимость и требование корректной настройки окружения. Runtime-анализ создал бы security риски и проблемы с зависимостями. AST — правильный баланс для данной задачи.

**Q:** Что происходит, если repair loop не помог и тесты всё равно падают?

**A:** Pipeline не прерывается. `FileResult` получает `status="failed"` с сообщением "Generated tests failed even after repair attempts." Файл с упавшими тестами всё равно сохраняется в `tests/generated/` как артефакт — developer может посмотреть, что именно не так, и либо починить вручную, либо написать тест с нуля. Это лучше, чем молча пропустить файл: разработчик знает, что инструмент попытался, но не справился, и может принять осознанное решение.

## 🎤 Что сказать вслух

> Этот проект — не магия. Это pipeline, который делает одну вещь хорошо: автоматически предлагает тесты для изменённого кода, чтобы разработчик не начинал с чистого листа.

> Главный принцип безопасности — всё, что делает LLM, это предложения. Ни один байт не попадает в репозиторий без явного одобрения разработчика.

> Repair loop — это не "LLM чинит свои ошибки сам". Это детерминированный feedback: pytest говорит что именно упало, LLM получает эту информацию и пробует снова. Лимит попыток жёсткий — бесконечные петли исключены.

> `temperature=0.0` — это сознательный выбор. Тесты должны быть предсказуемыми. Творческий LLM в генерации тестов — это антипаттерн.

> Dry-run mode означает, что сам инструмент можно тестировать без реального LLM и без расходов. CI самого проекта работает именно в этом режиме.

> Простота pipeline — это фича, не ограничение. Когда что-то ломается, любой член команды может прочитать `pipeline.py` и понять, на каком шаге и почему.

> Артефакты в GitHub Actions — это не просто файлы. Это прозрачность: ревьюер PR видит в Step Summary отчёт инструмента и может оценить качество предложенных тестов наравне с quality кода.
