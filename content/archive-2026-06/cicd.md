## Простыми словами

**CI/CD** — это автоматизация того, что раньше люди делали руками после написания кода. **CI (Continuous Integration)** — непрерывная интеграция: каждый раз, когда разработчик отправляет изменения, автоматически собирается проект, прогоняются линтеры и тесты. Цель — поймать поломку как можно раньше, пока изменение маленькое и его легко чинить. **CD** расшифровывается двояко: **Continuous Delivery** (артефакт всегда готов к выкатке, но финальную кнопку «деплой» жмёт человек) и **Continuous Deployment** (выкатка в прод происходит автоматически после зелёных тестов).

Технически это «пайплайн» — последовательность шагов, которые запускает CI-система (в нашем случае **GitHub Actions**) в ответ на событие: push, открытие pull request, расписание. Пайплайн крутится на чистой виртуальной машине (runner), что гарантирует воспроизводимость: «работает у меня на ноутбуке» больше не аргумент.

**Coding Agent** — это программа поверх LLM, которая не просто болтает, а выполняет инженерную задачу с помощью инструментов: читает файлы, запускает команды, анализирует результат, исправляет себя в цикле. Локально такой агент работает интерактивно — рядом сидит человек и подтверждает действия. В CI/CD агент запускается **неинтерактивно**: его дёргает пайплайн, он отрабатывает сам и оставляет результат, который человек проверит позже.

Зачем их сочетать: пайплайн — это идеальный «триггер и песочница» для агента. Есть чёткое событие (открыли PR), изолированное окружение, доступ к коду и предсказуемый момент, когда агенту есть что делать. Агент превращается в ещё один шаг пайплайна, как линтер или тесты.

> Ключевая мысль проекта: в **AI Unit Test Assistant** CI/CD используется **не для деплоя**, а для **автозапуска AI-ассистента на каждом pull request**. Мы выкатываем не приложение в прод — мы запускаем агента, который генерирует unit-тесты и кладёт их как артефакт для ревью.

То есть знакомый каркас GitHub Actions (триггер → runner → шаги → артефакт) переиспользован под новую задачу: вместо «собрать и задеплоить» — «запустить coding agent и отдать его вывод человеку на проверку». Принцип безопасности тот же, что в обычном CD: автоматика готовит результат, но решение принимает человек (**human review обязателен**, **no auto-commit**).

## Детальный разбор

### CI vs CD и стадии пайплайна

Разделение по ответственности:

- **Continuous Integration** — частая интеграция изменений в общую ветку с автоматической проверкой: build, lint, unit-тесты, иногда сканеры безопасности. Отвечает на вопрос «не сломал ли я сборку и тесты».
- **Continuous Delivery** — после успешного CI собирается готовый к выкатке артефакт (образ, пакет), но релиз в прод требует ручного подтверждения. Отвечает за «всегда готовы выкатить».
- **Continuous Deployment** — то же самое, но финальный деплой автоматический, без ручной кнопки. Требует высокой зрелости тестов и мониторинга.

Типовые стадии пайплайна:

```
checkout → setup (язык/зависимости) → build → lint → test →
  → package/artifact → (gate: review/approval) → deploy → smoke-test
```

В нашем проекте «правый хвост» (deploy) заменён на запуск агента и выгрузку артефакта: `checkout → setup-python → install → run agent → upload-artifact`.

### Полная анатомия GitHub Actions

GitHub Actions — это CI/CD-движок, встроенный в GitHub. Конфигурация лежит в YAML-файлах в каталоге `.github/workflows/`. Каждый файл — отдельный **workflow**.

#### name

```yaml
name: AI Test Assistant
```

Человекочитаемое имя workflow, отображается в UI на вкладке Actions. Необязательное; если опустить — GitHub возьмёт путь к файлу.

#### Триггеры on

Блок `on` описывает, какие события запускают workflow. Основные:

- **push** — пуш в ветку/тег. Часто ограничивают ветками: `branches: [ main ]`.
- **pull_request** — открытие/обновление PR. Workflow выполняется в контексте **головы PR**, но с **ограниченными правами** для PR из форков: `GITHUB_TOKEN` получает read-only, и **секреты не передаются** в форк-PR. Это защита от утечки.
- **pull_request_target** — то же событие, но workflow берётся из **базовой ветки** и выполняется **с полными правами и доступом к секретам** в контексте базы. Опасен: если в таком workflow сделать `checkout` кода из PR и затем выполнить его (сборка, скрипты), злоумышленник из форка получает выполнение кода с вашими секретами. Использовать только для безопасных операций (метки, комментарии) и **никогда не чекаутить и не запускать недоверенный код PR** с правами на запись.
- **workflow_dispatch** — ручной запуск кнопкой в UI или через API; можно объявить входные параметры `inputs`.
- **schedule** — запуск по расписанию через cron: `- cron: "0 3 * * *"` (UTC). Время не гарантировано минута-в-минуту при высокой нагрузке.
- **workflow_call** — делает workflow переиспользуемым (вызывается из другого workflow).

Фильтры внутри события:

- **paths / paths-ignore** — запускать только если изменились файлы по маске. У нас именно так: `paths: [ "**/*.py" ]` — ассистент стартует только когда тронули Python-файлы.
- **branches / branches-ignore** — фильтр по веткам (для push и pull_request).
- **tags** — фильтр по тегам.

#### jobs

```yaml
jobs:
  ai-test-assistant:
    runs-on: ubuntu-latest
```

`jobs` — словарь задач. Каждый job по умолчанию выполняется **параллельно** и на **отдельном** runner'е (отдельная чистая VM). У job есть свой id (ключ), `runs-on`, `permissions`, `env`, `steps`, `needs`, `if`, `strategy`.

#### runs-on

Тип runner'а:

- **ubuntu-latest / windows-latest / macos-latest** — managed-раннеры GitHub (чистая VM на каждый запуск, тарифицируется по минутам, macOS дороже).
- **self-hosted** — ваши собственные машины (метками выбирается пул). Плюсы: доступ к внутренней сети, спец-железо (GPU), отсутствие платы за минуты. Минусы: вы сами отвечаете за обновления и **изоляцию** — особенно опасно для публичных репозиториев и PR из форков.

> Версия `*-latest` со временем меняется (например, образ ubuntu обновляется). Если нужна стабильность — пиньте конкретную версию образа.

#### steps, uses vs run

`steps` — упорядоченный список шагов внутри job, выполняются **последовательно**. Шаг — это либо вызов готового action, либо shell-команда:

- **uses** — подключить переиспользуемый action: `uses: actions/checkout@v4`. Часть после `@` — это **версия/ref** (тег, ветка или SHA). Для безопасности сторонние actions лучше пинить на полный commit SHA.
- **run** — выполнить команду в shell runner'а (по умолчанию bash на Linux). Многострочный блок через `|`.
- **with** — входные параметры для `uses`-action.
- **name** (у шага) — подпись шага в логах.

#### Популярные actions

- **actions/checkout@v4** — клонирует репозиторий в runner. Важный параметр `fetch-depth`: по умолчанию `1` (shallow, только последний коммит). Для diff между ветками нужен полный лог — ставим `fetch-depth: 0`. Именно поэтому в нашем ассистенте стоит `fetch-depth: 0`: мы сравниваем PR с base-ref.
- **actions/setup-python@v5** — ставит нужную версию Python и кладёт её в PATH; параметр `python-version`. Умеет кэшировать pip-зависимости через `cache: pip`.
- **actions/upload-artifact@v4** — выгружает файлы/папки как артефакт запуска (скачивается из UI, хранится ограниченное время). Важно: v4 несовместим по протоколу с download-artifact@v3, версии нужно держать согласованными.
- **actions/cache@v4** — кэширует каталоги между запусками по ключу (например, `~/.cache/pip`). Ускоряет install, но не для секретных данных.

#### env, secrets, vars

- **env** — переменные окружения. Можно задать на уровне workflow, job или step. У нас на шаге запуска агента прокидываются `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`, `GEMINI_MODEL`.
- **secrets** — зашифрованные значения (`${{ secrets.NAME }}`), задаются в настройках репо/организации/environment. В логах автоматически маскируются. **Не передаются** в workflow для pull_request из форка.
- **vars** — несекретные конфигурационные переменные (`${{ vars.NAME }}`), видны в логах. Подходят для имени модели, региона и т.п. У нас `GEMINI_MODEL` — это `vars`, а проект/локация — `secrets`.

#### permissions и least-privilege, GITHUB_TOKEN

В каждом запуске GitHub выдаёт временный токен `GITHUB_TOKEN` (живёт только на время job). Блок `permissions` задаёт его права по **принципу наименьших привилегий** — выдавать только то, что нужно:

```yaml
permissions:
  contents: read
  pull-requests: write
  id-token: write
```

- `contents: read` — читать код, без права пушить.
- `pull-requests: write` — писать в PR (комментарии, метки).
- `id-token: write` — **разрешить выпуск OIDC-токена** для федеративной аутентификации в облаке (см. ниже). Без него OIDC не работает.

Если `permissions` не указан, применяется дефолт уровня репо/организации (может быть как read-only, так и расширенный — зависит от настроек). Лучшая практика — явно объявить минимальный набор.

#### if-условия, контексты и выражения

`if` управляет тем, выполнять ли job/step. Внутри — выражения `${{ }}` и контексты:

- **github.*** — данные события: `github.event_name`, `github.base_ref`, `github.ref`, `github.actor`, `github.sha`.
- Status-функции: **success()** (по умолчанию), **failure()**, **always()**, **cancelled()**.

`always()` критичен для шагов «выгрузить отчёт/артефакт даже если упало» — у нас `if: always()` на шагах добавления отчёта в summary и upload-artifact, чтобы получить диагностику даже при падении тестов внутри агента.

#### needs и зависимости job'ов

`needs: [build]` делает job зависимым: он стартует только после успеха указанных job'ов. Так строят последовательные стадии (test → package → deploy). Без `needs` job'ы идут параллельно.

#### strategy.matrix

Запуск одного job в нескольких вариациях:

```yaml
strategy:
  matrix:
    python-version: ["3.10", "3.11", "3.12"]
```

GitHub создаст по job на каждое значение (полное декартово произведение при нескольких осях). `fail-fast: false` не даёт отменять остальные при первом падении. Удобно для проверки на нескольких версиях Python/ОС.

#### concurrency

Группировка запусков, чтобы не гонять лишнее параллельно:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

При новом пуше в ту же ветку/PR старый ещё бегущий запуск отменяется. Экономит минуты CI и деньги на вызовах LLM.

#### Reusable workflows и composite actions

- **Reusable workflow** (`on: workflow_call`) — целый workflow, вызываемый из других через `uses: owner/repo/.github/workflows/file.yml@ref`, с `inputs`/`secrets`. Так выносят общий пайплайн на много репозиториев.
- **Composite action** — несколько шагов, упакованных в один переиспользуемый action (`runs.using: "composite"`). В отличие от reusable workflow, встраивается внутрь job как один шаг.

### Секреты и безопасная аутентификация в облако: OIDC + Workload Identity Federation

Классический способ — положить в `secrets` **сервисный JSON-ключ** GCP. Проблемы: ключ долгоживущий, его легко утащить из логов/артефактов, его нужно вручную ротировать, и при утечке он действует, пока его не отозвали.

**OIDC (OpenID Connect)** решает это через **короткоживущие токены без хранимых секретов**. Механика:

```
GitHub Actions (id-token: write)
        ↓ выпускает подписанный OIDC-JWT (кто: репо/ветка/workflow)
GCP STS + Workload Identity Federation (проверяет issuer и claims)
        ↓ обменивает JWT на короткоживущий access token
Vertex AI API (вызов Gemini)
```

1. Job с `id-token: write` запрашивает у GitHub OIDC-токен (JWT) с claims: какой репозиторий, какая ветка, какой workflow, кто запустил.
2. **Workload Identity Federation** в GCP настроен на доверие к issuer'у GitHub (`https://token.actions.githubusercontent.com`) и проверяет, что claims совпадают с разрешённым шаблоном (например, конкретный репозиторий и ветка).
3. GCP STS обменивает этот JWT на **короткоживущий** access-token (impersonation сервисного аккаунта с минимальными ролями — например, только `Vertex AI User`).
4. Этим токеном агент вызывает Vertex AI / Gemini.

Преимущества: **нет долгоживущих ключей** в репозитории, токен живёт минуты, доступ ограничен конкретным репо/веткой через condition на pool, ротация не нужна. Роль `id-token: write` — обязательное условие, чтобы GitHub вообще выпустил OIDC-токен. На практике это поднимают через `google-github-actions/auth` с параметрами `workload_identity_provider` и `service_account`.

### Артефакты, кэширование, ускорение пайплайна

- **Артефакты** (`upload-artifact`) — файлы, которые нужно вынести из эфемерного runner'а: сгенерированные тесты, отчёты, логи, coverage. Хранятся ограниченное время (настраивается retention), скачиваются из UI или API.
- **GITHUB_STEP_SUMMARY** — Markdown-сводка прямо на странице запуска. У нас отчёт ассистента пишется в `$GITHUB_STEP_SUMMARY`, чтобы ревьюер видел результат, не скачивая артефакт.
- **Кэширование** (`actions/cache` или `cache` в setup-actions) — переиспользование зависимостей между запусками по ключу; сильно ускоряет install.
- Прочие ускорители: `concurrency` с `cancel-in-progress`, `paths`-фильтры (не запускать лишнее), shallow `checkout` где не нужен полный лог, matrix-параллелизм.

### Coding Agents в CI/CD

Coding agent в пайплайне — это шаг, на котором запускается LLM-инструмент с доступом к коду и командам runner'а. Чем он отличается от локального запуска:

- **Неинтерактивность.** Нет человека, подтверждающего шаги. Агент должен отработать сам, детерминированно завершиться и вернуть код возврата.
- **Изоляция (sandbox).** Чистая эфемерная VM; после job всё стирается. Это и безопасность, и воспроизводимость.
- **Ограниченные права.** Не личный токен разработчика, а `GITHUB_TOKEN` с least-privilege; секреты строго контролируются (и недоступны для форк-PR).
- **Вывод вместо действия.** Хорошая практика — агент **не коммитит сам**, а оставляет **reviewable output** (артефакт, комментарий, отчёт), который человек проверяет.

Безопасные паттерны:

- **Reviewable output, а не auto-commit** — никаких прямых пушей в защищённую ветку.
- **Least privilege** — минимум прав у токена, минимум ролей у сервисного аккаунта.
- **Sandbox** — эфемерный runner, без доступа к прод-секретам без необходимости.
- **No overwrite** — не затирать существующие артефакты/тесты.

Примеры класса инструментов:

- **Этот проект** — генерация unit-тестов на PR, вывод в артефакт.
- **Dependabot / Renovate** — автоматическое обновление зависимостей: открывают PR с апдейтом, который ревьюит человек/CI.
- **Авто-ревью боты** — комментируют PR замечаниями (стиль, потенциальные баги), но не сливают изменения сами.

### Реалистичный пример ai-test-assistant.yml

```yaml
name: AI Test Assistant

on:
  pull_request:
    paths:
      - "**/*.py"

# least-privilege: только то, что нужно
permissions:
  contents: read          # читать код, не пушить
  pull-requests: write    # комментировать PR
  id-token: write         # выпуск OIDC-токена для GCP

# не гонять параллельные запуски на один PR
concurrency:
  group: ai-test-${{ github.ref }}
  cancel-in-progress: true

jobs:
  ai-test-assistant:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # полный лог для diff с base-ref

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      # OIDC -> GCP без долгоживущих ключей
      - name: Authenticate to Google Cloud
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_SERVICE_ACCOUNT }}

      - name: Install dependencies
        run: |
          python -m pip install -U pip
          pip install -e ".[dev]"

      - name: Run AI Test Assistant
        env:
          GOOGLE_CLOUD_PROJECT: ${{ secrets.GOOGLE_CLOUD_PROJECT }}
          GOOGLE_CLOUD_LOCATION: ${{ secrets.GOOGLE_CLOUD_LOCATION }}
          GEMINI_MODEL: ${{ vars.GEMINI_MODEL }}
        run: |
          ai-test-assistant run-pr-assistant \
            --base-ref origin/${{ github.base_ref }} \
            --output-dir tests/generated \
            --suggestions-dir reports/suggested-tests \
            --report reports/ai-test-report.md

      - name: Add report to GitHub summary
        if: always()
        run: cat reports/ai-test-report.md >> $GITHUB_STEP_SUMMARY

      - name: Upload generated tests and report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ai-test-assistant-output
          path: |
            tests/generated/
            reports/
```

> Номера версий action'ов (`checkout@v4`, `setup-python@v5`, `upload-artifact@v4`, `auth@v2`) актуальны на момент написания. Они эволюционируют; при обновлении читайте changelog — например, `upload-artifact@v4` сменил протокол и несовместим с `download-artifact@v3`.

## Инструменты и функции — шпаргалка

| Ключевое слово / инструмент | Что делает | Пример / значение |
| --- | --- | --- |
| `name` | Имя workflow в UI | `name: AI Test Assistant` |
| `on` | События-триггеры | `pull_request`, `push`, `schedule` |
| `on.pull_request.paths` | Запуск только при изменении файлов по маске | `paths: [ "**/*.py" ]` |
| `pull_request_target` | Триггер с правами/секретами базовой ветки (рискован) | не чекаутить недоверенный код PR |
| `workflow_dispatch` | Ручной запуск из UI/API | с опциональными `inputs` |
| `schedule` / `cron` | Запуск по расписанию (UTC) | `- cron: "0 3 * * *"` |
| `jobs` | Набор задач (по умолчанию параллельны) | каждая на своём runner'е |
| `runs-on` | Тип runner'а | `ubuntu-latest`, `self-hosted` |
| `steps` | Последовательные шаги job'а | `uses` или `run` |
| `uses` | Подключить готовый action (с `@ref`) | `actions/checkout@v4` |
| `run` | Shell-команда на runner'е | `python -m pytest -q` |
| `with` | Параметры action | `python-version: "3.12"` |

| `actions/upload-artifact` | Выгрузить файлы как артефакт | `name`, `path` |

| `env` | Переменные окружения | на workflow/job/step |
| `secrets` | Зашифрованные значения, маскируются | `${{ secrets.GOOGLE_CLOUD_PROJECT }}` |
| `vars` | Несекретные переменные, видны в логах | `${{ vars.GEMINI_MODEL }}` |
| `permissions` | Права `GITHUB_TOKEN` (least-privilege) | `contents: read` |
| `id-token: write` | Разрешить выпуск OIDC-токена | условие для WIF |
| `GITHUB_TOKEN` | Временный токен запуска | живёт на время job |
| `if` | Условие выполнения | `if: always()` |
| `always()` / `failure()` / `success()` | Status-функции | выгрузка артефакта при падении |
| `github.*` | Контекст события | `github.base_ref`, `github.sha` |
| `needs` | Зависимость между job'ами | `needs: [build]` |
| `strategy.matrix` | Запуск в нескольких вариациях | версии Python/ОС |
| `concurrency` | Группировка/отмена дублей | `cancel-in-progress: true` |
| `workflow_call` | Reusable workflow | вызов из другого workflow |
| composite action | Несколько шагов как один action | `runs.using: composite` |
| `$GITHUB_STEP_SUMMARY` | Markdown-сводка на странице запуска | отчёт ассистента |
| OIDC + WIF | Облачный доступ без хранимых ключей | обмен JWT на токен |

## Связь с проектом AI Unit Test Assistant

В репозитории два workflow:

- **`.github/workflows/ci.yml`** — классический CI: на `pull_request` и `push` в `main` ставит Python 3.12 и гоняет `pytest -q`. Это базовая проверка «не сломан ли проект».
- **`.github/workflows/ai-test-assistant.yml`** — собственно coding agent: триггер `pull_request` с фильтром `paths: [ "**/*.py" ]`, поэтому ассистент стартует только когда тронули Python-код.

Как именно встроен ассистент (по шагам реального файла):

1. `checkout@v4` c `fetch-depth: 0` — нужен полный лог, чтобы посчитать diff PR против `origin/${{ github.base_ref }}` и понять, какие `.py` изменились.
2. `setup-python@v5` (3.12) и установка пакета `pip install -e ".[dev]"`.
3. Шаг **Run AI Test Assistant** запускает CLI `ai-test-assistant run-pr-assistant` с base-ref, каталогом сгенерированных тестов, каталогом suggestions и путём отчёта. Внутри: определение изменённых файлов, AST-анализ, генерация pytest через Gemini (Vertex AI), запуск pytest, repair loop.
4. Аутентификация в GCP — через **OIDC/Workload Identity Federation** (`id-token: write` в `permissions`), без долгоживущих JSON-ключей. Конфигурация прокинута через `secrets` (проект, локация) и `vars` (`GEMINI_MODEL`).

**Reviewable artifacts.** Ассистент ничего не коммитит и не перезаписывает существующие тесты (**no auto-commit**, **no overwrite**, **human review обязателен**). Результат отдаётся двумя способами: отчёт пишется в `$GITHUB_STEP_SUMMARY` (виден прямо на странице запуска), а сгенерированные тесты и `reports/` выгружаются через `upload-artifact@v4`. Оба финальных шага помечены `if: always()` — диагностику получаем даже если pytest внутри агента упал.

**Права по least-privilege.** Токену даны ровно три права: `contents: read` (читать, не пушить), `pull-requests: write` (комментировать PR), `id-token: write` (OIDC). Запись в код намеренно не выдана — агент физически не может закоммитить.

**Переиспользуемость.** Каркас тривиально выносится в **reusable workflow** (`on: workflow_call` с `inputs`/`secrets`) и подключается в других репозиториях одной строкой `uses:`. Тогда логика ассистента централизована, а каждый проект лишь вызывает её, передавая свои параметры. Альтернатива — упаковать установку и запуск в **composite action**.

## ❓ Вопросы и ответы

**Q: Почему OIDC, а не сервисный JSON-ключ?**
**A:** JSON-ключ — долгоживущий секрет: его надо хранить, ротировать, и при утечке он действует до отзыва. OIDC выдаёт **короткоживущий** токен на лету: GitHub подписывает JWT с claims (репо/ветка/workflow), GCP через Workload Identity Federation проверяет их и обменивает на токен на минуты. Хранить нечего, ротация не нужна, доступ привязан к конкретному репозиторию/ветке.

**Q: Как безопасно хранить секреты в GitHub Actions?**
**A:** Чувствительное — в `secrets` (репо/организация/environment): они шифруются и маскируются в логах. Несекретное (имя модели, регион) — в `vars`. Никогда не печатать секреты в лог и не класть в артефакты. Для облака предпочтительнее вообще не хранить ключ, а использовать OIDC. Для прод-доступа — environment с required reviewers.

**Q: Что такое least-privilege permissions и как он применён?**
**A:** Выдавать токену только необходимый минимум прав. У нас `contents: read`, `pull-requests: write`, `id-token: write` — и всё. Права на запись в код нет, поэтому даже скомпрометированный шаг не запушит изменения. Дефолтные расширенные права лучше явно сузить блоком `permissions`.

**Q: В чём разница pull_request и pull_request_target и при чём тут инъекции?**
**A:** `pull_request` выполняет workflow из головы PR, но для форков даёт read-only токен и **не отдаёт секреты** — безопасно. `pull_request_target` берёт workflow из базовой ветки и запускает его **с секретами и правами на запись**. Если в нём сделать checkout кода PR и что-то из него выполнить (build, скрипт), злоумышленник из форка получит выполнение кода с вашими секретами — это и есть инъекция. Поэтому в `pull_request_target` нельзя запускать недоверенный код PR.

**Q: Как дебажить упавший пайплайн?**
**A:** Сначала логи конкретного шага в UI Actions (видно, какой step и команда упали). Включить debug-логи через секреты `ACTIONS_STEP_DEBUG=true` и `ACTIONS_RUNNER_DEBUG=true`. Использовать `if: always()` для выгрузки логов/отчётов даже при падении (как у нас). Воспроизвести локально (например, `act` или те же команды на чистом окружении). Проверить контексты/выражения, права токена и доступность секретов (для форк-PR их нет).

**Q: Сколько это стоит — минуты CI и Vertex AI?**
**A:** Два разных счёта. Минуты GitHub-раннеров тарифицируются по времени (Linux дешевле, macOS дороже; для приватных репо есть включённый лимит, дальше платно). Vertex AI/Gemini тарифицируется по токенам запроса и ответа. Экономим: `paths`-фильтр (агент не запускается без изменений `.py`), `concurrency` с `cancel-in-progress`, кэш зависимостей, ограничение числа итераций repair loop и объёма контекста, отправляемого в модель.

**Q: Self-hosted или hosted runners — что выбрать?**
**A:** Hosted (`ubuntu-latest`) — чистая VM на каждый запуск, ноль обслуживания, изоляция из коробки; платим за минуты. Self-hosted — свои машины: доступ к внутренней сети, спец-железо, нет платы за минуты, но вы сами обновляете и **изолируете** их. Для публичных репо и форк-PR self-hosted особенно рискован (чужой код на вашей машине). Для этого проекта hosted достаточно.

**Q: Как гарантировать, что агент не закоммитит плохой код?**
**A:** Архитектурно: токену не выдаётся `contents: write`, поэтому пуш физически невозможен. Процессно: агент только генерирует и кладёт **reviewable output** (артефакт + отчёт в summary), не перезаписывает существующие тесты (**no overwrite**), а слияние делает человек после ревью (**human review обязателен**). Защищённые ветки с required reviews — дополнительный барьер.

**Q: Зачем `fetch-depth: 0` в checkout?**
**A:** По умолчанию checkout делает shallow-клон (один коммит), и посчитать diff с базовой веткой нельзя. `fetch-depth: 0` тянет полную историю, чтобы сравнить PR с `origin/${{ github.base_ref }}` и определить изменённые `.py`-файлы.

**Q: Что делает `if: always()` и почему он важен здесь?**
**A:** По умолчанию шаг выполняется только если предыдущие успешны (`success()`). `always()` запускает шаг независимо от исхода. Мы вешаем его на «отчёт в summary» и «upload-artifact», чтобы получить диагностику и сгенерированные тесты даже когда pytest внутри агента упал.

**Q: Зачем `concurrency` и `cancel-in-progress`?**
**A:** Чтобы при новом пуше в тот же PR старый ещё бегущий запуск отменялся, а не висели параллельные прогоны. Это экономит и минуты CI, и платные вызовы Vertex AI, и убирает гонку артефактов.

**Q: Чем агент в CI отличается от запуска у разработчика локально?**
**A:** В CI он неинтерактивен (нет подтверждений человеком), работает в эфемерном sandbox (после job всё стирается), с least-privilege токеном и контролируемыми секретами (недоступны для форк-PR), и обязан детерминированно завершиться с кодом возврата. Локально это интерактивный инструмент с правами разработчика.

## 🎤 Что сказать вслух

> В этом проекте CI/CD используется не для деплоя приложения, а как триггер и песочница для AI-ассистента: открыли PR с изменением `.py` — запустился агент.

> Безопасность аутентификации держится на OIDC + Workload Identity Federation: никаких долгоживущих JSON-ключей, только короткоживущий токен, привязанный к нашему репозиторию.

> Права токена урезаны по least-privilege: `contents: read`, поэтому агент физически не способен закоммитить код — слияние всегда делает человек.

> Главный принцип — reviewable output вместо auto-commit: ассистент кладёт тесты и отчёт как артефакт и в summary, существующие тесты не перезаписывает.

> `pull_request_target` — это нож, которым легко порезаться: он даёт секреты и права на запись, поэтому недоверенный код PR в нём запускать нельзя.

> `fetch-depth: 0` и `if: always()` — два маленьких, но критичных штриха: первый даёт diff с базой, второй гарантирует артефакт и отчёт даже при падении.

> Стоимость под контролем: `paths`-фильтр, `concurrency` с отменой дублей и кэш зависимостей экономят и минуты CI, и платные вызовы Vertex AI.

> Каркас легко переиспользуется: выносим логику в reusable workflow или composite action, и другие репозитории подключают ассистента одной строкой.
