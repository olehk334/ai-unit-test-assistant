## Простыми словами

Time management в инженерии — это не про то, чтобы работать быстрее. Это про то, чтобы работать над **правильными вещами** в правильное время. Инженер без дисциплины тратит дни на красивый web UI, когда ключевой ценностью является алгоритм генерации тестов.

Self-discipline в контексте проекта — это умение сказать «нет» интересным идеям, которые не входят в текущий scope. Это отказ от overengineering: не строить distributed система, когда достаточно Python-скрипта. Это удержание фокуса на acceptance criteria, а не на «а вдруг понадобится».

Работа с дедлайнами — это не героизм в последнюю ночь, а декомпозиция задач на управляемые куски заранее и честная коммуникация при рисках срыва. Планирование должно оставлять буферы: реальные проекты всегда сложнее, чем кажется на старте.

Конкретно: выбрать из длинного backlog три задачи на неделю и довести их до done — это дисциплина. Закрыть вкладки, выключить уведомления и писать код два часа без переключений — это тоже дисциплина. Именно такие привычки отличают инженера, который стабильно доставляет, от того, кто вечно «почти готово».

## Почему это важно

Без явной приоритизации проект неизбежно разрастается. Начинается с «добавим web UI для удобства» — и вот уже нужна база данных, авторизация, миграции. Появляется идея «а давай auto-commit» — и это тянет за собой конфигурацию git-хуков, обработку конфликтов, rollback-механизм.

AI Unit Test Assistant мог стать: web-приложением с dashboard, multi-agent framework с несколькими LLM, системой с PR comments и auto-merge, поддержкой Java/TypeScript/Go, хранилищем истории тестов в PostgreSQL. Каждая из этих фич — реальная инженерная задача на несколько дней. Вместе они превратили бы MVP в полугодовой проект.

Дисциплина scope control позволила сосредоточиться на том, что прямо покрывает цели PDP: обнаружение изменений, анализ кода, генерация тестов через LLM, запуск pytest, repair loop, CI/CD через GitHub Actions, артефакты. Всё остальное — Excluded или Low priority.

Эта же дисциплина критична в реальных командах: без неё sprint превращается в «мы взяли 20 задач, закрыли 8». Time management — это инструмент предсказуемости и доверия.

## Prioritizing Tasks {#s8-prioritize}

Приоритизация — это процесс принятия решения, какую задачу делать следующей и что не делать вовсе. Существует несколько фреймворков; каждый применяется в своём контексте.

### MoSCoW

Делит фичи на четыре группы:

- **Must have** — без этого продукт не работает
- **Should have** — важно, но можно обойтись во временном релизе
- **Could have** — nice-to-have, добавляется только если есть время
- **Won't have (this time)** — явно исключено из текущего итерации

**Как применять:** пройти по backlog и задать вопрос «что сломается, если этого нет?». Если ответ «ничего» — это Could have или Won't have. MoSCoW хорошо работает для согласования scope с заказчиком на старте.

### Матрица Эйзенхауэра (Urgent/Important)

Четыре квадранта:

| | Важно | Не важно |
| --- | --- | --- |
| Срочно | Делаю сейчас | Делегирую |
| Не срочно | Планирую | Убираю |

**Как применять:** большинство ценных инженерных задач — «важно, не срочно». Если всё время уходит на «срочно + важно», это признак отсутствия планирования. Рефакторинг, тесты, документация — всегда важны, но редко срочны; без дисциплины они вытесняются.

### RICE

Числовая формула: `RICE = (Reach × Impact × Confidence) / Effort`

- **Reach** — сколько пользователей/случаев затронет фича (число)
- **Impact** — насколько сильно (1–3: minimal/medium/massive)
- **Confidence** — насколько уверен в оценках (0–100%)
- **Effort** — время в person-weeks

**Как применять:** вычислить RICE-score для каждой фичи и отсортировать по убыванию. Фичи с высоким RICE делаются первыми. Позволяет обосновать решение цифрами, а не интуицией.

### Value vs Effort (2x2)

Простая матрица: ось X — усилия (низкие/высокие), ось Y — ценность (низкая/высокая).

- Высокая ценность + низкие усилия → Quick wins, делать немедленно
- Высокая ценность + высокие усилия → Major projects, планировать
- Низкая ценность + низкие усилия → Fill-ins, делать в свободное время
- Низкая ценность + высокие усилия → Time sinks, не делать

**Как применять:** нарисовать на доске или в Miro, разместить фичи, выделить quick wins. Хорошо работает на воркшопах с командой.

### WSJF (Weighted Shortest Job First)

Из SAFe: `WSJF = Cost of Delay / Job Duration`. Чем выше стоимость задержки и чем короче задача — тем выше приоритет. Применяется в PI Planning для выбора между эпиками.

### Правило Парето 80/20

80% ценности даёт 20% фич. Задача — найти эти 20%. Для AI Unit Test Assistant: generate + run + report — это и есть те 20%, которые дают основную ценность.

### Что такое MVP и как резать scope

MVP (Minimum Viable Product) — минимальный набор функций, достаточный для проверки гипотезы или достижения цели. Критерий: «могу ли я получить обратную связь или достичь цели без этой фичи?». Если да — фича не в MVP.

При резке scope сначала убирать: UI-слои, интеграции с внешними системами, настраиваемость/конфигурируемость, исторические данные и аналитику. Оставлять: core value flow (happy path), базовое error handling, минимальную документацию.

## Dealing with Deadlines {#s8-deadlines}

Дедлайны — это ограничение, которое помогает принимать решения. Без дедлайна задача растягивается до бесконечности (закон Паркинсона: работа заполняет всё доступное время). С дедлайном приходится приоритизировать.

### Оценка задач

**Story Points** — относительные единицы сложности (1, 2, 3, 5, 8, 13 по Фибоначчи). Не измеряют время напрямую, измеряют сложность относительно эталонной задачи. Команда договаривается, что «1 point» — это, например, «добавить поле в конфиг».

**T-shirt sizing** — грубая оценка: XS/S/M/L/XL. Используется для быстрого ранжирования backlog без детального анализа. XS = часы, S = день, M = 2–3 дня, L = неделя, XL = больше недели.

**Three-point / PERT** — три оценки: оптимистичная (O), наиболее вероятная (M), пессимистичная (P). Итог: `(O + 4M + P) / 6`. Учитывает неопределённость; хорошо работает для задач с техническим риском.

**Почему оценки врут — planning fallacy.** Люди систематически недооценивают время выполнения задач, игнорируя прошлый опыт и концентрируясь на «идеальном» сценарии. Противодействие: reference class forecasting (смотреть на похожие задачи из прошлого), добавление явного буфера 20–30%, декомпозиция до задач размером не более одного дня.

### Декомпозиция

Задача размером больше двух дней содержит скрытую неопределённость. Декомпозировать до sub-tasks: каждая — конкретный артефакт (файл, функция, тест). Хороший критерий готовности sub-task: можно сделать pull request только с этим изменением.

### Итеративная / phased delivery

Вместо одного большого релиза — последовательные фазы с работающим результатом на каждом шаге. Это снижает риск: если фаза 3 задерживается, фазы 1–2 уже готовы и приносят ценность.

### Буферы

В оценку спринта закладывать не 100% доступного времени, а 70–80%. Оставшееся — на review, unexpected issues, коммуникацию. Deadline commitment делать только после того, как учтён буфер.

### Что резать под давлением дедлайна

**Резать scope, не качество.** Под давлением соблазн — убрать тесты, пропустить code review, написать «временный» код. Это технический долг, который в следующем спринте займёт больше времени, чем сэкономил сейчас.

Правильная стратегия: убрать фичи с низким приоритетом (Low/Excluded из таблицы выше), упростить UI/output, сдвинуть «should have» на следующую итерацию.

### Как коммуницировать срыв срока

Сообщать о риске срыва как можно раньше — не в день дедлайна. Структура сообщения: текущий статус, что блокирует, варианты (сдвинуть срок / урезать scope / добавить ресурс), рекомендация. Это называется «управление ожиданиями» и является признаком зрелости инженера.

## Balancing Focus and Multitasking {#s8-focus}

Multitasking — миф. Мозг не выполняет две когнитивные задачи одновременно; он переключается между ними. Каждое переключение стоит времени и энергии.

### Стоимость переключения контекста

Исследования (Gloria Mark, UC Irvine) показывают: после прерывания требуется в среднем 23 минуты, чтобы вернуться к глубокой работе. Для инженера это означает: одно Slack-сообщение в середине отладки может стоить полчаса продуктивного времени.

Применительно к проекту: работа над `llm_client.py` параллельно с `pytest_runner.py` — это context switching. Модульная архитектура (один этап — один файл) снижает этот эффект: в каждый момент времени вся нужная логика сосредоточена в одном файле с чётко определёнными входами/выходами.

### Deep Work

Концепция Кэла Ньюпорта: работа в состоянии полной концентрации без отвлечений, которая создаёт наибольшую ценность. Противоположность — shallow work (email, встречи, административные задачи).

Практики для глубокой работы:
- Блокировать в календаре 2–4 часа без встреч для работы над сложными задачами
- Уведомления в телефоне и Slack — off на время работы
- Один открытый проект/файл за раз

### Time-blocking

Назначать конкретные временные слоты для конкретных задач в календаре. Не «сегодня напишу тесты», а «10:00–12:00 — реализация `pytest_runner.py`». Это создаёт внешнее обязательство и снижает прокрастинацию.

### Pomodoro

25 минут работы без прерываний → 5-минутный перерыв. После четырёх «помидоров» — длинный перерыв 15–30 минут. Техника снижает субъективную тяжесть больших задач («нужно только 25 минут») и создаёт ритм работы.

### Single-tasking и WIP-лимиты

WIP (Work In Progress) limit — Kanban-практика: ограничить количество задач одновременно «в работе». Рекомендуемый лимит для одного человека: 1–2 задачи. Если задача заблокирована — это повод для коммуникации или исследования проблемы, а не повод начать третью задачу.

### Как модульная архитектура снижает context switching

В AI Unit Test Assistant каждый модуль отвечает за один этап pipeline:

```
git_utils.py       → Phase 2: git operations only
source_analyzer.py → Phase 3: AST parsing only
llm_client.py      → Phase 4a: Gemini API communication
test_generator.py  → Phase 4b: prompt building, response parsing
pytest_runner.py   → Phase 5: test execution, repair loop
report.py          → Phase 6a: output formatting
pipeline.py        → Phase 6b: orchestration
```

Работая над `pytest_runner.py`, не нужно держать в голове детали AST-парсинга. Это архитектурное решение с прямым эффектом на когнитивную нагрузку.

### Инструменты

- **Jira / Linear** — управление задачами, WIP-лимиты, sprint board
- **Trello** — простая Kanban-доска для личных проектов
- **Google Calendar / Outlook** — time-blocking, защита deep work слотов
- **Focus/Do Not Disturb режимы** — в macOS/Windows/iOS блокируют уведомления на заданное время

## Как проект демонстрирует Time Management

**Scope control.** Из ~15 возможных фич реализованы 7 ключевых, прямо покрывающих цели PDP. Это не случайность — это осознанное решение с явным списком исключений.

**Focus на PDP.** Каждый реализованный модуль трассируется к конкретному пункту PDP: LLM integration, CI/CD, automated testing, code analysis. Нет ни одного модуля «для красоты».

**Отказ от overengineering.** Выбран простейший pipeline: скрипт на Python + GitHub Actions. Не FastAPI, не Celery, не Redis, не Docker Compose. Инструмент соответствует задаче.

**Phased delivery.** Шесть фаз с работающим результатом на каждом шаге. После Phase 2 уже можно показать обнаружение изменённых файлов. После Phase 4 — первые сгенерированные тесты. Это снижает риск и даёт промежуточные checkpoint-ы.

**Чёткие acceptance criteria.** Каждый модуль имеет определённые входные/выходные интерфейсы. Критерий готовности — не «кажется, работает», а прохождение конкретных тестовых сценариев.

## ❓ Вопросы и ответы

**Q:** Как ты приоритизировал фичи в проекте?

**A:** Использовал комбинацию MoSCoW и value vs effort. Сначала определил «Must have» — то, без чего pipeline не работает вообще: обнаружение изменений, генерация тестов, запуск pytest. Затем проверил каждую остальную идею на вопрос «покрывает ли это цель PDP?». Всё, что не трассируется к PDP-пункту и требует значительных усилий — ушло в Excluded.

**Q:** Почему исключил web UI и auto-commit?

**A:** Web UI требует frontend-разработки, state management, возможно — базу данных. Это минимум 3–5 дней дополнительной работы, которая не добавляет ценности для PDP. Цель — демонстрация LLM-интеграции и CI/CD, а не UX. Auto-commit — это риск: автоматическая запись кода в репозиторий без человеческой проверки может сломать рабочий код. Сложность rollback и конфликтов делает эту фичу опасной для MVP.

**Q:** Как ты оценивал сроки на задачи?

**A:** Использовал t-shirt sizing для первичной оценки каждого модуля. Затем декомпозировал задачи размером M и выше до sub-tasks на один день. Для Phase 4 (LLM integration) применял three-point estimation, потому что там была неопределённость с API response parsing. В итоговый план заложил буфер 20% на integration issues между модулями.

**Q:** Что бы вырезал первым под давлением дедлайна?

**A:** Coverage reporting и dry-run mode. Они в Low priority именно потому, что добавляют удобство, но не влияют на core value. После них — repair loop: это важная фича, но в самом базовом варианте можно обойтись без неё, просто логируя упавшие тесты. Core flow (generate → run → report) должен выжить при любом давлении.

**Q:** Как ты борешься с прокрастинацией при работе над проектом?

**A:** Две техники работают лучше всего. Первая — декомпозиция до задач на 25–90 минут: когда задача конкретная и маленькая, начать легче. Вторая — time-blocking: ставлю в календарь слот «работа над модулем X» и отношусь к нему как к встрече, которую нельзя отменить. Если всё равно прокрастинирую, это обычно сигнал, что задача недостаточно декомпозирована или есть скрытый технический страх — тогда трачу 15 минут на разбор именно этой неопределённости.

**Q:** Как борешься с переключением контекста между модулями?

**A:** Архитектурно — один модуль за одну рабочую сессию. Если начал `pytest_runner.py`, не открываю `llm_client.py`, пока не закончу текущую задачу. Помогает явный WIP-лимит: не более одного модуля «в работе» одновременно. Если нужно что-то записать об другом модуле — добавляю в backlog, не переключаюсь сразу.

**Q:** Как понять, что это overengineering?

**A:** Три признака. Первый: решение сложнее проблемы — если для генерации текстового файла нужна очередь сообщений, это overengineering. Второй: «на будущее» — фичи, которые «могут пригодиться», но нет конкретного use case сейчас. Третий: решение требует объяснения своей необходимости дольше, чем реализация альтернативы. Проверочный вопрос: «Что сломается для пользователя, если этого не будет?»

**Q:** Как сказать «нет» запросу на лишнюю фичу?

**A:** Не говорить просто «нет» — объяснять через trade-offs. Структура: «Эта фича интересна, но она займёт X времени, что означает Y другая фича не попадёт в этот релиз. Если для тебя это важнее, давай обсудим, что мы убираем». Это переводит разговор из конфликта в совместное принятие решений. Для личного проекта то же самое: явно записать «это не делаем потому что...» в документации или комментарии в backlog.

**Q:** Как фазовая доставка помогла в управлении временем?

**A:** Каждая фаза заканчивается работающим артефактом, который можно показать и получить обратную связь. Это предотвращает классическую ловушку «почти готово»: если Phase 5 задержалась, Phase 1–4 уже задемонстрированы. Кроме того, фазы создают естественные checkpoint-ы для переоценки приоритетов — после Phase 3 стало понятно, какие данные реально нужны LLM, и это скорректировало Plan фазы 4.

**Q:** Как ты отслеживал прогресс по фазам?

**A:** GitHub Issues как lightweight task tracker: одна issue на sub-task, milestone на каждую фазу. Это позволяло видеть % completion фазы и принимать решения о буферах. Дополнительно — коммиты привязаны к фазам через naming convention, что даёт git log как хронологию прогресса.

## 🎤 Что сказать вслух

> Самый важный навык time management для инженера — это умение сказать «нет» интересной идее. Не потому что идея плохая, а потому что сейчас есть задача важнее.

> Я мог сделать web UI, базу данных, auto-commit, multi-agent систему. Каждая из этих фич технически интересна. Но ни одна из них не нужна для проверки гипотезы, которую я проверяю. Это и есть scope control.

> Planning fallacy — это когда мы оцениваем задачу в лучшем случае, игнорируя прошлый опыт. Противоядие: смотреть на похожие задачи из прошлого и добавлять буфер 20–30% по умолчанию.

> Context switching стоит 23 минуты после каждого прерывания. Модульная архитектура — это не только про код, это про когнитивную нагрузку разработчика. Один модуль — один этап — один файл: это решение, которое помогает фокусироваться.

> Когда дедлайн давит — режь scope, не качество. Технический долг, набранный под давлением, в следующем спринте стоит больше, чем время, которое сэкономил.

> Сообщить о риске срыва дедлайна за неделю до дедлайна — это профессионализм. Сообщить за день — это кризис. Разница в одном слове: заранее.

> Deep work — это когда два часа без уведомлений решают то, что четыре часа с ними не могут. Это не про количество времени, это про качество внимания.
