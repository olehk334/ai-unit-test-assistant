## Простыми словами

**Unit-тест** — это маленькая программа-проверка, которая берёт одну функцию или метод (unit, «единицу» кода), вызывает её с конкретными входными данными и проверяет, что результат именно такой, какой мы ожидаем. Если кто-то случайно сломает эту функцию при правке, тест «упадёт» и сразу подскажет, что именно сломалось, ещё до того как код доедет до продакшена.

Зачем они нужны. Без тестов любое изменение — это риск: поправил одно, незаметно сломал другое. Это называется **regression** (регрессия) — когда раньше работавшая функциональность перестаёт работать. Тесты ловят регрессии автоматически: вместо того чтобы вручную перепроверять весь продукт после каждой правки, мы запускаем набор тестов и за секунды видим, всё ли в порядке. Тесты также служат живой документацией: по тесту видно, как функцию задумано использовать.

**Test automation** в широком смысле — это про то, чтобы тесты запускались сами (например, на каждый push в CI), а не вручную. Но запуск — лишь часть. Самое трудоёмкое и скучное — это **писать** тесты и **поддерживать** их после рефакторинга.

Что именно автоматизирует наш ассистент. Он закрывает три задачи, а не только запуск:

1. **Генерация first draft** — для изменённых функций сам пишет черновик pytest-тестов (нормальные кейсы, граничные, ошибки). Человеку остаётся проверить и доработать, а не писать с нуля.
2. **Прогон и самопочинка** — запускает pytest по сгенерированным тестам, и если они падают из-за своих же ошибок (неверный импорт, опечатка в ожидаемом значении), отправляет вывод обратно в модель и просит починить **только тест** — это **repair loop**.
3. **Suggestions после рефакторинга** — если функция изменилась, а тесты к ней уже есть, ассистент предлагает обновлённую версию этих тестов. Важно: предложение сохраняется **отдельным файлом**, существующие тесты не перезаписываются.

> Ключевая философия проекта: **no auto-commit, no overwrite, human review обязателен.** Ассистент — это «умный черновик», а не автор, которому доверяют вслепую.

## Детальный разбор

### Основы unit-тестирования

**AAA (Arrange-Act-Assert)** — каноническая структура теста из трёх фаз:

```python
def test_discount_applies_to_total():
    cart = Cart(items=[Item(price=100)])   # Arrange — подготовка данных
    total = cart.total(discount=0.1)       # Act — одно действие, которое тестируем
    assert total == 90                     # Assert — проверка результата
```

**Изоляция.** Хороший unit-тест проверяет одну единицу кода в отрытыве от внешнего мира: без реальной БД, сети, файловой системы, текущего времени. Зависимости заменяются на mock/stub или на временные ресурсы (`tmp_path`). Так тест быстрый и не зависит от чужих сбоев.

**Детерминизм.** Тест при одинаковом входе всегда даёт одинаковый результат. Источники недетерминизма — текущее время, `random`, порядок словарей/множеств, многопоточность, сеть. Их надо фиксировать (заморозить время, задать seed, замокать). Недетерминированный тест становится **flaky** — иногда зелёный, иногда красный без изменений кода, и ему перестают верить.

**Regression.** Каждый тест — это «защёлка»: однажды зафиксированное поведение нельзя сломать незаметно. Когда находят баг, на него обычно сначала пишут падающий тест, потом чинят код — так баг не вернётся.

**Test pyramid.** Тестов разного уровня должно быть разное количество:

```
        /\
       /  \    E2E / UI         — мало, медленные, хрупкие
      /----\
     /      \  Integration      — среднее число
    /--------\
   /          \ Unit            — много, быстрые, изолированные
  /------------\
```

Основание пирамиды — многочисленные быстрые unit-тесты; наверху — немного медленных end-to-end. Ассистент работает именно на уровне unit.

**Coverage как метрика и её пределы.** Покрытие (coverage) показывает, какой процент строк/веток кода был исполнен во время тестов. Это полезный индикатор «слепых зон» (что вообще ни разу не вызвали), но это **метрика количества, а не качества**. Можно получить 100% покрытия тестом, который вызывает функцию, но почти ничего не проверяет в `assert`. Высокий coverage — необходимое, но не достаточное условие хороших тестов.

**Тестировать поведение, а не реализацию.** Тест должен проверять наблюдаемый контракт функции (что на входе → что на выходе/какой эффект), а не внутренние детали (какие приватные методы вызывались в каком порядке). Тесты «под реализацию» ломаются при любом безобидном рефакторинге, хотя поведение не менялось — это лишний шум. Именно поэтому ассистент тестирует **публичные** функции и игнорирует приватные.

### pytest по существу

**Автодискавери тестов.** pytest сам находит тесты по соглашению об именах: файлы `test_*.py` или `*_test.py`, внутри них функции `test_*` и классы `Test*` (без `__init__`). Никакой регистрации не нужно — положил файл, запустил `pytest`, он подхватился.

```python
# файл tests/test_math.py
def test_add():
    assert add(2, 3) == 5
```

**Голый `assert` и интроспекция.** В pytest не нужны методы вроде `assertEqual` — пишется обычный `assert`. При падении pytest переписывает (assertion rewriting) выражение и показывает фактические значения сторон:

```python
def test_values():
    assert compute() == 42   # при падении покажет: assert 41 == 42
```

**`pytest.raises` — проверка исключений.** Проверяет, что код кидает нужное исключение; через `match` можно проверить и текст (regex):

```python
import pytest

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError, match="division by zero"):
        divide(1, 0)
```

**`pytest.approx` — сравнение чисел с плавающей точкой.** `0.1 + 0.2 == 0.3` — это `False` из-за погрешности float. `approx` сравнивает с допуском:

```python
import pytest

def test_float_sum():
    assert 0.1 + 0.2 == pytest.approx(0.3)
```

**Фикстуры (`@pytest.fixture`).** Фикстура — это подготовка данных/ресурсов, которые тест получает как аргумент по имени. pytest сам видит, какие фикстуры запрошены, и подставляет их:

```python
import pytest

@pytest.fixture
def sample_user():
    return User(name="Alice", age=30)

def test_greeting(sample_user):           # имя аргумента = имя фикстуры
    assert greet(sample_user) == "Hi Alice"
```

**`scope`** управляет, как часто фикстура пересоздаётся:

- `function` (по умолчанию) — заново на каждый тест;
- `class` — одна на класс;
- `module` — одна на файл;
- `session` — одна на весь прогон (например, дорогой коннект).

**`conftest.py`** — специальный файл: фикстуры в нём автоматически доступны всем тестам в этой папке и вложенных, без импорта. Туда выносят общие фикстуры.

**yield-фикстуры и teardown.** Если фикстуре нужна уборка после теста, используют `yield`: код до `yield` — setup, код после — teardown (выполнится даже при падении теста):

```python
@pytest.fixture
def db_connection():
    conn = connect()          # setup
    yield conn                # отдаём в тест
    conn.close()              # teardown
```

**`autouse=True`** — фикстура применяется ко всем тестам в области видимости без явного запроса (например, сброс глобального состояния).

**Фикстуры-зависимости.** Одна фикстура может запрашивать другую как аргумент — pytest выстроит цепочку:

```python
@pytest.fixture
def db(): ...

@pytest.fixture
def repo(db):                 # repo зависит от db
    return Repo(db)
```

**Встроенные фикстуры:**

- **`tmp_path`** — уникальная временная папка (`pathlib.Path`) на тест; для тестов работы с файлами без мусора в репозитории.
- **`monkeypatch`** — безопасно подменяет атрибуты/переменные окружения/словари на время теста и автоматически откатывает: `monkeypatch.setattr(mod, "now", lambda: fixed)`, `monkeypatch.setenv("KEY", "v")`, `monkeypatch.chdir(path)`.
- **`capsys`** — захватывает то, что код печатает в `stdout`/`stderr`: `out, err = capsys.readouterr()`.
- **`caplog`** — захватывает записи логирования: после вызова смотрят `caplog.records` или `caplog.text`.

**Параметризация `@pytest.mark.parametrize`.** Один тест прогоняется на множестве наборов данных — каждый набор это отдельный кейс в отчёте:

```python
import pytest

@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (0, 0, 0),
    (-1, 1, 0),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

**Маркеры (`@pytest.mark.*`).** Метки на тестах:

- `@pytest.mark.skip(reason=...)` — всегда пропустить;
- `@pytest.mark.skipif(condition, reason=...)` — пропустить при условии (например, версия Python, отсутствие зависимости);
- `@pytest.mark.xfail(reason=...)` — «ожидаемо падает» (известный баг): если упал — это `xfail`, если внезапно прошёл — `xpass`;
- **кастомные маркеры** — например, `@pytest.mark.slow`, регистрируются в конфиге, потом `pytest -m slow` или `-m "not slow"`.

**Мокирование (`unittest.mock`).** Mock — это объект-заглушка, который записывает, как его вызывали, и возвращает то, что ему задали:

- **`Mock` / `MagicMock`** — `MagicMock` дополнительно поддерживает «магические» методы (`__len__`, `__iter__` и т.д.);
- **`return_value`** — что вернёт мок при вызове: `m.return_value = 42`;
- **`side_effect`** — функция/исключение/список: можно заставить мок бросить исключение или возвращать разное на разных вызовах;
- **`assert_called_with(...)`**, `assert_called_once_with(...)`, `call_count` — проверка, как вызвали.

**`patch`** временно подменяет объект по «пути, где он используется»:

```python
from unittest.mock import patch

# как декоратор — мок прокидывается аргументом
@patch("myapp.service.requests.get")
def test_fetch(mock_get):
    mock_get.return_value.json.return_value = {"ok": True}
    assert fetch() == {"ok": True}

# как контекстный менеджер
with patch("myapp.service.send") as mock_send:
    do_work()
    mock_send.assert_called_once()

# patch.object — подменить атрибут конкретного объекта/класса
with patch.object(Client, "connect", return_value=None):
    ...
```

> Важный нюанс `patch`: путь указывают туда, **где имя используется**, а не где определено. Если в `service.py` написано `from x import get`, мокать надо `service.get`, а не `x.get`.

**`pytest-mock` и фикстура `mocker`.** Плагин даёт фикстуру `mocker` — обёртку над `unittest.mock`, которая сама откатывает патчи после теста (не нужен `with`/декоратор):

```python
def test_with_mocker(mocker):
    m = mocker.patch("myapp.service.send", return_value=True)
    do_work()
    m.assert_called_once()
```

**Измерение покрытия (`pytest-cov`).** Плагин поверх `coverage.py`:

```bash
pytest --cov=myapp --cov-report=term-missing --cov-report=html
```

`--cov=myapp` — какой пакет мерить; `term-missing` — печатает в терминал непокрытые строки; `html` — отчёт-страница. Можно требовать минимум: `--cov-fail-under=80`.

**Полезные флаги CLI:**

- `-k "expr"` — запустить тесты, чьи имена подходят под выражение: `-k "login and not slow"`;
- `-x` — остановиться на первом падении;
- `--maxfail=N` — остановиться после N падений;
- `-q` / `-v` — тихий / подробный вывод;
- `-rA` — итоговая сводка по всем (включая skip/xfail) с причинами;
- `--lf` (last-failed) — гонять только то, что упало в прошлый раз; `--ff` — сначала упавшие.

**Конфигурация в `pyproject.toml`.** Настройки pytest держат в секции `[tool.pytest.ini_options]`:

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q --strict-markers"
markers = [
    "slow: marks tests as slow",
]
```

`--strict-markers` запрещает незарегистрированные маркеры (защита от опечаток).

### Анализ исходника через модуль `ast`

`ast` — стандартный модуль, который парсит Python-код в дерево (Abstract Syntax Tree). Это надёжнее, чем regex: мы работаем со структурой кода, а не с текстом.

Что ищем на верхнем уровне модуля:

- **`ast.FunctionDef`** — обычная функция;
- **`ast.AsyncFunctionDef`** — `async def` функция;
- **`ast.ClassDef`** — класс; внутри его `body` ищем методы (те же `FunctionDef`/`AsyncFunctionDef`).

**Как отличить приватное.** По соглашению Python имя, начинающееся с `_`, считается приватным (`_helper`, `__secret`). Мы пропускаем такие функции/методы/классы: их контракт не публичный, тестировать их напрямую — значит привязывать тесты к реализации.

```python
for node in tree.body:
    if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
        if node.name.startswith("_"):
            continue   # приватное — пропускаем
```

**Зачем брать только изменённые таргеты.** Из git мы знаем номера изменённых строк. Берём только те функции, чьи строки пересеклись с диапазоном изменений. Это даёт две выгоды: **экономия токенов** (не гоняем в LLM весь файл-портянку функций, которых правка не касалась) и **точность** (модель фокусируется на том, что реально менялось, а не размазывает внимание). Если изменённых строк нет (режим «весь файл») — берём все публичные таргеты.

### Поиск связанных тестов

Цель — найти уже существующие тесты для изменённого файла, чтобы (а) показать модели стиль и не дублировать, (б) предложить их обновление. Используются три эвристики:

1. **По именам файлов.** Для `pkg/foo.py` проверяем кандидатов: `tests/test_foo.py`, зеркальный путь `tests/pkg/test_foo.py`, альтернативный суффикс `tests/foo_test.py`.
2. **По импортам.** Сканируем тестовые файлы и ищем упоминание модуля (`pkg.foo` или `foo`) — обычно это `import`.
3. **По именам таргетов.** Ищем упоминание имён изменённых функций/классов в тексте тестов.

**Почему это эвристика (минусы).** Совпадение по тексту даёт **ложные срабатывания** (имя `save` встречается в куче тестов, не относящихся к нашему файлу) и **пропуски** (тесты названы нестандартно или вызывают функцию через другой слой). Поэтому результат — это «вероятно связанные» файлы для подсказки модели и для предложений, а не гарантия. Финальное решение — за человеком на review.

### Generation flow

```
git diff (изменённые .py, изменённые строки)
        ↓
AST-анализ: публичные функции/методы → выбор изменённых таргетов
        ↓
поиск связанных существующих тестов (эвристики)
        ↓
сборка prompt (source + targets + related tests + system rules)
        ↓
Gemini генерирует pytest-тест (first draft)
        ↓
clean (убрать markdown-фенсы) + validate (ast.parse, есть ли test_*)
        ↓
запись test_<путь>_generated.py (имя из relative-пути источника) (с шапкой "review before commit")
        ↓
запуск pytest -q
        ↓
passed? → готово (status=passed)   |   failed? → repair loop
```

### Refactoring update flow

```
изменённый production-файл + найденные существующие тесты
        ↓
для каждого существующего теста: сборка update-prompt
   (текущий source + изменённые таргеты + полный текст старого теста)
        ↓
Gemini возвращает ПОЛНЫЙ обновлённый файл теста (не diff)
        ↓
clean + validate
        ↓
запись в ОТДЕЛЬНУЮ папку suggestions (зеркальный путь) с шапкой
   "suggested update — review before replacing"
        ↓
исходный тест НЕ тронут; человек сам решает, применять ли
```

### Repair loop

Когда сгенерированный тест падает на `pytest`, мы не сдаёмся сразу, а пробуем починить. В модель подаётся три вещи:

1. **Production-код** (с пометкой DO NOT MODIFY) — чтобы модель видела реальный контракт;
2. **Текущий сгенерированный тест** (FIX THIS) — то, что чиним;
3. **Вывод pytest** (stdout + stderr) — текст ошибки/трейсбек, по которому видно причину.

**Почему чинить только тест.** Падение почти всегда означает, что черновик теста сделал неверное предположение (не тот импорт, неверное ожидаемое значение, неправильно замокал). Production-код — это «истина», его трогать нельзя: иначе ассистент начнёт «подгонять» рабочий код под кривой тест и может скрыть настоящий баг. Если же тест верный, а код реально сломан — это и есть полезный сигнал, который должен увидеть человек.

**Почему лимит попыток** (по умолчанию `repair_attempts = 2`). Без лимита возможно **зацикливание** (модель чинит одно, ломает другое по кругу), а каждая итерация — это **стоимость** (токены) и **время** (ещё один полный прогон pytest). Лимит ставит потолок: не починилось за пару попыток — отдаём человеку со статусом `failed` и сохранённым последним вариантом.

### Качество сгенерированных тестов

LLM пишет правдоподобный код, но у автогенерации есть типичные болезни. На review их надо целенаправленно искать:

- **Over-mocking.** Модель мокает всё подряд, включая чистые функции и внутреннюю логику. В итоге тест проверяет моки, а не реальное поведение. Лечение: мокать только настоящие внешние границы (сеть, БД, время, LLM), чистую логику считать по-настоящему.
- **Слабые assertions.** `assert result is not None`, `assert mock.called` без проверки самого значения. Тест зелёный, но почти ничего не гарантирует. Лечение: требовать проверки конкретных значений/эффектов.
- **Тесты «под реализацию».** Проверка приватных методов и порядка внутренних вызовов вместо наблюдаемого контракта — ломаются при безобидном рефакторинге. Лечение: проверять вход→выход и побочные эффекты, а не внутренности.

> Поэтому система спроектирована вокруг review: сгенерированное помечается шапкой, кладётся в отдельную папку и не коммитится автоматически. Тесты — это код, и к ним применяется такой же code review, как к любому коду.

## Связь с проектом AI Unit Test Assistant

Pipeline собран в `pipeline.py` (`run_pr_assistant` → `_process_file`) и раскладывается по модулям ровно по этапам разбора выше.

**Поиск изменений — `git_utils.py`.** `get_changed_python_files` делает `git diff --name-only base...HEAD`, фильтрует только production-`.py` (`is_production_python_file` отбрасывает `test_*.py`, `*_test.py`, `*_generated.py`, папку `tests/` и `exclude_paths`), а `_parse_changed_lines` через `git diff --unified=0` и regex по hunk-заголовкам `@@ ... +N,M @@` собирает множество изменённых строк.

**AST-анализ — `source_analyzer.py`.** `analyze_source_file` парсит файл (`ast.parse`), обходит `tree.body`, берёт `FunctionDef`/`AsyncFunctionDef`/`ClassDef`, пропуская имена с `_` (приватное). `select_test_targets` оставляет только таргеты, чьи строки пересеклись с изменёнными (`_intersects`); если изменённых строк нет — берёт все публичные.

**Поиск связанных тестов — `test_finder.py`.** `_candidate_paths` строит кандидатов по именам (`test_<stem>.py`, зеркальный путь, `<stem>_test.py`), `_scan_for_references` сканирует тестовые папки и ищет упоминания модуля и имён таргетов. Это и есть три эвристики из разбора.

**Сборка prompt — `prompts.py`.** Три пары (system, user): `build_generate_tests_prompt`, `build_repair_tests_prompt`, `build_update_tests_prompt`. System-инструкции прямо кодируют принципы: «use pytest», «do not over-mock pure functions», «do not test private implementation details», «do not modify production code».

**LLM — `llm_client.py` + `test_generator.py`.** `LlmClient.generate` зовёт Gemini через `google-genai` с Vertex AI (`temperature=0.0` для детерминизма); при `dry_run=True` сети нет — возвращается фиксированный stub. `test_generator.py` чистит ответ (`clean_llm_python_response` срезает markdown-фенсы) и валидирует (`validate_python_test_code`: `ast.parse` + проверка, что есть `test_*`/`Test*`), иначе `ValidationError`.

**Прогон и repair — `pytest_runner.py` + `_generate_and_repair`.** `run_pytest` запускает `python -m pytest -q` в subprocess с таймаутом, падения не кидают исключение, а возвращают `PytestResult`. В `_generate_and_repair` цикл `while not passed and attempts < config.repair_attempts` (по умолчанию 2) шлёт в `repair_tests` production-код + тест + объединённый stdout/stderr.

**Suggestions без перезаписи — `_process_file` + `report.py`.** При `update_existing_tests=True` для каждого найденного теста зовётся `update_existing_tests`, результат пишется через `_suggested_path_for` в отдельную `suggestions_dir` (`reports/suggested-tests`) с шапкой `_SUGGESTED_HEADER`. Сгенерированные с нуля тесты идут в `output_dir` (`tests/generated`) с шапкой `_GENERATED_HEADER`. `report.py` пишет md и json отчёт. Отдельная команда `apply-suggested-updates` (`apply_suggested_updates`) — это явный, осознанный шаг человека, чтобы применить предложения; автоматически это не происходит.

> Все принципы — no auto-commit, no overwrite, human review — не на словах, а прошиты в коде: отдельные папки, шапки-предупреждения, отсутствие любого вызова `git commit`.

## ❓ Вопросы и ответы

**Q: Как убедиться, что сгенерированный тест действительно хороший, а не просто «зелёный»?**
**A:** «Зелёный» — необходимое, но не достаточное условие. На review смотрю: (1) проверяет ли `assert` конкретное значение/эффект, а не `is not None`; (2) есть ли граничные и error-кейсы, а не только happy path; (3) не over-mock ли — мокаются ли только внешние границы; (4) тестируется ли поведение, а не приватные детали. Полезный приём — **mutation testing мысленно**: «если я внесу баг в функцию, упадёт ли этот тест?». Если нет — тест бесполезен.

**Q: Coverage 90% — это хорошо? Coverage vs quality.**
**A:** Coverage говорит только, что строки **исполнялись**, а не что результат **проверялся**. Можно иметь 90% покрытия с пустыми по сути проверками. Я использую coverage как карту слепых зон (что вообще ни разу не вызвали — точно дыра), но не как оценку качества. Качество смотрится глазами на содержание assertions. Поэтому в проекте coverage — это вспомогательный сигнал, а не критерий приёмки.

**Q: Что делать с flaky-тестами?**
**A:** Flaky — тест, который то проходит, то падает без изменений кода. Это яд: ему перестают верить и начинают игнорировать красное. Причины — недетерминизм: реальное время, `random` без seed, порядок коллекций, сеть, гонки. Лечение — устранить источник: заморозить время (`monkeypatch`/`freezegun`), задать seed, замокать сеть, изолировать состояние. Прятать ретраями (`pytest-rerunfailures`) — крайняя мера, она маскирует проблему. Генератор по дизайну просят писать deterministic-тесты и ставят `temperature=0.0`.

**Q: Как мокать Vertex AI / Gemini в тестах самого ассистента?**
**A:** Два уровня. Первый — встроенный `dry_run`: при `config.dry_run=True` `LlmClient.generate` вообще не ходит в сеть и возвращает фиксированный stub-тест, так весь pipeline тестируется офлайн и бесплатно. Второй — для unit-тестов конкретной логики патчим саму границу: `mocker.patch.object(LlmClient, "generate", return_value=...)` или мокаем `google.genai` клиент. Реальные сетевые вызовы в unit-тестах недопустимы — это недетерминизм и деньги. Тестируем нашу логику (сборка prompt, парсинг ответа, repair-цикл), а не сам Gemini.

**Q: Как именно работает repair loop и почему есть лимит попыток?**
**A:** Если `pytest` упал, в модель шлём три вещи — production-код (DO NOT MODIFY), текущий тест (FIX THIS) и вывод pytest (stdout+stderr) — и просим вернуть исправленный тест. Цикл повторяется, пока тест не зелёный или пока не исчерпан `repair_attempts` (по умолчанию 2). Лимит нужен против трёх рисков: зацикливание (чиним одно — ломаем другое по кругу), стоимость (токены на каждой итерации) и время (полный прогон pytest каждый раз). Не починилось — отдаём человеку со статусом `failed`.

**Q: Почему в repair loop чините только тест, а не код?**
**A:** Production-код — источник истины; тест — гипотеза о его поведении. Падение чаще всего значит, что черновик теста ошибся (импорт, ожидаемое значение, мок). Если разрешить править код, ассистент начнёт «подгонять» рабочий код под кривой тест и может **замаскировать настоящий баг**. А если код реально сломан — пусть тест останется красным, это ценный сигнал для человека.

**Q: Почему вы не перезаписываете существующие тесты при рефакторинге?**
**A:** Существующие тесты часто содержат ручные, продуманные кейсы и знание контекста, которого у модели нет. Слепая перезапись могла бы их потерять или ослабить. Поэтому обновление сохраняется **отдельным файлом** в `suggestions_dir` с шапкой-предупреждением, а оригинал не трогается. Человек делает diff и решает. Применение — отдельная явная команда `apply-suggested-updates`, а не побочный эффект прогона.

**Q: Что если тест проходит, но логика на самом деле неверна?**
**A:** Это реальный риск: модель могла «зафиксировать» ошибочное поведение как ожидаемое (тест отражает то, что код делает, а не то, что должен). Зелёный тест такое не поймает. Защита — человек на review сверяет ожидаемые значения со спецификацией/требованиями, а не с поведением кода. Именно поэтому система — это ассистент с обязательным review, а не автопилот: подтвердить корректность контракта может только человек.

**Q: В чём разница между fixtures и mocks — когда что?**
**A:** Это про разное. **Fixture** — механизм pytest для подготовки и уборки тестовых данных/ресурсов (создать объект, временную папку, соединение). **Mock** — поддельный объект, который подменяет реальную зависимость и фиксирует вызовы. Часто они вместе: фикстура создаёт замоканный клиент. Правило: реальные данные и дешёвые объекты — через фикстуры; дорогие/внешние/недетерминированные границы (сеть, БД, время, LLM) — через mock. Over-mocking — антипаттерн: чистую логику не мокают.

**Q: Почему анализ через `ast`, а не regex по тексту?**
**A:** Regex не понимает структуру языка: спотыкается на многострочных сигнатурах, декораторах, вложенности, строках с `def` внутри. `ast.parse` даёт настоящее дерево, где `FunctionDef`/`AsyncFunctionDef`/`ClassDef` — это узлы с точными границами строк, аргументами и телом. Это надёжно для определения публичности (имя с `_`) и для сопоставления с изменёнными строками.

**Q: Почему тестируете только публичные функции и пропускаете приватные (`_name`)?**
**A:** Публичный API — это контракт, который не должен ломаться, его и проверяем. Приватные функции — деталь реализации: их можно переименовать/переписать без изменения поведения, и тесты на них ломались бы зря (тесты «под реализацию»). Приватная логика всё равно покрывается косвенно — через тесты вызывающих её публичных функций. Плюс это экономит токены и фокусирует модель.

**Q: Зачем брать только изменённые таргеты, а не весь файл?**
**A:** Из git известны изменённые строки; берём функции, пересекающиеся с ними. Выгод две: экономия токенов (не шлём в LLM весь файл) и точность (модель не размазывает внимание на нетронутый код). В режиме генерации для одного файла целиком (команда `generate-tests`) изменённых строк нет — тогда берём все публичные таргеты.

## 🎤 Что сказать вслух

> Ассистент автоматизирует не только запуск тестов — он пишет first draft и предлагает обновления после рефакторинга. Самую дорогую человеческую работу — написание и поддержку — он берёт на себя как черновик.

> Главный принцип: no auto-commit, no overwrite, human review обязателен. Это не лозунг, а решения в коде — отдельные папки, шапки-предупреждения и полное отсутствие вызова git commit.

> Coverage — это метрика количества, а не качества. 100% покрытия можно получить тестом, который ничего по сути не проверяет. Качество тестов решается глазами на review.

> В repair loop мы чиним только тест и никогда production-код — иначе можно подогнать рабочий код под кривой тест и спрятать настоящий баг. И ставим лимит попыток против зацикливания, стоимости и времени.

> Тестируем поведение, а не реализацию. Поэтому берём только публичные функции через `ast` и пропускаем приватные — тесты не должны ломаться от безобидного рефакторинга.

> Самый коварный риск автогенерации — зелёный тест с неверной логикой: модель фиксирует то, что код делает, а не то, что должен. Подтвердить контракт может только человек — поэтому это ассистент, а не автопилот.

> В тестах самого ассистента Vertex AI не вызывается по-настоящему: есть dry-run со stub и мок границы LLM. Реальная сеть в unit-тестах — это недетерминизм и деньги.
