Part 1 · Distributed Systems & Cloud Architecture

What changes when a program becomes several programs on several machines, and the four ideas that make that manageable: microservices, events, serverless, and the patterns for scaling.

1.1 What "distributed" really means

On one machine, a function call either returns or crashes, and both are immediate. Across a network, there is a third outcome: you do not know. The request may have been lost, the answer may have been lost, or the other side may still be working. Everything in distributed systems follows from living with that third outcome.

Three facts you cannot engineer away:

  • Partial failure. One machine restarts while the others keep going. The system has to make sense in the middle of that.
  • No shared clock, no shared memory. Two services cannot look at the same variable; they can only send each other messages, and messages take time and can arrive twice or out of order.
  • Latency is a cost. A function call takes nanoseconds, a network call takes milliseconds, and a cold container takes seconds. Design around the slow parts.

The one-line rule: assume every message can be lost, delayed or duplicated, and design so that the system still ends in the right state.

1.2 Microservices: split where requirements conflict

A microservice is a separately deployed program with one job that talks to others over the network. Splitting has a real price: every boundary adds a network hop, a message format to keep stable, and one more thing to deploy and monitor. So the question is never "how small can a service be?" but "where do requirements conflict so much that one program cannot satisfy both?"

This project has exactly one such conflict, and so it has exactly two services:

GitHub gives a webhook ten seconds to answer and then marks it failed, so the receiver must be tiny and fast and reachable from the internet. The analysis takes minutes and should be reachable by nobody. One program could not be both. Two programs with a queue between them can.

What the split costs here: a message contract (five JSON fields) that both sides must agree on, and two Docker images instead of one. What it buys: each side can fail, scale and be deployed on its own.

Rule of thumb: split along conflicting requirements (latency, exposure, resource needs, release cadence), never along nouns like "user service" and "order service" just because they are different words.

1.3 Event-driven systems: talk through messages, not calls

In a call, the caller waits for the answer and fails if the callee is down. In an event, the producer writes a message to a topic and moves on; whoever is subscribed receives it when they are ready. The producer does not know who listens, and a consumer that is down simply gets the message later. That decoupling is the whole point.

Idempotency: why "at least once" is enough

Exactly-once delivery across a network is impossible in general: the broker cannot tell whether a consumer that stopped answering had finished the work or not. So brokers promise at-least-once and push the problem to the consumer: processing the same message twice must have the same effect as processing it once. That property is called idempotency, and it is usually implemented with a key that identifies the work and a marker that says it was done.

The receiver publishes; the worker checks for the marker before doing anything, writes it only on success, and answers 500 on any failure so the broker retries. A malformed message is acknowledged immediately: retrying it could never help, and it would otherwise occupy the queue for five attempts.

1.4 Serverless: containers that exist only while there is work

"Serverless" does not mean no servers; it means you do not manage them. You give the platform a container image and it starts instances when requests arrive, adds more when traffic grows, and stops them all when it goes quiet. You pay for the time instances run.

Two consequences shape the code:

  • Stateless by construction. An instance can disappear at any time, so nothing that matters may live only in its memory. State belongs in the queue (what is still to do) and in storage (what was done). The worker's LLM response cache lives in memory on purpose: losing it costs a few repeated calls, never correctness.
  • Cold starts are real. The first request after idle waits for a container to boot (hundreds of milliseconds to seconds). Fine for a background worker, something to measure for a user-facing API; the usual fix is a minimum number of warm instances, which costs money.

In this project

Both services run on Cloud Run with scale-to-zero. The worker is deployed with concurrency = 1: one request per instance at a time, because the job shells out to git and pytest and would not share a CPU well. More load means more instances, not more threads. The code mirrors that with a lock around each job.

1.5 Scalability patterns

Queue-based load levelling

Traffic arrives in bursts; work takes a fixed time. Without a queue, a burst either overloads the workers or is rejected. With a queue, the burst waits and is drained at the workers' pace. Try it: raise the burst, then add workers.

Horizontal scaling

Scaling up means a bigger machine; scaling out means more machines. Out is the cloud's natural direction and it needs one thing from you: units of work that do not share state. A job here is one PR at one commit, writing to its own folder, so any number of workers can run side by side.

Retries, backoff and the dead-letter queue

A retry fixes transient failures (a network blip, a model outage of a minute) and makes permanent failures worse (a job that always crashes would loop forever). So retries are bounded, spaced out with growing delays (backoff), and the message is finally parked where a person can look at it. Five attempts and a dead-letter topic are a typical setting.

Idempotent consumers

The pattern from 1.3: retries are only safe because doing the work twice is harmless. The marker-before-ack ordering is what makes that true.

How the four fit together: the queue absorbs bursts, horizontal scaling drains them, bounded retries handle transient failures, and idempotency makes those retries safe. Remove any one and the others stop being safe.

1.7 The whole picture in this project

Read it as a story: GitHub signs a webhook; the receiver verifies the signature, filters to the three PR actions that matter, publishes a five-field job and answers in milliseconds. Pub/Sub pushes the job to the worker and keeps it until the worker says 200. The worker clones, runs the eight steps, uploads artifacts to repo/pr/sha/, posts a commit status, and acknowledges. A job that fails five times lands in the dead-letter topic with its own subscription for inspection.

Verified locally with the Pub/Sub emulator: a signed webhook was queued and processed end to end, and a job with a non-existent base branch was delivered five times and then dead-lettered.

1.8 Check yourself

Why is exactly-once delivery impossible, and what do we do instead?

After sending a message, the broker cannot distinguish "consumer finished and the ack was lost" from "consumer crashed before finishing". Either way it must redeliver, so delivery is at least once. The consumer makes the duplicate harmless with an idempotency key and a marker written only on success.

What would break if the worker wrote the marker before uploading the artifacts?

A crash between the marker and the upload would leave a job marked done with no artifacts, and every retry would skip it. The marker must be the last durable effect, or the retry cannot repair a half-done job.

Why push delivery rather than a worker that pulls?

With push the worker is an ordinary HTTP service, scaled by the platform, with no subscriber loop to keep alive. Pull is better when jobs are very long or when the consumer must control its own rate.

Why not make the receiver do the analysis in a background thread?

Because a Cloud Run instance may be stopped as soon as it has answered the request; background work in it is not guaranteed to finish. Work that must complete goes through the queue.

Where would you add a metric for queue length?

Nowhere in the code: the broker already knows it (num_undelivered_messages in Cloud Monitoring). A metric measured by the worker would be a worse copy of a number the platform already exports.
