Part 1 · Distributed Systems & Cloud Architecture

What changes when a program becomes several programs on several machines, and the four ideas that make that manageable: microservices, events, serverless, and the patterns for scaling.

1.1 What "distributed" really means

On one machine, a function call either returns or crashes, and both are immediate. Across a network, there is a third outcome: you do not know. The request may have been lost, the answer may have been lost, or the other side may still be working. Everything in distributed systems follows from living with that third outcome.

Three facts you cannot engineer away:

  • Partial failure. One machine restarts while the others keep going. The system has to make sense in the middle of that.
  • No shared clock, no shared memory. Two services cannot look at the same variable; they can only send each other messages, and messages take time and can arrive twice or out of order.
  • Latency is a cost. A function call takes nanoseconds, a network call takes milliseconds, and a cold container takes seconds. Design around the slow parts.

The one-line rule: assume every message can be lost, delayed or duplicated, and design so that the system still ends in the right state.

1.2 Microservices: split where requirements conflict

A microservice is a separately deployed program with one job that talks to others over the network. Splitting has a real price: every boundary adds a network hop, a message format to keep stable, and one more thing to deploy and monitor. So the question is never "how small can a service be?" but "where do requirements conflict so much that one program cannot satisfy both?"

This project has exactly one such conflict, and so it has exactly two services:

GitHub gives a webhook ten seconds to answer and then marks it failed, so the receiver must be tiny and fast and reachable from the internet. The analysis takes minutes and should be reachable by nobody. One program could not be both. Two programs with a queue between them can.

What the split costs here: a message contract (five JSON fields) that both sides must agree on, and two Docker images instead of one. What it buys: each side can fail, scale and be deployed on its own.

Rule of thumb: split along conflicting requirements (latency, exposure, resource needs, release cadence), never along nouns like "user service" and "order service" just because they are different words.

1.3 Event-driven systems: talk through messages, not calls

In a call, the caller waits for the answer and fails if the callee is down. In an event, the producer writes a message to a topic and moves on; whoever is subscribed receives it when they are ready. The producer does not know who listens, and a consumer that is down simply gets the message later. That decoupling is the whole point.

Idempotency: why "at least once" is enough

Exactly-once delivery across a network is impossible in general: the broker cannot tell whether a consumer that stopped answering had finished the work or not. So brokers promise at-least-once and push the problem to the consumer: processing the same message twice must have the same effect as processing it once. That property is called idempotency, and it is usually implemented with a key that identifies the work and a marker that says it was done.

In this project the key is repo/pr/sha and the marker is the JSON report in Cloud Storage at that path. Pick where the worker crashes and watch what the second delivery does:

The receiver publishes; the worker checks for the marker before doing anything, writes it only on success, and answers 500 on any failure so the broker retries. A malformed message is acknowledged immediately: retrying it could never help, and it would otherwise occupy the queue for five attempts.

1.4 Serverless: containers that exist only while there is work

"Serverless" does not mean no servers; it means you do not manage them. You give the platform a container image and it starts instances when requests arrive, adds more when traffic grows, and stops them all when it goes quiet. You pay for the time instances run.

Two consequences shape the code:

  • Stateless by construction. An instance can disappear at any time, so nothing that matters may live only in its memory. State belongs in the queue (what is still to do) and in storage (what was done). The worker's LLM response cache lives in memory on purpose: losing it costs a few repeated calls, never correctness.
  • Cold starts are real. The first request after idle waits for a container to boot (hundreds of milliseconds to seconds). Fine for a background worker, something to measure for a user-facing API; the usual fix is a minimum number of warm instances, which costs money.

In this project

Both services run on Cloud Run with scale-to-zero. The worker is deployed with concurrency = 1: one request per instance at a time, because the job shells out to git and pytest and would not share a CPU well. More load means more instances, not more threads. The code mirrors that with a lock around each job.

1.5 Scalability patterns

Queue-based load levelling

Traffic arrives in bursts; work takes a fixed time. Without a queue, a burst either overloads the workers or is rejected. With a queue, the burst waits and is drained at the workers' pace. Try it: raise the burst, then add workers.

Horizontal scaling

Scaling up means a bigger machine; scaling out means more machines. Out is the cloud's natural direction and it needs one thing from you: units of work that do not share state. A job here is one PR at one commit, writing to its own folder, so any number of workers can run side by side.

Retries, backoff and the dead-letter queue

A retry fixes transient failures (a network blip, a model outage of a minute) and makes permanent failures worse (a job that always crashes would loop forever). So retries are bounded, spaced out with growing delays (backoff), and the message is finally parked where a person can look at it. Five attempts and a dead-letter topic are a typical setting.

Idempotent consumers

The pattern from 1.3: retries are only safe because doing the work twice is harmless. The marker-before-ack ordering is what makes that true.

How the four fit together: the queue absorbs bursts, horizontal scaling drains them, bounded retries handle transient failures, and idempotency makes those retries safe. Remove any one and the others stop being safe.

1.7 The whole picture in this project

Read it as a story: GitHub signs a webhook; the receiver verifies the signature, filters to the three PR actions that matter, publishes a five-field job and answers in milliseconds. Pub/Sub pushes the job to the worker and keeps it until the worker says 200. The worker clones, runs the eight steps, uploads artifacts to repo/pr/sha/, posts a commit status, and acknowledges. A job that fails five times lands in the dead-letter topic with its own subscription for inspection.

Verified locally with the Pub/Sub emulator: a signed webhook was queued and processed end to end, and a job with a non-existent base branch was delivered five times and then dead-lettered.

1.8 Check yourself

Why is exactly-once delivery impossible, and what do we do instead?

After sending a message, the broker cannot distinguish "consumer finished and the ack was lost" from "consumer crashed before finishing". Either way it must redeliver, so delivery is at least once. The consumer makes the duplicate harmless with an idempotency key and a marker written only on success.

What would break if the worker wrote the marker before uploading the artifacts?

A crash between the marker and the upload would leave a job marked done with no artifacts, and every retry would skip it. The marker must be the last durable effect, or the retry cannot repair a half-done job.

Why push delivery rather than a worker that pulls?

With push the worker is an ordinary HTTP service, scaled by the platform, with no subscriber loop to keep alive. Pull is better when jobs are very long or when the consumer must control its own rate.

Why not make the receiver do the analysis in a background thread?

Because a Cloud Run instance may be stopped as soon as it has answered the request; background work in it is not guaranteed to finish. Work that must complete goes through the queue.

Where would you add a metric for queue length?

Nowhere in the code: the broker already knows it (num_undelivered_messages in Cloud Monitoring). A metric measured by the worker would be a worse copy of a number the platform already exports.

Part 2 · Monitoring with Prometheus and Grafana

How a running service is turned into numbers, how those numbers are stored and queried, and how a dashboard and an alert are built from them.

2.1 Metrics, logs, traces: three different questions

Observability is the ability to answer questions about a running system from the outside. The three kinds of data answer three kinds of question, and metrics are the cheapest of the three.

A metric is a number with a name and a time: at 14:03:05, jobs processed = 8. Thousands of such numbers per second cost almost nothing to store, so metrics are always on, and questions like "how many per minute?" or "what is the slowest 5 %?" are answered in milliseconds. What a metric cannot tell you is which job failed or why; for that you read the log line the worker printed.

2.2 The pull model

Prometheus does not wait for services to send data. It keeps a list of targets and asks each one for its current values on a schedule: an HTTP GET to /metrics, which returns a plain text page. The service needs no library beyond a tiny one that formats the page, and it does not need to know that Prometheus exists.

Why pull and not push: Prometheus controls the rate and knows immediately when a target stops answering (the up metric drops to 0), the service cannot flood the monitoring system, and a developer can open /metrics in a browser to see exactly what is being reported. The cost is that Prometheus must be able to reach the service; for short-lived batch jobs there is a push gateway, and in the cloud a managed collector scrapes on Prometheus's behalf.

Each scrape produces one sample per series: (timestamp, value). A series is a metric name plus a set of labels. Prometheus stores samples compressed (about 1–2 bytes each), which is why keeping every 5-second sample for weeks is affordable.

2.3 The metric types

  • Counter. A number that only increases: requests served, jobs failed, tokens sent. Its raw value is rarely interesting (it depends on when the process started); its rate of change is. Everything in this project is a counter except the duration.
  • Gauge. A number that goes up and down: queue length, memory in use, temperature. You read it directly.
  • Histogram. Counts observations into cumulative buckets: how many jobs took ≤ 5 s, ≤ 15 s, ≤ 30 s… plus a sum and a count. It is the only type from which you can compute percentiles later, across many instances.
  • Summary. Percentiles computed inside the service. Precise but not aggregatable across instances; histograms are preferred.

Why a counter and not a gauge for "jobs"

If the worker reported "jobs in the last minute" as a gauge, a restart would lose the window and two instances could not be added together. A counter is restart-safe (Prometheus detects the reset) and additive (sum the rates of all instances). The rule: if it only ever goes up, make it a counter and let the query do the arithmetic.

A longer window gives a smoother, laggier line; a shorter one reacts faster but is noisy. Alert rules use long windows (15 minutes here) so that one odd scrape cannot fire them; dashboards use shorter ones. The window must contain at least two samples, so with a 5-second scrape interval the minimum useful window is about 15 seconds.

2.4 Labels and the cardinality trap

A label splits one metric into several series: jobs_processed_total{status="processed"}, {status="failed"}, and so on. That is how one metric answers "how many failed?" without a second metric. Every distinct combination of label values is a separate series that Prometheus stores and scans, so labels must have few, bounded values: a status (4 values), a cache policy (2 values), an HTTP method. A label whose values are unbounded — a user id, a PR number, a commit SHA — creates a new series per value and will eventually exhaust memory. That mistake is called a cardinality explosion, and it is the most common way to break a Prometheus server.

In this project

Labels: status on jobs (processed, failed, skipped, ignored), result on generated test files (passed, failed), policy on cache counters (lru, lfu). The repository name and PR number are deliberately not labels; they live in the log line and in the Cloud Storage path.

A histogram never stores the individual durations, only how many fell below each boundary. The project's alert for "more than 20 % of jobs failing" had exactly this bug: it divided the failed series by every status series and matched only with itself, so the ratio was 1.0 after any single failure. It was found by writing a unit test for the rule, and the fix is sum() on both sides.

2.6 Alert rules: conditions with patience

An alert rule is a PromQL expression evaluated on a schedule plus a for: duration. When the expression returns something, the alert becomes pending; only when it has stayed true for the whole for period does it become firing. That one knob removes most false alarms: a short spike never fires.

Prometheus decides that an alert fires. A second program, Alertmanager, decides who hears about it: it groups related alerts, silences known ones, and routes to Slack, email or a pager. The project runs Prometheus with two rules and leaves Alertmanager out, because the rules can be inspected and tested without it.

Testing a rule

Rules are code and can be unit-tested with promtool test rules: you declare synthetic series (0+9x40 means "start at 0, add 9 every step, 40 steps"), an evaluation time, and the alerts you expect. The project's test feeds a 10 % failure rate and expects nothing, then a 50 % rate and expects the alert; the old expression failed the first case.

In this project

HighJobFailureRate: more than 20 % failing over 15 minutes, for: 15m. SlowAnalysisJobs: p95 above 300 s for 10 minutes, because at 600 s the ack deadline causes redelivery and duplicate work. Both are in monitoring/alerts.yml with tests in alerts_test.yml.

2.7 Grafana: dashboards as code

Grafana does not store metrics; it asks Prometheus and draws the answer. A dashboard is a grid of panels, each panel one query plus how to show it (a time series, a single number, a gauge) and a unit. Grafana can load dashboards and data sources from files at start-up, which means the dashboard lives in git next to the code and is identical on every machine.

What makes a dashboard useful rather than decorative: the first row answers "is it healthy?" (throughput, errors, latency), the second "what does it cost or produce?" (tokens, pass ratio), and every panel has a unit. Six panels that each answer one question beat thirty that answer none.

In this project

monitoring/docker-compose.yml starts the worker in dry-run mode, Prometheus with the scrape config and rules, and Grafana with the data source and dashboard provisioned from monitoring/grafana/. python send_test_job.py --repeat 5 creates traffic. The same /metrics endpoint works unchanged with Google's managed Prometheus on Cloud Run.

2.8 Check yourself

Why does a counter restart not corrupt rate()?

Prometheus treats any decrease in a counter as a reset and adds the increase before the reset to the increase after it. The only thing lost is whatever happened between the last scrape and the restart.

When is a gauge the right type?

When the value itself is the answer and it can go down: queue length, memory, number of busy workers. If you find yourself wanting the rate of a gauge, it probably should have been a counter.

What is wrong with a label for the PR number?

Unbounded values: every PR creates a new series forever. Put the PR number in the log line and in the artifact path instead.

Why sum by (le) before histogram_quantile?

Each instance exports its own bucket series. Adding them per bucket boundary gives one histogram for the whole service; then the quantile is computed once, correctly, across instances.

What does for: 15m protect against, and what does it cost?

It stops a brief spike from paging anyone. The cost is that a real outage is reported 15 minutes late; choose the duration by how fast a human could act anyway.

Part 3 · Topological Sort and the LRU / LFU Caches

Two classic algorithms you can run by hand below: one orders work that depends on other work, the other decides what to forget when memory is full.

3.1 Dependencies are a graph

Whenever "A must happen before B", you have a directed edge A → B. Files that import each other, build steps, database migrations, courses with prerequisites, tasks in a schedule: all are directed graphs. A valid order of doing things is one where every edge points forward. Such an order exists only if the graph has no cycle, and a graph without cycles is called a DAG (directed acyclic graph).

Two ideas carry the whole topic: the in-degree of a node is how many edges point into it, which is to say how many things it still waits for; a node with in-degree 0 can go right now.

3.2 Kahn's algorithm, step by step

  1. Count the in-degree of every node.
  2. Put every node with in-degree 0 into a ready queue.
  3. Take a node from the queue, emit it, and for each edge out of it lower the target's in-degree by one; a target that reaches 0 joins the queue.
  4. Repeat until the queue is empty.

Press Step and watch the in-degrees fall. Then switch to the example with a cycle and see what happens when the queue runs dry early:

Two properties fall out of the procedure for free:

  • Cycle detection. If nodes remain when the queue is empty, each of them still waits for something, and that something waits for them: they are in a cycle or downstream of one. No extra bookkeeping needed.
  • Deterministic ties. When several nodes are ready at once, any of them is a valid next choice. Taking them from a plain queue gives one valid order; taking the one with the smallest original position (a min-heap keyed by position) gives the same order on every run, which matters for reproducible output.

Cost

Every node enters and leaves the queue once, and every edge is looked at once when its source is emitted: O(V + E) with a plain queue. The heap adds a logarithm, O((V + E) log V), to buy the stable tie-break. For a pull request with a handful of files this is microseconds either way; the point of knowing the cost is knowing what you traded for the determinism.

The other way: depth-first search

You can also topologically sort by running a depth-first search and listing nodes in the reverse of the order in which they are finished. It needs the same O(V + E) and detects cycles by meeting a node that is still "in progress". Kahn's version is preferred when you want the ready set explicitly, for example to run independent nodes in parallel: everything in the queue at the same moment can go at once.

In this project

import_graph.py builds the graph over the changed files only (imports read with ast, including relative imports), runs Kahn with a min-heap keyed by the file's original position, keeps cycle files in their original order and lists them in the report. The order decides what the report shows first and makes sure a module is processed before any tests exist for its importers.

3.3 Caches: remembering what is expensive to recompute

A cache is a small, fast store in front of a slow operation. Ask the cache first; on a hit return the stored answer, on a miss do the slow work and store the result. The only interesting decision a cache makes is what to throw away when it is full. That decision is the eviction policy, and the quality of a cache is its hit ratio: hits divided by all lookups.

Two conditions make caching correct: the same input must always produce the same answer (otherwise a hit returns a stale value), and the key must contain everything that could change the answer. In this project the slow operation is a Gemini call, the key is a hash of model, temperature, system instruction and prompt, and temperature 0 is what makes the first condition true.

3.4 LRU: forget the least recently used

LRU bets on temporal locality: what was used a moment ago will probably be used again soon. The classic O(1) design keeps two structures that point at the same nodes: a hash map from key to node, for lookup, and a doubly linked list in order of use, for eviction. A lookup moves its node to the front with two pointer swaps; eviction removes whatever is at the back.

The two sentinels, HEAD and TAIL, are a trick that removes every special case: the list is never empty, so inserting at the front and removing at the back never check for null pointers. Python's OrderedDict implements the same structure; the project writes it out to show the mechanism.

3.5 LFU: forget the least frequently used

LFU bets on popularity: what has been used many times will be used again, even if not recently. The O(1) design keeps three maps: key → value, key → use count, and use count → the keys at that count in insertion order, plus a pointer to the smallest count. A hit moves the key one bucket up; eviction takes the oldest key from the lowest bucket (so LRU breaks ties within a bucket).

LFU's weakness is the mirror of its strength: a key that was hot an hour ago keeps its high count and refuses to leave, while new keys fight over the lowest bucket. Production LFU implementations decay counts over time for that reason.

3.6 Which one wins depends on the workload

Run both policies on two access patterns. The first is "a developer re-pushes a branch": the same few prompts come back in bursts. The second is "a shared module appears in most PRs": one hot key among many one-off keys.

There is no best policy, only a best policy for a workload. That is why the project makes the policy a one-line setting and exports the hit ratio per policy: the question can be answered on the dashboard with real jobs instead of being argued about.

In this project

cache.py holds both classes with hit and miss counters. llm_client.py looks the prompt up before calling Gemini. The worker owns one 256-entry cache for the whole process and chooses the class from LLM_CACHE_POLICY (lru by default). Measured on two identical jobs: 3 misses, then 3 hits and 0 LLM calls, under both policies.

3.7 Check yourself

Why does Kahn's algorithm detect cycles without extra code?

A node in a cycle always has at least one incoming edge from another cycle member that is never emitted, so its in-degree never reaches 0 and it never enters the queue. The leftovers when the queue is empty are exactly those nodes and anything behind them.

Why is the doubly linked list needed? Would a singly linked one do?

To move a node to the front you must unlink it, which requires updating its predecessor's pointer. With a singly linked list you would have to walk from the head to find the predecessor: O(n). The back pointer makes it O(1).

What must be in the cache key, and what must not?

Everything that changes the answer: model, temperature, instruction, prompt. Nothing that does not: the project once included the clone directory path, so every job had unique keys and the cache never hit. Normalise the input before hashing.

When would LFU clearly beat LRU here?

One worker serving many repositories where a few shared modules (say models.py) appear in most PRs: their prompts are hot all day, while each PR's other files are seen once. LRU would flush the hot entries on every burst; LFU keeps them.

Is the hand-written cache thread-safe, and does it matter?

No, and not here: the worker handles one job at a time (Cloud Run concurrency 1 plus a lock). A shared cache under real concurrency would need a mutex or lock striping; the limitation is documented rather than solved with a lock nobody needs.
