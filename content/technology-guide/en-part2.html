Part 2 · Monitoring with Prometheus and Grafana

How a running service is turned into numbers, how those numbers are stored and queried, and how a dashboard and an alert are built from them.

2.1 Metrics, logs, traces: three different questions

Observability is the ability to answer questions about a running system from the outside. The three kinds of data answer three kinds of question, and metrics are the cheapest of the three.

A metric is a number with a name and a time: at 14:03:05, jobs processed = 8. Thousands of such numbers per second cost almost nothing to store, so metrics are always on, and questions like "how many per minute?" or "what is the slowest 5 %?" are answered in milliseconds. What a metric cannot tell you is which job failed or why; for that you read the log line the worker printed.

2.2 The pull model

Prometheus does not wait for services to send data. It keeps a list of targets and asks each one for its current values on a schedule: an HTTP GET to /metrics, which returns a plain text page. The service needs no library beyond a tiny one that formats the page, and it does not need to know that Prometheus exists.

Why pull and not push: Prometheus controls the rate and knows immediately when a target stops answering (the up metric drops to 0), the service cannot flood the monitoring system, and a developer can open /metrics in a browser to see exactly what is being reported. The cost is that Prometheus must be able to reach the service; for short-lived batch jobs there is a push gateway, and in the cloud a managed collector scrapes on Prometheus's behalf.

Each scrape produces one sample per series: (timestamp, value). A series is a metric name plus a set of labels. Prometheus stores samples compressed (about 1–2 bytes each), which is why keeping every 5-second sample for weeks is affordable.

2.3 The metric types

  • Counter. A number that only increases: requests served, jobs failed, tokens sent. Its raw value is rarely interesting (it depends on when the process started); its rate of change is. Everything in this project is a counter except the duration.
  • Gauge. A number that goes up and down: queue length, memory in use, temperature. You read it directly.
  • Histogram. Counts observations into cumulative buckets: how many jobs took ≤ 5 s, ≤ 15 s, ≤ 30 s… plus a sum and a count. It is the only type from which you can compute percentiles later, across many instances.
  • Summary. Percentiles computed inside the service. Precise but not aggregatable across instances; histograms are preferred.

Why a counter and not a gauge for "jobs"

If the worker reported "jobs in the last minute" as a gauge, a restart would lose the window and two instances could not be added together. A counter is restart-safe (Prometheus detects the reset) and additive (sum the rates of all instances). The rule: if it only ever goes up, make it a counter and let the query do the arithmetic.

A longer window gives a smoother, laggier line; a shorter one reacts faster but is noisy. Alert rules use long windows (15 minutes here) so that one odd scrape cannot fire them; dashboards use shorter ones. The window must contain at least two samples, so with a 5-second scrape interval the minimum useful window is about 15 seconds.

2.4 Labels and the cardinality trap

A label splits one metric into several series: jobs_processed_total{status="processed"}, {status="failed"}, and so on. That is how one metric answers "how many failed?" without a second metric. Every distinct combination of label values is a separate series that Prometheus stores and scans, so labels must have few, bounded values: a status (4 values), a cache policy (2 values), an HTTP method. A label whose values are unbounded — a user id, a PR number, a commit SHA — creates a new series per value and will eventually exhaust memory. That mistake is called a cardinality explosion, and it is the most common way to break a Prometheus server.

In this project

Labels: status on jobs (processed, failed, skipped, ignored), result on generated test files (passed, failed), policy on cache counters (lru, lfu). The repository name and PR number are deliberately not labels; they live in the log line and in the Cloud Storage path.

2.5 PromQL in five expressions

ExpressionWhat it returns
jobs_processed_totalan instant vector: the latest value of every series with that name
jobs_processed_total[5m]a range vector: all samples of the last five minutes, per series; only functions consume it
rate(jobs_processed_total[5m]) * 60jobs per minute, per status
sum by (status) (rate(…[5m]))the same, added up across instances but still split by status
histogram_quantile(0.95, sum by (le) (rate(job_duration_seconds_bucket[15m])))the estimated 95th percentile of job duration

histogram_quantile: percentiles from buckets

A histogram never stores the individual durations, only how many fell below each boundary. To find p95 Prometheus walks the cumulative counts until it passes 95 % of the total, then assumes the observations inside that bucket are spread evenly and interpolates. Vector matching: the bug the project shipped

Binary operators (/, +, -) pair series from the left and right sides by their labels. If the label sets differ, the series without a partner simply disappears. That makes ratios easy to get wrong:

The project's alert for "more than 20 % of jobs failing" had exactly this bug: it divided the failed series by every status series and matched only with itself, so the ratio was 1.0 after any single failure. It was found by writing a unit test for the rule, and the fix is sum() on both sides.

2.6 Alert rules: conditions with patience

An alert rule is a PromQL expression evaluated on a schedule plus a for: duration. When the expression returns something, the alert becomes pending; only when it has stayed true for the whole for period does it become firing. That one knob removes most false alarms: a short spike never fires.

Prometheus decides that an alert fires. A second program, Alertmanager, decides who hears about it: it groups related alerts, silences known ones, and routes to Slack, email or a pager. The project runs Prometheus with two rules and leaves Alertmanager out, because the rules can be inspected and tested without it.

Testing a rule

Rules are code and can be unit-tested with promtool test rules: you declare synthetic series (0+9x40 means "start at 0, add 9 every step, 40 steps"), an evaluation time, and the alerts you expect. The project's test feeds a 10 % failure rate and expects nothing, then a 50 % rate and expects the alert; the old expression failed the first case.

In this project

HighJobFailureRate: more than 20 % failing over 15 minutes, for: 15m. SlowAnalysisJobs: p95 above 300 s for 10 minutes, because at 600 s the ack deadline causes redelivery and duplicate work. Both are in monitoring/alerts.yml with tests in alerts_test.yml.

2.7 Grafana: dashboards as code

Grafana does not store metrics; it asks Prometheus and draws the answer. A dashboard is a grid of panels, each panel one query plus how to show it (a time series, a single number, a gauge) and a unit. Grafana can load dashboards and data sources from files at start-up, which means the dashboard lives in git next to the code and is identical on every machine.

What makes a dashboard useful rather than decorative: the first row answers "is it healthy?" (throughput, errors, latency), the second "what does it cost or produce?" (tokens, pass ratio), and every panel has a unit. Six panels that each answer one question beat thirty that answer none.

In this project

monitoring/docker-compose.yml starts the worker in dry-run mode, Prometheus with the scrape config and rules, and Grafana with the data source and dashboard provisioned from monitoring/grafana/. python send_test_job.py --repeat 5 creates traffic. The same /metrics endpoint works unchanged with Google's managed Prometheus on Cloud Run.

2.8 Check yourself

Why does a counter restart not corrupt rate()?

Prometheus treats any decrease in a counter as a reset and adds the increase before the reset to the increase after it. The only thing lost is whatever happened between the last scrape and the restart.

When is a gauge the right type?

When the value itself is the answer and it can go down: queue length, memory, number of busy workers. If you find yourself wanting the rate of a gauge, it probably should have been a counter.

What is wrong with a label for the PR number?

Unbounded values: every PR creates a new series forever. Put the PR number in the log line and in the artifact path instead.

Why sum by (le) before histogram_quantile?

Each instance exports its own bucket series. Adding them per bucket boundary gives one histogram for the whole service; then the quantile is computed once, correctly, across instances.

What does for: 15m protect against, and what does it cost?

It stops a brief spike from paging anyone. The cost is that a real outage is reported 15 minutes late; choose the duration by how fast a human could act anyway.
