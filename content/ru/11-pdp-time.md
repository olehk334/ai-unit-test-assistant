# 11. PDP · Time Management and Self-Discipline {#ru-time}

## Простыми словами

Проект строился по фазам пять месяцев, параллельно с основной работой. Удержало его на курсе не больше рабочих часов, а раннее решение, чего не строить, доставка проверенными шагами и работа над одной вещью за раз. Этот раздел показывает три привычки на собственной истории проекта.

![Как строился проект: по фазам, каждая проверялась до следующей.](images/phases.ru.png)

## Приоритизация задач

Первая версия была ограничена простым списком must / should / could / won't. Всё из «won't» было заманчиво и удвоило бы работу.

| Приоритет | Функция | Почему |
| --- | --- | --- |
| Must | поиск изменённых файлов, цели по AST, генерация LLM, запуск pytest, цикл починки, отчёт, GitHub Actions | без любого из этого продукта нет |
| Should | предложения правок для существующих тестов, dry-run, конфиг YAML | делают инструмент пригодным и тестируемым; дёшево добавить |
| Could | облачный сервис, метрики, кэш | ценно, но только после того, как ядро работает (стали фазами 2–4) |
| Won't | web-интерфейс, база данных, автокоммит, multi-agent фреймворк, другие языки, отчёты о покрытии | много усилий или много риска, нет ценности для PDP |

Рабочее правило: **функция попадает в первую версию, только если без неё продукт бесполезен.** Всё остальное ждёт своей фазы.

## Работа с дедлайнами

Работа была разбита на фазы, каждая из которых заканчивалась чем-то демонстрируемым, поэтому сдвинувшаяся фаза никогда не оставляла «нечего показать»:

| Фаза | Когда | Результат | Подтверждение |
| --- | --- | --- | --- |
| 1 MVP | май – июнь 2026 | CLI, GitHub Actions, отчёт | юнит-тесты, dry-run CI |
| 2 Облако | июль 2026 | ресивер, Pub/Sub, воркер, `deploy.sh` | тесты сервисов |
| 3 Мониторинг | июль 2026 | метрики, дашборд, алерты | счётчики видны в Grafana |
| 4 Алгоритмы | июль 2026 | порядок импортов, LRU / LFU | юнит-тесты на алгоритм |
| 5 Упрощение | октябрь 2026 | 15 маленьких pull request | тесты зелёные после каждого |
| 6 Проверка | октябрь 2026 | всё запущено локально, 5 багов исправлено | к каждому исправлению сначала падающий тест |

Две привычки, которые сделали дедлайны переживаемыми: оценивать фазами, а не функциями, и держать буферную фазу (проверку), которая вбирает то, что пропустили раньше.

## Баланс фокуса и многозадачности

- **Один pull request за раз.** Октябрьское упрощение — пятнадцать PR, каждый достаточно мал, чтобы отревьюить за минуты, и каждый оставляет весь набор тестов зелёным. Ни один PR не смешивал рефакторинг с изменением поведения; где поведение менялось, PR говорил об этом и имел тест, падавший до него.
- **Сначала страховка.** До любого рефакторинга сквозной тест зафиксировал текущий результат. Это превратило каждый следующий шаг в механическую проверку вместо суждения — именно это позволяет остановиться и продолжить, не теряя нить.
- **Маленькие модули снижают переключение контекста.** При одной задаче на файл и зависимостях в одну сторону починить баг — значит открыть один файл. Финальное ревью всей кодовой базы заняло один присест.
- **Облако — в рамки.** Всё, что стоит денег (вызовы Gemini, развёртывание в GCP), спрятано за флагом или скриптом, который запускают осознанно; запуск по умолчанию бесплатен и офлайн, поэтому эксперименты не требуют обсуждения бюджета.

## Вероятные вопросы

**Q:** О каком вырезанном пункте вы жалеете?

**A:** Об измерении покрытия. Это был бы дешёвый сигнал для ревьюеров. Его вырезали, чтобы первая версия осталась маленькой, и это очевидный следующий шаг.

**Q:** Как избежать «последних 10 %», которые никогда не кончаются?

**A:** Определяя «готово» для фазы как «демонстрируемо и протестировано», а не «закончено». Фаза 6 была явным местом для полировки с фиксированным списком, поэтому полировка не растекалась по остальным фазам.
