# 5. PDP · CI/CD + Coding Agents {#ru-cicd}

## Простыми словами

Continuous Integration (CI) означает, что каждое изменение собирает и тестирует машина до того, как на него посмотрят люди. Continuous Delivery (CD) — что прошедшее изменение машина может и выпустить. Coding agent в CI — программа, которая делает инженерную работу внутри этого конвейера, а не только проверяет её. Агент этого проекта пишет тесты, а конвейер гарантирует, что его результат виден, но никогда не вливается сам.

## Коротко о теории

- **Конвейер — цепочка шагов по триггеру.** Триггер (push, PR, расписание), шаги (checkout, установка, тесты, сборка, публикация) и результаты (логи, артефакты, статус на коммите).
- **Секреты внедряются, а не хранятся в репозитории.** GitHub держит их зашифрованными и отдаёт задаче как переменные окружения. Для доступа к облаку лучшая практика — короткоживущая идентичность (OIDC / Workload Identity Federation) вместо долгоживущего ключа.
- **Артефакты и summary — способ задачи говорить с людьми.** Артефакт — файл, который задача загружает; step summary — Markdown на странице запуска.
- **`if: always()`** выполняет шаг даже после падения предыдущего; так отчёт переживает упавший запуск.
- **Coding agent нуждается в границе.** Он может читать репозиторий и писать артефакты; не может пушить, вливать и менять секреты. Всё за этой границей должно требовать действия человека.

## Как проект применяет это

В `.github/workflows/` два workflow:

| Workflow | Триггер | Что делает |
| --- | --- | --- |
| `ci.yml` | каждый PR и push в `main` | устанавливает проект и запускает его собственные 103 теста (dry-run, без облака) |
| `ai-test-assistant.yml` | PR, меняющий любой `.py`-файл | забирает полную историю, запускает `run-pr-assistant`, дописывает отчёт в step summary, загружает `tests/generated/` и `reports/` как артефакты |

Демо-репозиторий (`calculator`) добавляет третий workflow, `apply-ai-suggestions.yml`: когда мейнтейнер ставит на PR метку `apply-ai-suggestions`, он заново генерирует предложения, применяет их командой `ai-test-assistant apply-suggestions` и коммитит в ветку PR. Агент пересекает границу «записать в репозиторий» только потому, что человек явно попросил.

Две детали, которые стоит знать:

- `fetch-depth: 0` на checkout, потому что `git diff base...HEAD` нужна история обеих веток. Неглубокий клон молча не нашёл бы ничего, поэтому с октября инструмент падает громко, когда git не может сделать diff: запуск становится красным, а не зелёным с «изменений нет».
- Команда `apply-suggestions` отказывается писать что-либо, кроме тест-файлов внутри репозитория, даже из повреждённого артефакта. Прод-код через этот путь перезаписать нельзя.

## Вероятные вопросы

**Q:** Почему не дать агенту коммитить тесты напрямую?

**A:** Потому что проходящий тест всё ещё может быть неверным, а коммит от бота ревьюят менее внимательно, чем дифф, на который человек должен кликнуть. Артефакты плюс метка оставляют шаг человека явным и дешёвым.

**Q:** Что делает конвейер, когда Gemini недоступен?

**A:** Каждый файл попадает в отчёт с ошибкой, отчёт всё равно пишется (`if: always()`), и workflow заметно падает. В CI ничего не повторяется вслепую; повторы — дело очереди в облачном режиме.

**Q:** Как обрабатываются учётные данные Vertex AI?

**A:** В workflow демо-репозитория Google auth action входит по ключу сервисного аккаунта, хранящемуся в секрете `GCP_SA_KEY`; проект, регион и имя модели берутся из секретов и переменных. Лучшая практика и следующий шаг — Workload Identity Federation: короткоживущий токен вместо хранимого ключа. Локально инструмент использует Application Default Credentials. Ключ никогда не записывается в репозиторий.
