# 8. PDP · Distributed Systems & Cloud Architecture {#ru-cloud}

## Простыми словами

Распределённая система — несколько программ на нескольких машинах, которые вместе делают одну работу. Сложность в том, что любая из них может тормозить, перезапуститься или получить одно сообщение дважды. Облачный режим этого проекта — небольшой, но полный пример: публичный ресивер, отвечающий GitHub за миллисекунды, очередь, которая помнит работу, и приватный воркер, тратящий минуты на задачу. Каждая часть может отказать сама по себе, не потеряв задачу.

## Коротко о теории

- **Микросервисы** делят систему там, где конфликтуют требования. Ресивер должен ответить за 10 секунд таймаута webhook'а GitHub и быть доступным из интернета; воркер работает минутами и не должен быть доступен вовсе. Разные потребности — разные сервисы. Правило, которое стоит запомнить: делить по конфликтующим требованиям, а не по существительным.
- **Событийные системы** соединяют сервисы сообщениями, а не вызовами. Производитель кладёт сообщение в топик и идёт дальше; потребители берут его, когда могут. Очереди доставляют *как минимум один раз*, поэтому потребитель должен быть **идемпотентным**: обработать одно сообщение дважды — тот же эффект, что один раз.
- **Serverless** означает, что платформа запускает контейнер только когда есть работа и опускает до нуля между задачами. Сервисы должны быть без состояния; всё важное живёт в хранилище или очереди. Цена — холодный старт (от 100 мс до секунд).
- **Паттерны масштабирования здесь:** выравнивание нагрузки очередью (всплески ждут в очереди, а не перегружают воркеры), горизонтальное масштабирование (больше экземпляров, каждый с одной задачей), ограниченные повторы с **dead-letter очередью** для сообщений, которые падают всегда, и ключ идемпотентности, делающий повторы безопасными.
- **Облачные платформы.** Те же формы есть везде:

| Роль | GCP (используется) | AWS | Azure |
| --- | --- | --- | --- |
| Контейнеры, масштаб до нуля | Cloud Run | App Runner / Lambda | Container Apps |
| Очередь между сервисами | Pub/Sub | SNS + SQS | Service Bus |
| Dead letters | dead-letter топик Pub/Sub | dead-letter очередь SQS | dead-letter очередь Service Bus |
| Хранилище артефактов | Cloud Storage | S3 | Blob Storage |
| Аутентификация между сервисами | IAM + OIDC push | роли IAM | Managed Identity |
| Управляемая LLM | Vertex AI | Bedrock | Azure OpenAI |

## Как проект применяет это

**Ресивер** (`services/webhook_receiver/`, один файл): проверить HMAC-подпись общим секретом, оставить только события `pull_request` с действиями opened / synchronize / reopened, опубликовать задачу из пяти полей (`repo_full_name`, `clone_url`, `pr_number`, `head_sha`, `base_ref`) и ответить 202. Всё остальное — 401 или «ignored».

**Очередь:** один топик Pub/Sub с push-подпиской на воркер, дедлайн подтверждения 600 секунд, пять попыток доставки, затем dead-letter топик со своей pull-подпиской для разбора.

**Воркер** (`services/analysis_worker/`, шесть файлов, по одному на обязанность): HTTP-сторона, сообщение задачи, сама задача (клон → pipeline → метрики → загрузка → статус коммита), Cloud Storage, статус GitHub, метрики Prometheus. Он отвечает 200, чтобы подтвердить сообщение, и 500, чтобы Pub/Sub повторил. Повреждённое сообщение подтверждается сразу, потому что его повтор не может помочь.

**Идемпотентность:** ключ — `repo/pr/sha`, он же папка в Cloud Storage. Задача, чей JSON-отчёт уже лежит по этому пути, пропускается. Маркер пишется только при успехе, поэтому задача, упавшая на полпути, просто выполняется заново.

**Одна задача за раз:** Cloud Run запускает воркер с concurrency 1, а воркер держит блокировку на время каждой задачи, потому что пайплайн вызывает git и pytest. Масштабирование — это больше экземпляров. Эндпоинты — обычные функции в пуле потоков, поэтому `/health` и `/metrics` продолжают отвечать во время задачи (замерено: 27 мс вместо 1,6 с у прежнего async-дизайна).

**Проверено локально с эмулятором Pub/Sub:** подписанный webhook был поставлен в очередь, доставлен и обработан; задача с несуществующей базовой веткой упала пять раз и попала в dead-letter топик; счётчик упавших задач воркера вырос с 1 до 6.

**Развёртывание:** `infra/deploy.sh` создаёт всё через `gcloud`: API, Artifact Registry, оба образа через Cloud Build, топики, бакет, оба сервиса Cloud Run, push-подписку с её сервисным аккаунтом и IAM-права для dead-letter пути. Запускается осознанно: создаёт платные ресурсы.

## Вероятные вопросы

**Q:** Почему push-доставка, а не воркер, который сам забирает из очереди?

**A:** С push воркер — обычный HTTP-сервис, как и ресивер: та же модель программирования, масштабируется платформой, нет цикла подписчика, который нужно поддерживать. Pull лучше для очень долгих задач или строгого контроля скорости.

**Q:** А если две доставки одной задачи перекроются?

**A:** В одном экземпляре они не могут перекрыться (блокировка), а между экземплярами вторая найдёт отчёт в Cloud Storage и пропустит. Окно, где обе работают, мало и лишь тратит работу; испортить результат оно не может, потому что каждая задача пишет в свою папку `repo/pr/sha`.

**Q:** Почему у ресивера нет метрик?

**A:** Он делает одно дешёвое действие, и Cloud Run уже сообщает для него число запросов, задержку и ошибки. Свои метрики нужны там, где своя логика: в воркере.
