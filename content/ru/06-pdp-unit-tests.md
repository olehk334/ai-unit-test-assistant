# 6. PDP · AI Assistant for Unit Test Automation {#ru-unit-tests}

## Простыми словами

Unit-тест вызывает одну функцию с известным входом и проверяет выход. Хорошие тесты маленькие, независимые, детерминированные и названы по тому, что проверяют. LLM может писать такие тесты быстро, но может и написать тест, который не разбирается, импортирует не тот модуль или проверяет не то значение. Задача проекта — поймать всё это до того, как результат прочитает человек.

## Коротко о теории

- **pytest** находит файлы `test_*.py`, запускает каждую функцию `test_*` и считает обычный `assert` проверкой. Фикстуры дают подготовку; `pytest.raises` проверяет ошибки; параметризация прогоняет один тест по многим входам.
- **Хороший unit-тест** проверяет одно поведение, не имеет скрытых зависимостей (сеть, часы, порядок других тестов) и падает ровно по одной причине.
- **Сгенерированным тестам нужны три ворот:** синтаксические (это Python?), структурные (есть ли в нём тесты?) и поведенческие (проходят ли они на настоящем коде?). Первые две — дешёвые статические проверки; третья требует выполнения.
- **Цикл починки должен быть ограничен.** Модель, которая чинит свой тест, может зациклиться или «починить» тест, удалив проверку. Небольшое фиксированное число попыток и человек в конце делают это безопасным.

## Как проект применяет это

**Выбор целей.** `test_targets.py` разбирает файл через `ast` и оставляет публичные функции и методы (без ведущего подчёркивания), строки которых пересекаются с диффом. Сначала функции уровня модуля, затем методы, так что промпты стабильны от запуска к запуску.

**Контекст для модели.** Промпт содержит весь исходный файл, цели с их кодом и содержимое связанных существующих тестов, чтобы модель следовала стилю проекта и не дублировала существующее. Пути в промпте — пути модулей, никогда не пути на диске, поэтому один и тот же код даёт один и тот же промпт на любой машине (именно это заставляет кэш работать).

**Три ворот** живут в `llm_test_code.py`: убрать Markdown-ограждения, отвергнуть shell-shebang, разобрать через `ast`, потребовать хотя бы одну функцию `test_` или класс `Test`. Непройденные ворота поднимают `ValidationError`; ничего не записывается.

**Запуск и починка.** `pytest_runner.py` запускает pytest в подпроцессе с таймаутом 120 секунд. При падении `test_generator.py` отправляет модели исходник, тест и вывод pytest, не больше двух раз (`repair_attempts`, настраивается). После этого файл остаётся с пометкой `failed`, и отчёт объясняет причину.

**Предложения для существующих тестов.** Для каждого связанного тест-файла `suggested_updates.py` просит полную новую версию и записывает её в `reports/suggested-tests/` с заголовком. Когда два изменённых файла делят один тест-файл, вторая правка строится на первом предложении, так что ничего не теряется. `apply-suggestions` копирует предложения поверх оригиналов только когда её запускает человек.

**Имена файлов.** Сгенерированные тесты названы по полному пути: `examples/calculator.py` → `tests/generated/test_examples_calculator_generated.py`, поэтому два модуля с одинаковым именем не могут столкнуться.

## Вероятные вопросы

**Q:** Может ли модель заставить падающий тест пройти, ослабив его?

**A:** Может, в пределах двух попыток починки, и это главная причина, по которой результат ревьюят. Промпт починки говорит «исправляй только тестовый код» и «убирай неверные предположения», а ревьюер видит итоговый файл и его историю в отчёте.

**Q:** Почему не измеряется покрытие?

**A:** Его намеренно вырезали из первой версии: цифры покрытия провоцируют игру с ними, а отчёт и так говорит по каждому файлу, есть ли тесты и проходят ли они. Это естественный следующий шаг, а не пропуск.

**Q:** Как тестируется сам инструмент?

**A:** 103 теста: юнит-тесты на каждый модуль, тесты сервисов для ресивера и воркера, сквозные тесты, которые прогоняют весь пайплайн на временном git-репозитории в dry-run и фиксируют отчёт. Сценарный фальшивый LLM покрывает случаи, которые фиксированный dry-run ответ показать не может.
