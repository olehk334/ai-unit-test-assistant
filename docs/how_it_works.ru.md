# Как устроен и работает этот проект

Полный разбор AI Unit Test Assistant: что он делает, из чего состоит, почему
выбраны именно эти решения и какой измеримый выигрыш они дают.

Этот документ — «проектный» спутник материалов из `docs/exam/`, где те же
технологии разбираются со стороны теории.

---

## 1. Задача и форма решения

**Задача.** Написание юнит-тестов — механическая работа, съедающая
непропорционально большую часть времени на pull request. С рефакторингом
хуже: меняешь одно публичное поведение — ломаются двадцать существующих
тестов, и каждый нужно править вручную; это утомительно, но интеллектуально
несложно.

**Решение.** Инструмент, который читает диф pull request'а, определяет, какие
публичные функции изменились, запрашивает тесты у языковой модели,
**запускает** эти тесты, чинит их при падении и складывает всё в артефакты
для ревью — ни разу не тронув продакшен-код и не перезаписав написанный
человеком тест.

**Базовое проектное ограничение**, определяющее всё остальное:

> Ассистент производит **предложения**, а не факты. Что попадёт в
> репозиторий, решает человек.

Именно поэтому сгенерированные тесты идут в `tests/generated/`, обновлённые —
в `reports/suggested-tests/`, а не поверх оригиналов, ничего не коммитится
автоматически, и применение предложений требует явного действия (команды CLI
или метки на PR).

**Масштаб реализации:** ~2 470 строк Python в 16 модулях, покрытых 77
тестами. Достаточно мало, чтобы прочитать за вечер, — и это осознанно.

## 2. Три способа запуска

Один и тот же код конвейера имеет три точки входа. Это важно: бизнес-логика
существует **однажды**, как библиотека, а каждая «поверхность» — тонкая
обёртка.

### 2.1 Локальный CLI — цикл разработчика

```bash
ai-test-assistant run-pr-assistant --base-ref main
```

Самая быстрая обратная связь, используется в процессе разработки. Читает
`.env` и `ai-test-assistant.yml` из рабочего каталога.

### 2.2 GitHub Actions — командный цикл

Два workflow в целевом репозитории:

| Workflow | Триггер | Что делает |
| --- | --- | --- |
| `ai-test-assistant.yml` | каждый PR, затрагивающий `**/*.py` | Запускает ассистента, пишет отчёт в summary прогона, выкладывает сгенерированные тесты и отчёты артефактом |
| `apply-ai-suggestions.yml` | добавление метки `apply-ai-suggestions` на PR | Перезапускает ассистента, применяет предложенные обновления тестов, коммитит и пушит в ветку PR |

Второй workflow — это и есть кнопка «применить в один клик»: вместо скачивания
артефакта и ручного копирования файлов мейнтейнер вешает метку, а бот
открывает коммит, пригодный для ревью.

### 2.3 Облачный сервис — цикл организации

Развёрнутая событийная система, на которую любой репозиторий может направить
вебхук, без настройки CI в каждом репозитории:

```
Событие PR в GitHub
   │  HTTPS-вебхук, подписан HMAC-SHA256
   ▼
webhook-receiver        Cloud Run, публичный, масштабируется в ноль
   │  проверить подпись → отфильтровать → опубликовать → 202 Accepted
   ▼
Pub/Sub  pr-analysis-jobs
   │  push-подписка, OIDC-аутентификация, ack deadline 600 с,
   │  5 попыток доставки → dead-letter топик
   ▼
analysis-worker         Cloud Run, приватный, concurrency = 1
   │  проверка идемпотентности → клон → анализ → генерация → pytest
   ├──▶ Cloud Storage    артефакты (отчёты, сгенерированные тесты)
   └──▶ GitHub API       commit status (best-effort)
```

## 3. Конвейер по этапам

Всё описанное ниже живёт в `ai_test_assistant/` и одинаково работает во всех
трёх режимах. Оркестратор — `pipeline.run_pr_assistant()`; он намеренно
линеен и читается сверху вниз.

### Этап 1 — Определение изменённых файлов · `git_utils.py`

**Что делает:** выполняет `git diff --name-only <base_ref>...HEAD`, затем по
каждому файлу `git diff --unified=0`, разбирая **номера изменённых строк** из
заголовков ханков.

**Зачем нужны номера строк:** они позволяют следующему этапу тестировать
только то, что реально изменилось, вместо перегенерации тестов на весь файл
при каждом коммите — меньше расходов на LLM и меньше шума в дифе.

**Фильтрация** (`is_production_python_file`): оставляет `*.py` и исключает
тест-файлы (`test_*.py`, `*_test.py`), ранее сгенерированные файлы
(`*_generated.py`), всё внутри `tests/` и каждый путь из `exclude_paths`. Это
первая линия обороны принципа «никогда не анализировать и не изменять
собственный вывод».

### Этап 2 — Упорядочивание файлов по зависимостям · `import_graph.py`

**Что делает:** строит граф импортов только по изменённым файлам и
топологически сортирует его **алгоритмом Кана**, чтобы импортируемый модуль
анализировался раньше тех, кто его импортирует.

**Зачем:** если PR меняет `models.py` и `service.py` (который его
импортирует), обработка в произвольном порядке означает генерацию тестов для
`service` на основе устаревшего понимания зависимости, а порядок вывода
различался бы между запусками.

**Детали реализации:** импорты извлекаются через `ast` (не регулярками),
включая относительные импорты и форму `from package import module`; ничьи
разрешаются по исходному порядку файлов, поэтому запуски воспроизводимы;
**циклы не приводят к падению** — затронутые файлы сохраняют исходный порядок
и попадают в оба формата отчёта как `import_cycle_files`. Цикл — «запах» в
*анализируемом* репозитории, а не ошибка анализатора.

### Этап 3 — Анализ исходного кода · `source_analyzer.py`

**Что делает:** разбирает файл через `ast`, извлекает публичные функции и
публичные методы публичных классов (`FunctionInfo`, `ClassInfo`),
восстанавливает сигнатуры и вырезает исходник каждой цели через
`ast.get_source_segment`.

**Затем выбирает цели:** если номера изменённых строк известны — только
функции, диапазон строк которых с ними пересекается; если нет (например, диф
не удалось разобрать) — все публичные цели. Приватные имена (`_foo`)
пропускаются: ассистент тестирует публичный контракт, а не детали реализации.

**Почему AST, а не регулярки:** регулярное выражение не может надёжно
определить, где заканчивается функция, обработать декораторы, вложенные
определения или многострочные сигнатуры. AST — та же структура, которую видит
сам Python.

### Этап 4 — Поиск связанных существующих тестов · `test_finder.py`

**Что делает:** две эвристики.

1. **Соглашения об именах** — для `calculator/pricing.py` проверяются
   `tests/test_pricing.py`, `tests/calculator/test_pricing.py`,
   `tests/pricing_test.py`.
2. **Ссылки по содержимому** — сканирует тест-файлы на путь модуля, имя
   модуля или имена целей, используя регулярку **с границами слов**, чтобы
   функция `add` не совпала со словом `address`.

**Зачем это нужно:** найденные файлы становятся и контекстом для генерации
(«не дублируй это»), и входными данными для потока предложенных обновлений.

### Этап 5 — Построение промптов · `prompts.py`

Три системные инструкции (генерация / починка / обновление), каждая
формулирует непреложные правила: возвращать только валидный Python, без
Markdown-ограждений, без пояснений, **не изменять продакшен-код**.

**Тонкое, но критичное правило:** в промптах присутствуют **только путь
модуля и имя файла — никогда абсолютные пути**. В облаке каждое задание
клонирует репозиторий во временный каталог; если бы эти пути попадали в
промпт, одинаковый код давал бы разные промпты и кэш ответов не срабатывал бы
никогда. Регрессионный тест (`test_prompt_stability.py`) фиксирует это
поведение.

### Этап 6 — Вызов модели · `llm_client.py`

**Что делает:** тонкая обёртка над `google-genai` в режиме Vertex AI. Три
важных поведения:

- **Режим dry-run** возвращает детерминированную заглушку и вообще не ходит в
  сеть — именно это делает весь тестовый набор и локальную демонстрацию
  мониторинга бесплатными и офлайн.
- **Кэш ответов** (опциональный, внедряется снаружи): перед генерацией
  выполняется поиск по **SHA-256 от (модель, температура, системная
  инструкция, промпт)**.
- **Учёт потребления**: вызовы, секунды, токены промпта и ответа — хранятся
  как обычные целые, поэтому у библиотеки нет зависимости от системы метрик.

### Этап 7 — Очистка и валидация · `test_generator.py`

Вывод LLM — недоверенный ввод, и обращаются с ним соответственно:

1. **Очистка** — убрать Markdown-ограждения и лишние обратные кавычки.
2. **Валидация** — не пусто; успешно проходит `ast.parse()`; содержит хотя бы
   одну функцию `test_*` или класс `Test*`; не содержит shell-шебанга.

Если валидация не прошла, результат по этому файлу помечается ошибкой, а
конвейер **продолжает со следующим файлом**. Один плохой ответ никогда не
топит весь прогон.

### Этап 8 — Запуск pytest · `pytest_runner.py`

Выполняет `python -m pytest -q <path>` в подпроцессе с таймаутом, захватывая
stdout/stderr и возвращая `PytestResult`. **Падение тестов не является
исключением** — это данные, нужные следующему этапу.

**Почему подпроцесс:** изоляция. Сгенерированный код никогда не должен
импортироваться в процесс самого ассистента.

### Этап 9 — Цикл починки · `pipeline.py`

Если pytest упал, исходный код, падающий тест и вывод pytest отправляются
модели с инструкцией починки, до `repair_attempts` раз (по умолчанию 2).
Каждая попытка перезаписывает только файл в `tests/generated/`.

**Почему цикл ограничен:** бесконечный цикл с уверенно ошибающейся моделью
будет жечь деньги бесконечно. Две попытки закрывают типичные случаи (неверный
импорт, неверное ожидаемое значение) и останавливаются.

### Этап 10 — Предложения по обновлению существующих тестов · `pipeline.py`

Для каждого связанного существующего тест-файла у модели запрашивается
**полный обновлённый файл**, который записывается в
`reports/suggested-tests/<исходный путь>` с шапкой, указывающей, что это
предложение. **Оригинал не трогается.**

Это и есть поток рефакторинга — на практике экономящий больше всего времени.

### Этап 11 — Запись отчётов · `report.py`

- `reports/ai-test-report.md` — человеческая сводка: счётчики, статус по
  каждому файлу, пути сгенерированных файлов, предложенные обновления,
  результат pytest.
- `reports/ai-test-report.json` — те же данные машиночитаемо, для гейтов CI и
  дашбордов.

### Этап 12 (по запросу) — Применение предложений · `pipeline.apply_suggested_updates`

Копирует каждый предложенный файл поверх оригинала — но **только** те файлы,
которые выглядят как тесты (`test_*.py` / `*_test.py`) и разрешаются внутри
корня репозитория. Всё остальное отклоняется и попадает в список
пропущенных. Именно эта защита делает кнопку «применить в один клик»
безопасной даже при повреждённом артефакте.

## 4. Выбор технологий и обоснование

| Выбор | Что рассматривалось | Почему именно так |
| --- | --- | --- |
| **Python + `ast`** | разбор регулярками, tree-sitter | Целевой язык — Python; AST из стандартной библиотеки точен, не требует зависимостей и совпадает с тем, что видит интерпретатор |
| **Gemini 2.5 Flash на Vertex AI** | GPT/Claude через API, своя модель | Достаточно быстро и дёшево для запуска на каждом PR (центы), корпоративная аутентификация через Google IAM, не нужно отдельно управлять API-ключами |
| **temperature = 0.0** | выше — «ради креативности» | Воспроизводимый вывод, меньше выдуманных API — и это предусловие, делающее кэширование ответов корректным |
| **Typer** | argparse, click | Аннотации типов становятся CLI; меньше шаблонного кода, чем в argparse, а трёхзначный `--dry-run/--no-dry-run` получается естественно |
| **FastAPI** | Flask, чистый WSGI | Асинхронность, автоматическая валидация, крошечная поверхность — каждый сервис ~100–335 строк |
| **Cloud Run** | GKE, Cloud Functions, ВМ | Масштабирование в ноль (простой = $0), стандартные образы контейнеров (мало вендор-лока), подходит и для публичного HTTP-эндпоинта, и для приватного потребителя очереди |
| **Pub/Sub push** | pull-подписка, прямой HTTP-вызов | Push работает с масштабированием в ноль (не платим за простаивающего потребителя); брокер сам обрабатывает ретраи по HTTP-кодам |
| **GCS для артефактов** | БД, реестр артефактов | Дёшево, надёжно, а само существование объекта служит маркером идемпотентности — не нужно отдельное хранилище состояния |
| **Prometheus + Grafana** | только Cloud Monitoring, Datadog | Открытые стандарты, поднимается локально в Docker для бесплатной демонстрации, и тот же `/metrics` без изменений работает в облаке |
| **LRU-кэш, написанный вручную** | `functools.lru_cache`, Redis | Нужны счётчики попаданий/промахов как данные и кэш, общий между заданиями; плюс это результат по PDP (внутреннее устройство, а не использование) |
| **Алгоритм Кана вручную** | `graphlib.TopologicalSorter` | Бесплатное обнаружение циклов, детерминированное разрешение ничьих, отсутствие лимита рекурсии — и снова: целью было внутреннее устройство |
| **Shell-скрипт для развёртывания** | Terraform | Читаемо, ноль зависимостей, идемпотентно за счёт проверок существования. Честный компромисс: нет состояния, нет обнаружения дрейфа, нет аккуратного удаления |

## 5. Что дало каждое дополнение

MVP был обычным CLI. Поверх него добавлены четыре подсистемы, и каждая решала
реальную проблему MVP.

### 5.1 Анализ в порядке импортов (топологическая сортировка)

- **Проблема:** произвольный, невоспроизводимый порядок обработки; зависимые
  анализировались раньше своих зависимостей.
- **Улучшение:** детерминированный порядок «сначала зависимости» за O(V+E),
  плюс циклы импортов, всплывающие в отчёте как бесплатный сигнал качества
  кода.
- **Цена:** 118 строк, без зависимостей.

### 5.2 Кэш ответов LLM (LRU)

- **Проблема:** перезапуск на перебазированной ветке заново отправлял
  байт-в-байт одинаковые промпты; при temperature 0 ответ детерминирован,
  поэтому каждый повтор был чистой тратой денег и времени.
- **Улучшение — измеренное:** четыре одинаковых задания дали **3 вызова
  модели и 9 попаданий в кэш**; задания 2–4 стоили **ноль** токенов и ноль
  ожидания.
- **Цена:** 154 строки (LRU + LFU), без зависимостей.

### 5.3 Облачные сервисы (событийная архитектура)

- **Проблема:** режим «только CI» требует настройки workflow и учётных данных
  в каждом репозитории; всплеск PR запускает неограниченное число
  параллельных заданий.
- **Улучшение:** один вебхук на репозиторий вместо workflow; выравнивание
  нагрузки очередью поглощает всплески; ретраи и dead-lettering делают
  временные сбои самовосстанавливающимися; идемпотентность делает повторную
  доставку безвредной; масштабирование в ноль держит стоимость простоя на
  нуле.
- **Цена:** 435 строк в двух сервисах.

### 5.4 Мониторинг (Prometheus + Grafana)

- **Проблема:** нет видимости пропускной способности, доли отказов,
  стоимости и того, помогает ли кэш.
- **Улучшение:** шесть семейств метрик, отвечающих на значимые вопросы —
  пропускная способность, задержка относительно дедлайна очереди, расход
  токенов, эффективность кэша и KPI качества (проходят ли сгенерированные
  тесты?). Два алерта, привязанных к реальным ограничениям. Демонстрация
  через `docker compose up`, не требующая облачного аккаунта.
- **Цена:** ~40 строк инструментирования плюс конфигурационные файлы.

## 6. Измеренные результаты

Всё ниже — наблюдения в этом проекте, а не оценки.

**Реальный прогон с Gemini** (репозиторий calculator, ветка с добавлением
`percentage` и `apply_tax`):

| Показатель | Результат |
| --- | --- |
| Обнаружено изменённых файлов | 2 из 4 (README и тест-файл корректно проигнорированы) |
| Сгенерировано тест-файлов | 2, содержащих 19 тестов |
| Прошли pytest с первой попытки | Оба — цикл починки не понадобился |
| Предложенных обновлений | 1 (`tests/test_operations.py`) |
| Стоимость | 3 вызова Gemini Flash ≈ доли цента |

Примечательно, что предложенное обновление **сохранило стиль существующего
файла** (простые assert'ы, а не параметризация, использованная в
сгенерированном файле) — инструкция «сохраняй существующий стиль» доказуемо
сработала.

**Эффективность кэша** (четыре одинаковых задания, локальный стенд
мониторинга):

```
jobs_processed_total{status="processed"}     4
llm_calls_total                              3     ← модель вызвало только задание 1
llm_cache_hits_total                         9
llm_cache_misses_total                       3
generated_test_files_total{result="passed"}  8
```

**Проверка облачного конвейера** (реальное развёртывание в GCP):

| Проверка | Результат |
| --- | --- |
| Неподписанный / неверно подписанный вебхук | Отклонён с 401 |
| Подписанный вебхук | 202 + идентификатор сообщения Pub/Sub |
| Push-доставка приватному воркеру | Аутентифицирована через OIDC, HTTP 200 |
| Артефакты в GCS | `ai-test-report.json` + `.md` по пути `repo/PR/sha/` |
| Проверка идемпотентности (дубль вебхука) | `processed=1, skipped=1` |
| Проверка dead-letter | Падающее задание повторено 5×, попало в DLQ, разобрано вручную |

## 7. Модель безопасности

Восемь гарантий и механизм, обеспечивающий каждую:

| Гарантия | Чем обеспечена |
| --- | --- |
| Продакшен-код никогда не изменяется | Ассистент пишет только в `tests/generated/` и `reports/`; `apply-suggestions` отклоняет имена файлов, не похожие на тесты |
| Существующие тесты не перезаписываются автоматически | Обновления идут в `reports/suggested-tests/`; применение — отдельное явное действие |
| Ничего не коммитится автоматически | Коммитит только workflow по метке, и только файлы, подходящие под шаблоны тестов |
| Вывод LLM никогда не исполняется в текущем процессе | Проверяется через `ast.parse`, затем запускается только в подпроцессе pytest |
| Никаких shell-команд из вывода LLM | Валидация отклоняет шебанги; в коде нет пути, где ответ модели попадал бы в `exec` |
| Секреты не печатаются | URL клонирования с встроенным токеном вырезается из сообщений об ошибках; значения переменных окружения не логируются |
| Один сбой не останавливает прогон | Пофайловый try/except записывает ошибку в результат и продолжает |
| Публичный эндпоинт нельзя использовать во вред | Проверка подписи HMAC-SHA256 до любой работы; воркер приватен и вызывается только Pub/Sub |

## 8. Что мы сознательно **не** делали

Сдержанность — это проектное решение, которое стоит защищать:

- **Никакой мультиагентной архитектуры.** Один линейный конвейер
  прослеживается сверху вниз; агенты, договаривающиеся друг с другом,
  отлаживались бы сложнее и точнее не стали бы.
- **Никакой базы данных.** Всё состояние — это файлы (артефакты в GCS) и
  очередь. Добавление Postgres добавило бы эксплуатацию, не отвечая ни на
  один наш вопрос.
- **LFU не в продакшене.** Он реализован и протестирован, но LRU
  соответствует фактическому профилю доступа (всплесковые перезапуски).
  Подключение политики, которая не может выиграть на текущей нагрузке, было
  бы спекулятивной абстракцией.
- **Никакой системы плагинов, DAG-исполнителя, service mesh.** При двух
  сервисах mesh стоит дороже, чем отдаёт.
- **Никакого автоматического слияния предложений.** Вся ценность продукта
  держится на том, что человек остаётся в контуре ревью.

## 9. Ограничения, названные честно

1. **Только Python и pytest.** Анализ через AST специфичен для языка.
2. **Поиск связанных тестов эвристический.** Соглашения об именах и
   текстовые ссылки находят большинство случаев и промахнутся на необычной
   структуре проекта.
3. **Сгенерированные тесты бывают уверенно неверными.** Они могут
   фиксировать текущее поведение вместо задуманного — именно поэтому они
   попадают в каталог для ревью.
4. **Динамические импорты невидимы** статическому графу импортов
   (`importlib`, `__import__`).
5. **Метрики живут в памяти процесса.** Экземпляр Cloud Run, ушедший в ноль,
   обнуляет счётчики; `rate()` это корректно обрабатывает, но суммарные
   значения за всё время не переживают рестарт. Лечение — remote write в
   устойчивый бэкенд.
6. **Кэш существует в пределах процесса.** Несколько экземпляров воркера его
   не разделяют; общий кэш потребовал бы Redis.
7. **Измерение покрытия вне области видимости.** Ассистент сообщает, проходят
   ли тесты, а не какую долю кода они затрагивают.
8. **У `deploy.sh` нет состояния.** Он создаёт и обновляет, но не умеет
   обнаруживать дрейф и аккуратно удалять; продакшен-ответом был бы Terraform.
