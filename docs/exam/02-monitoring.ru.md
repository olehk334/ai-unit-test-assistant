# ЧАСТЬ A — КОНСПЕКТ-ШПАРГАЛКА (устный ответ)

## A1. Мониторинг против наблюдаемости

**Мониторинг** отвечает на вопросы, заготовленные заранее («CPU выше 80 %?»).
**Наблюдаемость (observability)** — это свойство системы, позволяющее по её
внешним выходным данным ответить на вопросы, которые вы *не* готовили
заранее. Мониторинг ловит «известные неизвестные», наблюдаемость — способ
отлаживать «неизвестные неизвестные».

**Сигналы:** *метрики* (дёшево, агрегированные числа во времени — «сколько,
как часто»), *логи* (дискретные события с деталями — «что именно
произошло»), *трассировки* (путь одного запроса через сервисы — «где ушло
время») и всё чаще *профили* (какой код потребил CPU/память). Prometheus
владеет пилларом метрик; Grafana визуализирует всё.

**Компромисс «стоимость/точность»:** метрики дёшевы и «лоссовы» (нет деталей
по запросу); логи точны и дороги; трассировки точны, но обычно семплируются.
Зрелая система использует метрики, чтобы **обнаружить**, трассировки — чтобы
**локализовать**, логи — чтобы **объяснить**.

## A2. Prometheus — архитектура и модель данных

**Компоненты:** сервер Prometheus (сбор/retrieval → TSDB-хранилище → движок
PromQL → HTTP API), **service discovery** (Kubernetes, EC2, GCE, Consul,
файловый), **экспортеры** (переводят сторонние системы в формат Prometheus),
**клиентские библиотеки** (инструментируют ваш код), **Pushgateway** (только
для короткоживущих пакетных задач), **Alertmanager** (маршрутизация,
дедупликация, подавление оповещений) и UI — обычно Grafana.

**Модель опроса (pull).** Prometheus по расписанию (обычно каждые 15–30 с)
опрашивает HTTP-эндпоинт `/metrics`. Почему pull — хороший выбор по
умолчанию:

- Здоровье цели достаётся бесплатно — синтетическая метрика `up` равна 1/0
  для каждой цели, поэтому «сервис исчез» само по себе является наблюдаемым
  фактом.
- Конфигурация централизована; приложению не нужно знать, где живёт система
  мониторинга.
- Тривиально отлаживать вручную: `curl localhost:8080/metrics` показывает
  ровно то, что увидит сервер.
- Естественное ограничение скорости — сбойное приложение не зальёт бэкенд.

Pull плохо подходит для короткоживущих задач (они умирают до опроса — отсюда
Pushgateway) и для недостижимых целей (за NAT). Наружу Prometheus умеет и
*push* — через **remote write** в долговременные хранилища.

**Модель данных.** Временной ряд идентифицируется именем метрики и набором
меток (labels):

```
http_requests_total{method="POST", handler="/api", status="200"}  →  (метка_времени, значение)
```

**Сэмпл** — это метка времени в миллисекундах и значение float64. Каждая
уникальная комбинация меток — **отдельный временной ряд**. Отсюда и главная
возможность (разрез по любому измерению), и главный риск — **взрыв
кардинальности**.

**Кардинальность — сказать до того, как спросят.** Никогда не кладите в
метки неограниченные значения: ID пользователей, e-mail, ID запросов, полные
URL с параметрами, таймстемпы. Число рядов перемножается: 10 методов × 50
эндпоинтов × 5 кодов = 2 500 рядов; добавьте `user_id` — станут миллионы и
сервер исчерпает память. Метки — для значений из *небольшого ограниченного*
множества.

## A3. Четыре типа метрик

| Тип | Смысл | Чем запрашивать | Пример |
| --- | --- | --- | --- |
| **Counter** (счётчик) | Монотонно растёт; обнуляется при рестарте | `rate()`, `increase()` | `requests_total` |
| **Gauge** (измеритель) | Растёт и убывает | напрямую, `avg_over_time`, `delta`, `predict_linear` | `queue_depth`, `memory_bytes` |
| **Histogram** (гистограмма) | Кумулятивные корзины + `_sum` + `_count` | `histogram_quantile()` | `request_duration_seconds` |
| **Summary** (сводка) | Квантили, посчитанные клиентом, + `_sum` + `_count` | читается напрямую | легаси-метрики задержек |

**Histogram против Summary — гарантированный вопрос.** Гистограмма
экспонирует `_bucket{le="0.1"}`, `le="0.5"`, `le="+Inf"`… Квантили считаются
во время запроса, поэтому гистограммы **можно агрегировать между
экземплярами** (`sum by (le)` → `histogram_quantile`). Summary считает
квантили внутри клиента: читать дёшево, но **математически невозможно**
усреднить между экземплярами — нельзя из p99 десяти машин получить p99
флота. Правило: **для всего, что будете агрегировать, используйте
гистограммы**, то есть на практике для задержек; цена — выбор границ корзин
заранее.

**Нативные гистограммы** (Prometheus 2.40+, дозрели к 3.0, пока за флагом
`--enable-feature=native-histograms`) снимают эту проблему: экспоненциальные
корзины подбираются автоматически с высоким разрешением и низкой стоимостью
хранения, оставаясь агрегируемыми. Это направление развития.

Соглашения об именовании: `_total` для счётчиков, базовые единицы (секунды,
байты — не миллисекунды и не мегабайты), `snake_case`, префикс-неймспейс
(`myapp_requests_total`).

## A4. PromQL

**Четыре типа выражений:** мгновенный вектор (по одному сэмплу на ряд
*сейчас*), диапазонный вектор (окно сэмплов), скаляр и строка.

```promql
http_requests_total{job="api"}          # селектор мгновенного вектора
http_requests_total{job="api"}[5m]      # диапазонный вектор — 5 минут сэмплов
```

**Функции, которые важны:**

- `rate(counter[5m])` — средняя скорость в секунду за окно; **корректно
  обрабатывает обнуления счётчика**; основной инструмент для счётчиков и
  алертов.
- `irate(counter[5m])` — мгновенная скорость по двум последним сэмплам;
  только для «дёрганых» графиков, никогда для алертов.
- `increase(counter[1h])` — общий прирост за окно (= `rate` × секунды);
  экстраполируется, поэтому может вернуть нецелое число.
- `histogram_quantile(0.95, sum(rate(x_bucket[5m])) by (le))` — идиома p95.
- `predict_linear(disk_free[6h], 4*3600) < 0` — «заполнится ли диск за
  4 часа?»; канонический предиктивный алерт.
- `absent()` / `absent_over_time()` — алерт на *исчезновение* ряда.
- Семейство `*_over_time()` (`avg`, `max`, `min`, `quantile`) — агрегация
  одного ряда по времени, а не между рядами.

**Золотое правило: `rate()` до `sum()`.**
`sum(rate(x[5m]))` — правильно; `rate(sum(x)[5m])` — неправильно: суммирование
сырых счётчиков разрушает обнаружение обнулений в каждом ряде, поэтому
рестарт пода даст огромный провал или ложный всплеск.

**Агрегация:** `sum`, `avg`, `min`, `max`, `count`, `topk`, `bottomk`,
`quantile`, `stddev` — каждая с `by (метка,…)` (оставить эти) или
`without (метка,…)` (убрать эти).

**Сопоставление векторов:** бинарные операции соединяют ряды по наборам
меток; `on(...)`/`ignoring(...)` управляют тем, какие метки сопоставляются, а
`group_left`/`group_right` позволяют соединения «многие к одному» (например,
подтянуть метаданные вроде `kube_pod_info` к измерению).

**Правило окна:** окно `rate()` должно содержать хотя бы 2 сэмпла, поэтому
берите ≥ 4× интервала сбора (при 15-секундном сборе — `[1m]` и больше;
безопасное общее значение — `[5m]`).

**Recording rules** заранее вычисляют дорогие выражения по расписанию и
сохраняют как новые ряды. Соглашение об именах — `level:metric:operations`,
например `job:http_requests:rate5m`. Применяйте для медленных или часто
повторяемых запросов дашбордов.

## A5. Конфигурация, обнаружение целей, релейблинг

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
rule_files: [ "alerts.yml" ]
scrape_configs:
  - job_name: analysis-worker
    static_configs:
      - targets: ["analysis-worker:8080"]
```

**Service discovery** заменяет статические цели в динамических средах:
`kubernetes_sd_configs` (поды/сервисы/эндпоинты/ноды), `ec2_sd`, `gce_sd`,
`azure_sd`, `consul_sd`, `file_sd` (JSON-файл, который может писать любой
скрипт).

**Релейблинг** — два хука, которые часто путают:

- `relabel_configs` работает **до** сбора: выбирает, какие цели опрашивать,
  переписывает метки целей, отбрасывает цели.
- `metric_relabel_configs` работает **после** сбора: отбрасывает или
  переписывает отдельные метрики — основной инструмент **сокращения
  кардинальности** шумного экспортера до попадания в хранилище.

Действия: `keep`, `drop`, `replace`, `labelmap`, `labeldrop`, `labelkeep`,
`hashmod` (шардирование целей между несколькими серверами Prometheus).

## A6. Хранилище и масштабирование Prometheus

**Локальная TSDB:** входящие сэмплы попадают в **head-блок** в памяти и в
**журнал упреждающей записи (WAL)** для устойчивости к падениям; каждые 2 часа
head сбрасывается в постоянный блок (чанки + индекс); блоки затем
уплотняются в более крупные; retention удаляет старые блоки по времени или
размеру. Сжатие превосходное — примерно **1–2 байта на сэмпл**.

**Один Prometheus намеренно не кластеризуется.** Это один узел с локальным
хранилищем, размер которого определяется кардинальностью и сроком хранения.
Чтобы выйти за его пределы:

- **HA:** два одинаковых сервера опрашивают одни и те же цели; кластер
  Alertmanager дедуплицирует получающиеся дубликаты оповещений.
- **Шардирование:** цели разносятся между серверами через `hashmod` или по
  функциональному признаку.
- **Долговременное хранение и глобальный обзор:** **Thanos** (sidecar
  выгружает блоки в объектное хранилище; Querier делает fan-out; Compactor
  даунсемплит), **Mimir** или **Cortex** (горизонтально масштабируемые,
  мультиарендные, через remote write), **VictoriaMetrics** (один бинарник,
  очень эффективен). Управляемые аналоги есть во всех трёх облаках.
- **Remote write** — стандартный путь push'а в эти системы.
  **Remote-Write 2.0** (Prometheus 3.0) добавляет метаданные, экземпляры
  (exemplars), created timestamp и нативные гистограммы, а также использует
  интернирование строк для уменьшения размера payload'а.

**Федерация** (один Prometheus собирает агрегированные ряды с другого) — только
для небольшого глобального обзора; не используйте её для копирования всего.

## A7. Оповещения (алертинг)

**Разделение ответственности:** *Prometheus* вычисляет правила и решает, что
алерт «горит»; *Alertmanager* решает, кто и как часто об этом узнает.

```yaml
- alert: HighJobFailureRate
  expr: rate(jobs_processed_total{status="failed"}[15m])
        / clamp_min(rate(jobs_processed_total[15m]), 1e-9) > 0.2
  for: 15m
  labels:   { severity: warning }
  annotations:
    summary: "Более 20% заданий анализа завершаются ошибкой"
```

Состояния правила: **inactive → pending** (условие истинно, выжидаем `for`) →
**firing**. Именно `for` подавляет «дребезг» (flapping).

**Возможности Alertmanager:** *группировка* (одно уведомление на 50 связанных
алертов; управляется `group_by`, `group_wait`, `group_interval`,
`repeat_interval`), *дерево маршрутизации* с матчерами для доставки нужной
команде, *подавление (inhibition)* (горящий critical глушит зависимые
warning), *сайленсы* (временное отключение на период работ) и *получатели*
(PagerDuty, Slack, e-mail, webhook).

**Философия алертинга (Google SRE):**

- Алертить на **симптомы**, а не на причины. «Пользователи получают ошибки» —
  повод разбудить; «CPU 90 %» — нет: высокая загрузка при здоровом сервисе не
  инцидент.
- Каждое пробуждение обязано быть **срочным, действенным и требующим
  человеческого суждения**. Всё остальное — тикет или дашборд.
- Усталость от алертов — реальная причина аварий: шумный пейджер приучает
  людей его игнорировать.

**Алертинг по SLO** — современная практика. При SLO 99,9 % бюджет ошибок
равен 0,1 %. **Скорость прожига (burn rate)** = наблюдаемая доля ошибок ÷
допустимая. Политика **multi-window multi-burn-rate** будит только при
действительно срочном прожиге, а медленные утечки отправляет в тикеты:

| Burn rate | Длинное окно | Короткое окно | Действие |
| --- | --- | --- | --- |
| 14,4× | 1 ч | 5 мин | Разбудить (бюджет сгорит за ~2 дня) |
| 6× | 6 ч | 30 мин | Разбудить |
| 3× | 1 д | 2 ч | Тикет |
| 1× | 3 д | 6 ч | Тикет |

Короткое окно нужно, чтобы не алертить по уже закончившемуся инциденту.

## A8. Что измерять — три канонические методики

- **Четыре золотых сигнала** (Google SRE): **задержка, трафик, ошибки,
  насыщение**. Универсальная точка старта.
- **RED** (для сервиса): **Rate, Errors, Duration** — что сервис делает.
- **USE** (для ресурса): **Utilization, Saturation, Errors** для CPU, памяти,
  диска, сети — что делает машина.

Практическое правило: RED на каждый эндпоинт сервиса, USE на каждый ресурс,
плюс небольшое число **бизнес-метрик** (обработано заданий, сгенерировано
тестов, стоимость задания). Именно бизнес-метрики делают дашборд тем, ради
чего его открывают.

## A9. Grafana

**Что это:** слой визуализации и алертинга поверх множества источников данных
(Prometheus, Loki, Tempo, Mimir, SQL-СУБД, CloudWatch, Azure Monitor, Google
Cloud Monitoring, Elasticsearch…). Сама метрики не хранит.

**Ключевые понятия:** *дашборды* из *панелей* (time series, stat, gauge,
bar, таблица, heatmap, логи, трассировки, geomap); *источники данных*;
*переменные* (query/custom/interval/datasource/ad-hoc), благодаря которым
один дашборд обслуживает все сервисы, плюс `repeat` для генерации панелей по
значениям; *трансформации* (join, reduce, group by, переименование,
арифметика), применяемые на клиенте после запроса; *аннотации* (метки
деплоев поверх графиков — самый быстрый способ связать «сломалось в 14:02» с
«выкатили в 14:01»); *Explore* для ad-hoc запросов.

**Unified alerting** (Grafana 8+): правила, управляемые Grafana, contact
points, политики уведомлений, сайленсы и mute timings — альтернатива
Alertmanager, когда источники данных разнородны.

**Провижининг / дашборды как код:** источники данных, дашборды и правила
алертов описываются YAML/JSON-файлами, подключаемыми при старте, поэтому вся
конфигурация наблюдаемости версионируется и воспроизводится — ровно это
делает данный проект в `monitoring/grafana/provisioning/`.
**Grafana 12** (май 2025) развивает идею: **Git Sync** (ветки и pull request'ы
для дашбордов прямо из UI), **динамические дашборды** (вкладки, условная
логика), приложения **Drilldown** (исследование метрик/логов/трассировок
мышью, без написания запросов) и SQL-выражения.

**Стек Grafana:** **Loki** (логи — индексируются метки, а не полный текст,
поэтому дёшево), **Tempo** (трассировки, язык запросов TraceQL), **Mimir**
(масштабируемое долговременное хранение метрик), **Pyroscope** (непрерывное
профилирование), **Alloy** (дистрибутив OpenTelemetry-коллектора, заменивший
Grafana Agent), **Beyla** (автоинструментирование через eBPF), **k6**
(нагрузочное тестирование), **OnCall**. **Exemplars** связывают точку метрики
с trace ID — мост от «p99 плохой» к «вот конкретный медленный запрос».

## A10. Быстрые вопросы и ответы

**В: Почему pull, а не push?** Здоровье цели бесплатно (`up`),
централизованная конфигурация, тривиальная локальная отладка, естественное
ограничение скорости. Push (remote write) всё равно применяется для
долговременного хранения и короткоживущих задач.

**В: Counter или gauge для «запросов в обработке»?** Gauge — величина
убывает. «Обслужено запросов» — counter.

**В: Почему не использовать summary для задержек?** Их квантили считаются на
каждом экземпляре и не агрегируются; вы никогда не получите p99 по всему
флоту. Гистограммы — получите.

**В: `rate` против `irate` против `increase`?** `rate` — средняя скорость в
секунду за окно (алерты, дашборды); `irate` — только два последних сэмпла
(волатильные графики); `increase` — суммарный прирост за окно (человекочитаемые
подсчёты).

**В: Что такое кардинальность и почему она убивает Prometheus?** Каждая
уникальная комбинация меток — отдельный ряд, хранящийся в head-блоке в
памяти; неограниченные значения меток (ID пользователей, запросов) множат
ряды до миллионов и приводят к OOM. Лечится дропами в `metric_relabel_configs`
и запретом класть идентификаторы в метки.

**В: Как обеспечить высокую доступность Prometheus?** Два одинаковых сервера
на одних целях плюс кластер Alertmanager для дедупликации. Для
долговременного/глобального запроса — Thanos или Mimir: сам Prometheus не
шардирует и не реплицирует.

**В: Зачем нужен Pushgateway и почему его не рекомендуют?** Для пакетных
задач уровня сервиса, умирающих до опроса. Он становится единой точкой
отказа, хранит метрики до явного удаления (устаревшие данные живут дальше) и
ломает контроль здоровья по целям. Использовать только по прямому назначению.

**В: На что вы алертите?** На видимые пользователю симптомы, выраженные через
скорость прожига SLO; плюс несколько предиктивных алертов («диск заполнится
за 4 часа») и алертов на отсутствие данных («конвейер встал»).

**В: Как решать, что помещать на дашборд?** Верхний ряд — четыре золотых
сигнала или RED для сервиса. Затем бизнес-KPI. Затем ресурсы (USE). Всё, на
что вы ни разу не смотрели во время инцидента, следует удалить.

# ЧАСТЬ B — ПОЛНЫЙ ОТЧЁТ

## B1. Почему модель pull определяет всё остальное

Решение опрашивать, а не принимать, задаёт весь дизайн Prometheus. Поскольку
Prometheus инициирует контакт, он владеет авторитетным **списком того, что
должно существовать** — результатом service discovery. Этот список делает
возможной важнейшую метрику системы, `up`, синтезируемую для каждой цели при
каждом опросе. В push-архитектуре «нет данных» неоднозначно: сервис может
быть здоров и простаивать, быть неверно настроен или быть мёртв. В pull-модели
разница явная.

Следствие: Prometheus — это **система мониторинга, а не хранилище событий**.
Он дискретно сэмплирует состояние; он никогда не расскажет о всплеске,
целиком уместившемся между двумя опросами, и не годится как биллинговая
запись. Если нужны все события — это лог или конвейер данных. Проговорите
это, когда спросят «можно ли использовать Prometheus для X?»: ответ «нет»
всегда, когда требуется точный учёт каждого события.

Ещё одно следствие — **обработка устаревания (staleness)**. Если ряд перестал
приходить, Prometheus помечает его устаревшим примерно через 5 минут, а не
тянет последнее значение вечно, поэтому графики и алерты не «замерзают»
молча на старых данных.

## B2. Правильное инструментирование приложения

Прямое инструментирование клиентской библиотекой, из воркера этого проекта:

```python
from prometheus_client import Counter, Histogram, generate_latest

JOBS_PROCESSED = Counter(
    "jobs_processed_total", "Analysis jobs by outcome", ["status"]
)
JOB_DURATION = Histogram(
    "job_duration_seconds", "End-to-end job duration",
    buckets=(5, 15, 30, 60, 120, 300, 600),
)

@app.get("/metrics")
def metrics() -> Response:
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)
```

Здесь видны проектные решения, каждое из которых защитимо на экзамене:

1. **`status` — метка с ограниченным множеством значений** (`processed`,
   `skipped`, `failed`, `ignored`) — четыре значения, безопасно. Метка `repo`
   была бы неограниченной и неверной.
2. **Корзины подобраны под предметную область.** Корзины по умолчанию
   заканчиваются около 10 секунд, что бесполезно для заданий длиной в минуты.
   Границы выбраны вокруг SLO и 600-секундного дедлайна подтверждения
   Pub/Sub, поэтому гистограмма реально отвечает на вопрос «не приближаемся ли
   мы к повторной доставке?».
3. **Счётчики, а не gauge, для событий** — тогда `rate()` даёт пропускную
   способность и корректно переживает рестарты процесса.
4. **Счётчик токенов** превращает стоимость в первоклассную величину, которую
   можно нарисовать на графике.

**Что инструментировать не надо:** всё, что уже даёт платформа. Cloud Run
экспортирует число запросов, задержку и долю ошибок; Pub/Sub экспортирует
`num_undelivered_messages` (бэклог). Измерять бэклог внутри воркера было бы
строго худшими данными — воркер не видит сообщений, которых не получил.
**Кастомные метрики — там, где кастомная логика.**

## B3. PromQL как язык

PromQL функционален и множествен: каждое выражение возвращает *множество*
помеченных рядов, а операции соединяют эти множества по меткам.

Стандартный конвейер — **селектор → диапазонный вектор → функция →
агрегация**:

```promql
sum by (status) (rate(jobs_processed_total[5m])) * 60
```

Читаем изнутри наружу: взять счётчик с пятиминутной историей; превратить в
скорость в секунду по каждому ряду (с обработкой обнулений); просуммировать
эти скорости с группировкой по `status`; перевести в минуты для человека.

**Сборник рецептов, который стоит запомнить:**

```promql
# Пропускная способность в минуту, с разрезом по исходам
rate(jobs_processed_total[5m]) * 60

# Доля ошибок, с защитой от деления на ноль
rate(jobs_processed_total{status="failed"}[15m])
  / clamp_min(rate(jobs_processed_total[15m]), 1e-9)

# p95 задержки по всем экземплярам (возможно только с гистограммами)
histogram_quantile(0.95, sum by (le) (rate(job_duration_seconds_bucket[15m])))

# Средняя задержка (sum/count — дешевле и иногда честнее квантиля)
rate(job_duration_seconds_sum[15m]) / rate(job_duration_seconds_count[15m])

# Коэффициент попаданий в кэш (за всё время)
llm_cache_hits_total / clamp_min(llm_cache_hits_total + llm_cache_misses_total, 1)

# Топ-5 самых «шумных» метрик — инструмент расследования кардинальности
topk(5, count by (__name__)({__name__=~".+"}))

# Алерт на то, что конвейер замолчал
absent_over_time(jobs_processed_total[30m])

# Диск заполнится в ближайшие четыре часа
predict_linear(node_filesystem_avail_bytes[6h], 4*3600) < 0

# Подтянуть метаданные из info-метрики (соединение «многие к одному»)
sum by (pod) (rate(http_requests_total[5m]))
  * on(pod) group_left(node) kube_pod_info
```

**Ловушки, которые лучше назвать раньше экзаменатора:**

- `rate()` по gauge бессмысленен — функция предполагает монотонность.
- `sum()` до `rate()` ломает обнаружение обнулений.
- Окно `rate()` короче 4× интервала сбора даёт дыры или шум.
- `histogram_quantile` по корзинам, не рассчитанным на ваш диапазон, вернёт
  мусор, «прижатый» к верхней корзине — всегда держите разумный `+Inf` и
  достаточное разрешение вокруг порога SLO.
- Квантили нельзя усреднять. `avg(p99)` не является p99 ни для чего.

## B4. Эксплуатация Prometheus в масштабе

**Расчёт ресурсов.** Память определяется числом активных рядов в head-блоке;
распространённая оценка — несколько килобайт на ряд плюс рабочая память
запросов. Диск = сэмплы × ~1–2 байта × срок хранения. Обе величины
масштабируются с **кардинальностью**, поэтому именно её нужно
контролировать.

**Как сокращать кардинальность на практике:**

```yaml
metric_relabel_configs:
  # Полностью отбросить шумное семейство метрик
  - source_labels: [__name__]
    regex: "go_gc_duration_seconds.*"
    action: drop
  # Убрать метку высокой кардинальности, оставив саму метрику
  - regex: "request_id"
    action: labeldrop
```

Расследовать помогает `topk(20, count by (__name__)({__name__=~".+"}))` и
страница статуса TSDB, которая перечисляет имена метрик и меток с наибольшей
кардинальностью.

**Выбор архитектуры долговременного хранения:**

| Потребность | Решение |
| --- | --- |
| Одна команда, 15 дней данных | Обычный Prometheus с постоянным томом |
| Пережить отказ Prometheus | Две реплики + кластер Alertmanager |
| Годы истории, глобальный обзор | Thanos (объектное хранилище + даунсемплинг) или Mimir |
| Мультиарендная платформа | Mimir или Cortex |
| Минимум эксплуатации, высокая эффективность | VictoriaMetrics |
| Управляемое решение | Amazon Managed Prometheus / Google Managed Prometheus / Azure Monitor managed Prometheus |

**Prometheus 3.0** (ноябрь 2024) — ориентир «что актуально»: UTF-8 в именах
метрик и меток по умолчанию, встроенный **приёмник OTLP**
(`/api/v1/otlp/v1/metrics`), позволяющий SDK OpenTelemetry писать напрямую,
Remote-Write 2.0, переписанный UI и нативные гистограммы, идущие к
стабильности. Стратегический смысл — конвергенция с OpenTelemetry:
инструментируем OTel, храним в Prometheus-совместимых бэкендах, запрашиваем
на PromQL.

## B5. Проектирование алертов, которым доверяют

**Симптом против причины, конкретно.** Набор алертов «по причинам» для
веб-сервиса будил бы по высокому CPU, малому месту на диске, долгому GC и
рестартам подов — четыре пробуждения на один инцидент, три из которых по
отдельности безобидны. Набор «по симптомам» будит по «доля ошибок выше
прожига SLO» и «задержка выше SLO», а дежурный уже по дашбордам находит
причину. Причины живут в дашбордах и тикетах, а не в пейджере.

**Жизненный цикл алерта, который стоит описать:**

1. Prometheus вычисляет правила каждые `evaluation_interval`.
2. Совпавшее выражение переводит алерт в **pending**.
3. По истечении `for` алерт становится **firing** и повторно отправляется в
   Alertmanager (Prometheus шлёт заново; дедупликация — забота Alertmanager).
4. Alertmanager группирует по меткам, ждёт `group_wait` для сбора связанных
   алертов, применяет подавление и сайленсы и маршрутизирует получателю.
5. Когда выражение перестаёт совпадать, Prometheus отправляет уведомление о
   разрешении.

**Ранбуки.** В аннотациях каждого алерта должна быть ссылка на ранбук: что
означает алерт, как подтвердить, как смягчить, кому эскалировать. Алерт без
ранбука в три часа ночи будет обработан плохо тем, кто оказался на дежурстве.

**Два правила этого проекта и их обоснование:**

- `HighJobFailureRate` — более 20 % отказов за 15 минут. Уровень симптома
  (пользователи не получают предложений по тестам), `for: 15m` игнорирует
  единичное неудачное задание.
- `SlowAnalysisJobs` — p95 длительности задания выше 300 с в течение
  10 минут. Это не «метрика ради метрики»: дедлайн подтверждения Pub/Sub
  равен 600 с, и его превышение вызывает повторную доставку и двойную
  работу. **Это и есть признак хорошего алерта — он привязан к реальному
  ограничению системы, а не к круглому числу.**

## B6. Проектирование дашбордов

Дашборд — документ с аудиторией и целью. Сначала сформулируйте цель, потом
проектируйте.

**Работающая компоновка:**

1. **Верхний ряд — заголовок состояния.** Четыре-шесть панелей: скорость
   запросов/заданий, доля ошибок, p95 задержки, насыщение. Дежурный должен
   за пять секунд понять «сломано ли и насколько сильно».
2. **Второй ряд — бизнес-результат.** Для этого проекта: доля прошедших
   сгенерированных тестов, коэффициент попаданий в кэш, токены в минуту
   (стоимость).
3. **Нижние ряды — детализация.** Задержки по зависимостям, глубина очереди,
   потребление ресурсов.
4. **Низ — логи и ссылки.** Exemplars, ссылки на трассировки и ранбуки.

**Правила ремесла:** единые единицы измерения и цвета (красный = плохо
везде); пороги, нарисованные на графике, чтобы «плохо» было видно без знания
SLO; переменные-шаблоны вместо копий дашборда на каждое окружение; аннотации
деплоев; и безжалостное удаление — дашборд на 60 панелей никто не читает.

**Дашборды как код.** Провижинить JSON из git (как в этом проекте) или
использовать Git Sync в Grafana 12. Выгоды: ревью, откат, одинаковые дашборды
во всех окружениях и восстановление после сбоя. Собранные руками дашборды
дрейфуют и умирают вместе с тем, кто их сделал.

## B7. За пределами метрик: остальная наблюдаемость

**Логи.** Структурированные (JSON), с корреляционным/трассировочным ID,
осмысленными уровнями и без секретов. В Loki индексируйте только
ограниченные метки (`service`, `env`, `level`), а содержимое ищите на этапе
запроса — модель стоимости Loki обратна модели Elasticsearch.

**Трассировки.** SDK OpenTelemetry передаёт контекст трассировки (W3C
`traceparent`) через границы сервисов; каждый сервис записывает спаны;
бэкенд (Tempo, Jaeger, X-Ray, Cloud Trace) собирает водопад. Head sampling
решает в начале (дёшево, можно потерять редкие ошибки); tail sampling решает,
увидев трассировку целиком (сохраняет интересное, требует больше
инфраструктуры).

**Рабочий процесс по трём сигналам** (стоит проговорить вслух): сработал
алерт по метрике → дашборд локализует сервис и временное окно → exemplar
ведёт к репрезентативной трассировке → трассировка показывает медленный или
сбойный спан → логи по этому trace ID объясняют почему. Каждый переход должен
быть одним кликом; построение этих связей и составляет бо́льшую часть
ценности платформы наблюдаемости.

**Стратегия инструментирования сегодня:** OpenTelemetry для приложений
(вендор-нейтрально, один API для метрик/трассировок/логов), экспорт в
Prometheus-совместимое хранилище, и экспортеры Prometheus — для
инфраструктуры. Это избавляет от переинструментирования при смене бэкенда.

## B8. Как эта тема демонстрируется в проекте

**Локальный стенд** (`monitoring/docker-compose.yml`) — три контейнера в
одной сети: воркер анализа (в режиме dry-run: настоящий клон, настоящий
pytest, заглушённый LLM), Prometheus, опрашивающий его каждые 5 с и
вычисляющий правила алертов, и Grafana с провижининговыми источником данных и
дашбордом. Вся демонстрация наблюдаемости поднимается командой
`docker compose up --build` и не требует ни облачного аккаунта, ни учётных
данных.

**Набор метрик и логика выбора каждой:**

| Метрика | Тип | На какой вопрос отвечает |
| --- | --- | --- |
| `jobs_processed_total{status}` | counter | Пропускная способность и доля отказов |
| `job_duration_seconds` | histogram | p95 относительно дедлайна подтверждения в 600 с |
| `llm_calls_total`, `llm_seconds_total` | counter | Как часто и как долго ждём модель |
| `llm_prompt_tokens_total`, `llm_response_tokens_total` | counter | Стоимость в минуту |
| `llm_cache_hits_total` / `_misses_total` | counter | Окупается ли LRU-кэш? |
| `generated_test_files_total{result}` | counter | KPI качества: проходят ли сгенерированные тесты? |

**Измеренный результат, который стоит цитировать.** На локальный стенд были
отправлены четыре одинаковых задания. Счётчики после этого:

```
jobs_processed_total{status="processed"}  4
llm_calls_total                           3
llm_cache_hits_total                      9
llm_cache_misses_total                    3
generated_test_files_total{result="passed"} 8
```

Задание 1 дало три промаха (три реальных вызова модели); задания 2–4 были
обслужены целиком из LRU-кэша — девять попаданий и ноль дополнительных
вызовов. **Оптимизация из темы 3 не декларируется, а измеряется**, и панель
коэффициента попаданий рядом с панелью расхода токенов делает экономию
видимой. Такая пара — оптимизация и метрика, её доказывающая, — самый сильный
ответ на вопрос «зачем вы добавили мониторинг?».

**Облачный путь.** Тот же эндпоинт `/metrics` собирается Google Managed
Service for Prometheus на Cloud Run, и тот же JSON дашборда импортируется без
изменений. Ничто в приложении не отличает локальный сбор от облачного — а это
и есть выгода pull-модели и открытого формата экспозиции.

**Честное ограничение, которое стоит озвучить самому:** метрики живут в
памяти процесса, поэтому экземпляр Cloud Run, масштабировавшийся в ноль,
обнуляет счётчики. `rate()` корректно обрабатывает обнуления, так что графики
пропускной способности остаются верными, но суммарные значения за всё время
не переживают рестарт. Лечение — remote write в устойчивый бэкенд; это стоит
назвать как задел на будущее, а не делать вид, что проблемы нет.
