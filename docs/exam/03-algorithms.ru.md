# ЧАСТЬ A — КОНСПЕКТ-ШПАРГАЛКА (устный ответ)

## A1. Топологическая сортировка — определение и существование

**Топологический порядок** ориентированного графа — это линейное
упорядочивание вершин, при котором для каждого ребра `u → v` вершина `u`
стоит раньше `v`.

- Он существует **тогда и только тогда**, когда граф является **DAG**
  (ориентированным ациклическим графом). Цикл делает упорядочивание логически
  невозможным: каждая вершина должна была бы предшествовать самой себе.
- В общем случае он **не единственный**. Единственным он бывает ровно тогда,
  когда в DAG есть гамильтонов путь, — то есть каждая соседняя пара связана и
  свободы не остаётся.
- Оба стандартных алгоритма работают за **O(V + E)** времени и **O(V)**
  дополнительной памяти.

Направление ребра читается как «должно произойти раньше»: `models.py →
service.py` означает, что models — предпосылка для service.

## A2. Алгоритм Кана (BFS / входящие степени)

```python
def kahn(nodes, edges):                 # edges: зависимость -> [зависимые]
    indegree = {n: 0 for n in nodes}
    for u in nodes:
        for v in edges[u]:
            indegree[v] += 1

    ready = deque(n for n in nodes if indegree[n] == 0)
    order = []
    while ready:
        u = ready.popleft()
        order.append(u)
        for v in edges[u]:
            indegree[v] -= 1
            if indegree[v] == 0:
                ready.append(v)

    if len(order) != len(nodes):
        cycle = [n for n in nodes if n not in set(order)]   # участники цикла
    return order, cycle
```

**Почему это работает:** у вершины с входящей степенью 0 нет невыполненных
предпосылок, значит её безопасно выдать. Её выдача удаляет исходящие рёбра,
что может освободить другие вершины.

**Обнаружение цикла бесплатно:** если цикл завершился, не выдав все вершины,
оставшиеся — ровно те, что заперты в цикле (или ниже по течению от него);
никакого дополнительного учёта не требуется.

**Полезные вариации:**

- Заменить очередь **мин-кучей** → лексикографически наименьший допустимый
  порядок за `O(V log V + E)`.
- Обрабатывать очередь **по уровням** → каждый уровень есть набор задач без
  взаимных зависимостей, то есть **расписание параллельного выполнения**;
  число уровней равно длине критического пути.
- Разрешать ничьи по исходному порядку входных данных → **детерминированный**
  результат, что важно для воспроизводимых сборок и стабильного вывода
  тестов.

## A3. Алгоритм на основе DFS

```python
WHITE, GRAY, BLACK = 0, 1, 2       # не посещена, в обработке, завершена

def dfs_topo(nodes, edges):
    colour, out = {n: WHITE for n in nodes}, []
    def visit(u):
        colour[u] = GRAY
        for v in edges[u]:
            if colour[v] == GRAY:  raise CycleError(u, v)   # обратное ребро
            if colour[v] == WHITE: visit(v)
        colour[u] = BLACK
        out.append(u)              # пост-порядок
    for n in nodes:
        if colour[n] == WHITE: visit(n)
    return out[::-1]               # обратный пост-порядок = топологический
```

Идея: вершина добавляется только после того, как завершены **все** её
потомки, поэтому разворот порядка завершения ставит каждую вершину раньше
всего, от чего она зависит. **Обратное ребро** (ребро в GRAY-вершину)
доказывает наличие цикла.

**Кан против DFS — как выбирать:**

| | Кан | DFS |
| --- | --- | --- |
| Стиль | Итеративный — нет лимита рекурсии | Рекурсивный (или явный стек) |
| Обнаружение цикла | Бесплатно (проверка счётчика) | Обратное ребро через трёхцветную разметку |
| Дополнительная ценность | Уровни, параллельное расписание, лексикографический контроль | Времена завершения, интеграция с другой DFS-работой (SCC) |
| Когда лучше | Нужны детерминизм, уровни или безопасность на глубоких графах | Вы уже обходите в глубину или нужны SCC |

## A4. Применения и соседние алгоритмы

**Применения:** системы сборки (make, Bazel, Gradle), разрешение зависимостей
пакетов, планировщики задач (DAG в Airflow, конвейеры CI), пререквизиты
курсов, пересчёт электронных таблиц, порядок инициализации модулей и
планирование инструкций в компиляторах, разрешение символов компоновщиком,
порядок миграций БД, связывание контейнера внедрения зависимостей,
обнаружение взаимоблокировок по графу ожидания, и — в этом проекте —
упорядочивание изменённых исходных файлов, чтобы модуль анализировался раньше
тех модулей, которые его импортируют.

**Соседние алгоритмы, которые стоит назвать:**

- **Компоненты сильной связности (SCC)** (Тарьян или Косараджу, оба
  `O(V+E)`): если цикл всё-таки есть, стягиваем каждую SCC в один узел.
  **Конденсация** всегда является DAG, и её можно топологически отсортировать.
  Это профессиональный ответ на вопрос «а если цикл?» — не падать, а
  конденсировать.
- **ДП на DAG:** релаксация рёбер в топологическом порядке даёт кратчайшие
  *и* длиннейшие пути за `O(V+E)`, что невозможно в общем графе. Длиннейший
  путь = **критический путь** (CPM) = минимально возможное время завершения.
- **Коффман — Грэм** — планирование при ограниченном числе процессоров.

## A5. Кэширование — зачем нужна политика вытеснения

Кэш — это небольшое быстрое хранилище перед большим медленным. Именно
потому, что он мал, каждая вставка сверх ёмкости требует решения: **какую
запись вытеснить**. Это решение и есть политика вытеснения, и оно определяет
**коэффициент попаданий (hit ratio)** — единственную по-настоящему важную
метрику, поскольку
`средняя задержка ≈ hit_ratio × быстро + (1 − hit_ratio) × медленно`.

**Оптимальный алгоритм Белади (OPT/MIN)** вытесняет запись, следующее
обращение к которой наступит позже всех. Он доказуемо оптимален и
нереализуем (требует знания будущего), поэтому служит эталоном: реальные
политики измеряют в процентах от OPT.

Две модели доступа мотивируют две основные политики:

- **Временна́я локальность** — недавно использованное вероятно понадобится
  снова → **LRU**.
- **Перекос по частоте** — небольшая часть элементов популярна на длинных
  интервалах → **LFU**.

## A6. Внутреннее устройство LRU

**Требование:** `get` и `put` за O(1), включая вытеснение.

**Структура — хеш-таблица + двусвязный список:**

- `dict: ключ → узел` даёт поиск за O(1).
- **Двусвязный список** хранит порядок использования: самый свежий сразу
  после `head`, самый старый — перед `tail`.
- Два **узла-часовых (sentinel)** (`head`, `tail`) убирают все частные случаи
  пустого списка и краёв — список никогда не бывает по-настоящему пустым.

```
head ⇄ [самый свежий] ⇄ [ ] ⇄ [ ] ⇄ [самый старый] ⇄ tail
```

**Операции:**

- `get(k)`: поиск в словаре; при попадании **отцепить** узел и **прицепить**
  после `head` (две перестановки указателей); вернуть значение.
- `put(k, v)`: если ключ есть — обновить значение и переместить в начало.
  Если нет и кэш полон — вытеснить `tail.prev`, удалив его и из списка, **и
  из словаря**, затем вставить новый узел после `head`.

**Почему двусвязный?** Удаление узла из середины за O(1) требует знания его
предшественника. Односвязному списку понадобился бы проход за O(n).

**Почему не массив и не куча?** Массиву нужен сдвиг за O(n); куча делает
операции O(log n). Комбинация «словарь + список» — единственная структура,
дающая O(1) для всех трёх требований.

**Готовые средства языка:** `collections.OrderedDict` в Python даёт
`move_to_end()` и `popitem(last=False)` — это LRU, реализованный на C;
`functools.lru_cache` внутри использует кольцевой двусвязный список.
Упомянуть их полезно для широты, но на экзамене обычно ждут реализацию
руками.

**Классические ошибки, которые стоит проговорить:** забыть, что `get` обязан
обновлять свежесть; забыть удалить вытесненный ключ из словаря (утечка
памяти); позволить обновлению существующего ключа увеличить размер; не
обработать нулевую ёмкость.

## A7. Внутреннее устройство LFU

**Наивно:** мин-куча по частоте → O(log n) на операцию. Допустимо, но
ожидаемый ответ — **реализация за O(1)** (Shah, Mitra & Matani, 2010).

**Структура — три отображения и указатель:**

- `values: ключ → значение`
- `freqs: ключ → счётчик обращений`
- `buckets: счётчик → упорядоченное множество ключей с этой частотой`
  (порядок вставки внутри корзины = порядок свежести, старейший первым)
- `min_freq`: наименьшая непустая корзина

**Операции:**

- `get(k)`: прочитать значение, затем переместить ключ из `buckets[f]` в
  `buckets[f+1]`. Если `buckets[f]` опустела **и** `f == min_freq`, то
  `min_freq += 1`.
- `put(k, v)` для нового ключа при переполнении: вытеснить **старейший** ключ
  из `buckets[min_freq]` (`popitem(last=False)`), вставить новый ключ с
  частотой 1 и установить `min_freq = 1`.

**Почему `min_freq` всегда корректен:** новая запись всегда входит с частотой
1, что сбрасывает минимум; а частота увеличивается только на единицу за раз,
поэтому при опустошении минимальной корзины новым минимумом становится ровно
следующее целое. Поиск не нужен никогда — именно это и даёт O(1).

**Разрешение ничьих по LRU** внутри корзины: среди одинаково непопулярных
вытесняем ту запись, к которой дольше всех не обращались.

**Фатальный недостаток LFU: старение / загрязнение кэша.** Элемент, бывший
горячим вчера, навсегда сохраняет огромный счётчик и не может быть вытеснен,
тогда как реально горячие новые элементы выбрасываются со счётчиком 1.
Лечение: периодически **делить все счётчики пополам** (экспоненциальное
затухание), использовать **скользящее окно**, **вероятностный счётчик с
затуханием по времени** (подход Redis) или **W-TinyLFU**.

## A8. Ландшафт политик

| Политика | Идея | Сильная сторона | Слабость |
| --- | --- | --- | --- |
| **FIFO** | Вытеснить вставленный раньше всех | Тривиально | Игнорирует использование; подвержена аномалии Белади |
| **Random** | Вытеснить случайную запись | O(1), без метаданных | Посредственный hit ratio |
| **LRU** | Вытеснить наименее недавно использованную | Отлично при временно́й локальности; O(1) | Один полный скан вымывает весь кэш |
| **LFU** | Вытеснить наименее часто используемую | Отлично при стабильной популярности | Проблема старения; медленно адаптируется |
| **CLOCK / второй шанс** | Приближение LRU одним битом обращения на кольце | Очень дёшево; используется в кэшах страниц ОС | Грубее настоящего LRU |
| **SLRU / 2Q** | Сегменты «испытательный» и «защищённый» | Устойчива к сканам | Больше настроек |
| **ARC** | Адаптивный баланс свежести и частоты с «призрачными» списками | Самонастраивается, отлично работает | Сложна; была обременена патентом |
| **W-TinyLFU** | Допуск по частотному эскизу + маленькое LRU-окно + основной SLRU | Лучшие в классе hit ratio (Caffeine) | Самая сложная |

**Аномалия Белади:** для FIFO *увеличение* размера кэша может *увеличить*
число промахов. Для **стековых алгоритмов** — LRU, LFU и OPT — это
невозможно, потому что их содержимое при размере *n* всегда является
подмножеством содержимого при размере *n+1* (свойство включения). Любимый
продвинутый вопрос.

**Реальные системы:** кэши процессора используют псевдо-LRU с ассоциативными
множествами; кэши страниц ОС — варианты CLOCK; **Redis** предлагает
`allkeys-lru`, `allkeys-lfu`, `volatile-ttl` и другие, реализуя
*приближённый* LRU через выборку `maxmemory-samples` ключей (по умолчанию 5)
вместо глобального списка, а LFU — как 8-битный логарифмический счётчик с
затуханием по времени; **Caffeine** (Java) использует W-TinyLFU;
**Memcached** — сегментированный LRU; CDN часто применяют допуск по частоте,
поскольку хранилище огромно, а объекты велики.

## A9. Паттерны кэширования и опасности (сверх вытеснения)

**Паттерны чтения:** *cache-aside* (приложение проверяет кэш, при промахе
грузит и заполняет — самый распространённый, оставляет кэш опциональным),
*read-through* (библиотека кэша грузит сама), *refresh-ahead*
(упреждающее обновление до истечения).
**Паттерны записи:** *write-through* (пишем в оба, согласованно, медленнее),
*write-behind/back* (пишем в кэш сейчас, в хранилище потом — быстро, риск
потери), *write-around* (пишем в хранилище, инвалидируем кэш — хорошо, когда
записанное редко читают).

**Опасности, которые надо назвать:**

- **Cache stampede / dogpile** — истёк горячий ключ, и тысяча запросов
  одновременно бьёт в БД. Лечение: блокировка single-flight, вероятностное
  досрочное истечение, stale-while-revalidate.
- **Cache avalanche** — множество ключей истекает одновременно. Лечение:
  джиттер TTL.
- **Cache penetration** — повторяющиеся запросы несуществующего ключа.
  Лечение: негативное кэширование или фильтр Блума.
- **Горячий ключ** — один ключ насыщает один узел. Лечение: реплицировать
  ключ или добавить клиентский уровень кэша.
- **Устаревшие данные** — самая трудная проблема. Лечение: короткие TTL,
  инвалидация по событиям или версионированные ключи (`user:42:v7`), которые
  вовсе устраняют удаление.

**Распределённое кэширование** добавляет **консистентное хеширование с
виртуальными узлами**, чтобы добавление узла перемещало лишь ~1/N ключей, и
заставляет решить, является ли кэш источником истины (не должен).

## A10. Быстрые вопросы и ответы

**В: Докажите, что топологический порядок существует тогда и только тогда,
когда граф ациклический.**
(⇐) В конечном DAG есть вершина с входящей степенью 0 (иначе можно бесконечно
идти по рёбрам назад и, в силу конечности, повторить вершину — цикл). Выдаём
её, удаляем, остаток по-прежнему DAG; индукция.
(⇒) Если бы цикл существовал, каждая его вершина должна была бы
предшествовать следующей и, значит, самой себе — противоречие.

**В: Кан или DFS?** Кан — когда нужны отчёт о цикле, детерминированный вывод,
уровни или отсутствие риска переполнения стека; DFS — когда вы уже обходите в
глубину или нужны SCC.

**В: Что делать, если в графе зависимостей есть цикл?** Обнаружить, сообщить
об участниках и деградировать штатно — либо конденсировать SCC и
отсортировать конденсацию. Валить всю задачу из-за цикла обычно неверное
продуктовое решение.

**В: Почему LRU — это хеш-таблица плюс двусвязный список?** Таблица даёт
поиск за O(1), список — переупорядочивание за O(1) и вытеснение с хвоста за
O(1), а двойные связи позволяют отцепить известный узел, не разыскивая его
предшественника.

**В: Как LFU достигает O(1)?** Частотные корзины из ключей в порядке вставки
плюс указатель `min_freq`. Инкремент переносит ключ в соседнюю корзину,
вытеснение забирает старейший ключ из минимальной корзины. Поиск не
выполняется никогда.

**В: LRU или LFU для моей нагрузки?** LRU — при всплесковом доступе,
управляемом свежестью (перезапуски, сессии, скользящее рабочее множество).
LFU — когда стабильное подмножество устойчиво популярно, а разовый трафик
иначе вымыл бы кэш. Современный дефолт — гибрид вроде W-TinyLFU или ARC.

**В: Что убивает LRU?** Большое последовательное сканирование: оно вытесняет
всё рабочее множество данными, которые больше не понадобятся. Именно для
этого существуют устойчивые к сканам политики (2Q, SLRU, ARC, TinyLFU).

**В: Что такое аномалия Белади и какие политики от неё свободны?** При FIFO
больший кэш может дать больше промахов. Стековые алгоритмы (LRU, LFU, OPT)
защищены свойством включения.

**В: Как понять, что кэш помогает?** Измерять hit ratio и ставить рядом ту
метрику стоимости, которую он должен снижать. Неизмеренный кэш — это
гипотеза.

# ЧАСТЬ B — ПОЛНЫЙ ОТЧЁТ

## B1. Графы: кратко и формально

Ориентированный граф `G = (V, E)` состоит из вершин и упорядоченных пар
вершин. **Путь** следует направлению рёбер; **цикл** — путь из вершины в
саму себя. **DAG** не имеет циклов. DAG моделируют любое отношение «должно
произойти раньше» — поэтому один и тот же алгоритм встречается в системах
сборки, планировщиках, компиляторах и электронных таблицах.

**Представление влияет на сложность.** Список смежности занимает `O(V + E)`
памяти и позволяет перебрать соседей вершины за время, пропорциональное её
степени, — именно поэтому оба алгоритма работают за `O(V + E)`. Матрица
смежности занимает `O(V²)` и превратила бы те же алгоритмы в `O(V²)`. Для
разреженных графов зависимостей (реальный код, реальные задачи) списки
смежности всегда правильны.

**Словарь терминов:** входящая степень (входящие рёбра), исходящая степень,
источник (входящая степень 0), сток (исходящая степень 0), транзитивная
редукция (минимальный набор рёбер, сохраняющий достижимость, — то, что
рисуют системы сборки, чтобы не загромождать схему).

## B2. Алгоритм Кана на примере

Возьмём четыре файла, где `service` импортирует `models`, а `api` импортирует
оба:

```
models → service → api
   └───────────────↑
```

| Шаг | Входящие степени | Очередь готовых | Выдано |
| --- | --- | --- | --- |
| старт | models 0, service 1, api 2 | [models] | [] |
| 1 | service 0, api 1 | [service] | [models] |
| 2 | api 0 | [api] | [models, service] |
| 3 | — | [] | [models, service, api] |

Выдано 3 из 3 → цикла нет.

Теперь добавим `models → api → models`:

| Шаг | Входящие степени | Готовые | Выдано |
| --- | --- | --- | --- |
| старт | models 1, service 1, api 2 | [] | [] |

Очередь пуста с самого начала, ничего не выдаётся, `len(order) = 0 ≠ 3`,
поэтому все три помечаются как участники цикла. Тонкость: **вершины, просто
находящиеся ниже по течению от цикла, тоже никогда не выдаются**, поэтому
«множество цикла» на деле означает «всё, заблокированное циклом». Если нужно
указать точный цикл, запустите SCC Тарьяна и возьмите компоненты размера > 1
(или петлю).

**Детерминизм.** С обычной очередью результат зависит от порядка перебора.
Сортировка готового множества по исходным позициям вершин делает результат
воспроизводимым — это важно, когда вывод управляет сборкой, прогоном тестов
или отчётом, который человек будет сравнивать между запусками. Именно так
сделано в этом проекте.

**Набросок доказательства сложности.** Подсчёт входящих степеней затрагивает
каждое ребро один раз: `O(V + E)`. В основном цикле каждая вершина входит в
очередь и выходит ровно один раз (`O(V)`), а каждое ребро релаксируется ровно
один раз при выдаче его источника (`O(E)`). Итого `O(V + E)`; память `O(V)`
на словарь степеней и очередь.

## B3. Сортировка через DFS и зачем нужны три цвета

Двух цветов (посещена / не посещена) достаточно, чтобы понять, что вершину
уже видели, но не чтобы понять, является ли она *предком на текущем пути*.
Только ребро в вершину, которая всё ещё **в обработке** (GRAY), является
обратным, и только обратное ребро доказывает цикл. Ребро в **завершённую**
(BLACK) вершину — поперечное или прямое, и в DAG оно совершенно законно.
Правильное различение этих случаев — классический уточняющий вопрос.

**Глубина рекурсии** — практическая опасность: цепочка зависимостей из
10 000 файлов превысит лимит рекурсии Python по умолчанию. Либо переходите на
явный стек, либо используйте алгоритм Кана — ещё одна причина, по которой в
этом проекте выбран Кан.

## B4. За пределами простой топологической сортировки

**Параллельное планирование.** Выдача готового множества Кана целыми
*уровнями* даёт расписание с максимальным параллелизмом: все задачи уровня
могут выполняться одновременно, а число уровней и есть **длина критического
пути** — теоретический минимум календарного времени при неограниченном числе
исполнителей. При ограниченном числе исполнителей близкое к оптимальному
расписание даёт **Коффман — Грэм**.

**Длиннейший путь / CPM.** Обходя вершины в топологическом порядке,
релаксируем `dist[v] = max(dist[v], dist[u] + w(u,v))`. Это `O(V+E)` и лежит
в основе анализа критического пути в управлении проектами и оценок времени
сборки в современных системах сборки.

**Инкрементальные пересборки.** Реальные системы сборки не сортируют заново с
нуля: они хранят предыдущий граф, применяют разницу и пересчитывают только
затронутый подграф. Bazel и подобные дополнительно хешируют входы, поэтому
неизменившееся поддерево пропускается целиком.

**Циклы в реальной жизни.** Циклические импорты в Python нередко «работают»
во время выполнения, но ломаются при определённом порядке импорта;
циклические зависимости сервисов в микросервисной архитектуре указывают на
отсутствующий общий контекст. Инженерный ответ — *сообщать* о цикле как о
сигнале качества кода, а не падать: цикл в анализируемом проекте не является
ошибкой анализатора.

## B5. LRU: реализация и разбор

Версия из этого репозитория (`ai_test_assistant/cache.py`), сокращённая до
сути:

```python
class _LruNode:
    __slots__ = ("key", "value", "prev", "next")     # память: без словаря на узел

class LRUCache:
    def __init__(self, capacity: int):
        if capacity < 1:
            raise ValueError("Cache capacity must be at least 1")
        self.capacity = capacity
        self.hits = self.misses = 0
        self._nodes = {}
        self._head = _LruNode(None, None)     # часовой: сторона свежих
        self._tail = _LruNode(None, None)     # часовой: сторона старых
        self._head.next, self._tail.prev = self._tail, self._head

    def get(self, key):
        node = self._nodes.get(key)
        if node is None:
            self.misses += 1
            return None
        self.hits += 1
        self._unlink(node)
        self._link_after_head(node)
        return node.value

    def put(self, key, value):
        node = self._nodes.get(key)
        if node is not None:                  # обновляем, не увеличивая размер
            node.value = value
            self._unlink(node); self._link_after_head(node)
            return
        if len(self._nodes) >= self.capacity: # вытесняем самый старый
            victim = self._tail.prev
            self._unlink(victim)
            del self._nodes[victim.key]       # никогда не забывать про словарь!
        node = _LruNode(key, value)
        self._nodes[key] = node
        self._link_after_head(node)
```

**Проектные решения, которые надо уметь защитить:**

- **Часовые.** `head` и `tail` никогда не удаляются, поэтому `_unlink` и
  `_link_after_head` не нуждаются в проверках на None — меньше ветвлений,
  меньше багов.
- **`__slots__`.** Убирает `__dict__` у каждого узла; на тысячах записей это
  заметная экономия памяти и небольшой выигрыш в скорости.
- **Счётчики как обычные целые.** `hits`/`misses` выставлены как данные, а не
  отправляются в библиотеку метрик, поэтому у кэша нет зависимости от
  Prometheus, но он остаётся наблюдаемым. Как их экспортировать, решает
  *вызывающая сторона*.
- **Отказ при `capacity < 1`** в конструкторе превращает тихую
  неправильную настройку (кэш, который немедленно вытесняет всё и молча
  тратит деньги) в громкую ошибку.

**Сложность:** `get`, `put`, вытеснение — все `O(1)` и амортизированно, и в
худшем случае. Память: `O(capacity)`, одна запись словаря и один узел на
ключ.

**Конкурентность.** Эта реализация не потокобезопасна: два одновременных
`put` могут разрушить список. Варианты по возрастанию сложности: один мьютекс
(просто, но точка конкуренции); **разделение блокировок (lock striping)** —
шардировать кэш по `hash(key) % N`, у каждого шарда свой замок (масштабируется
почти линейно); неблокирующие структуры; либо подход Caffeine — буферизовать
события доступа в кольцевых буферах и воспроизводить асинхронно, чтобы
читатели никогда не блокировались. В этом проекте задания никогда не
пересекаются: Cloud Run даёт каждому экземпляру воркера один запрос за раз
(**concurrency = 1**), а воркер держит блокировку на время каждого задания.
Поэтому блокировка внутри кэша была бы чистыми накладными расходами. При этом
ограничение задокументировано, а не проигнорировано, и это правильная
инженерная позиция.

## B6. LFU: реализация и разбор

```python
class LFUCache:
    def __init__(self, capacity):
        self._values = {}                     # ключ -> значение
        self._frequencies = {}                # ключ -> счётчик
        self._keys_by_frequency = {}          # счётчик -> OrderedDict ключей
        self._min_frequency = 0

    def get(self, key):
        if key not in self._values:
            self.misses += 1
            return None
        self.hits += 1
        self._increment_frequency(key)
        return self._values[key]

    def put(self, key, value):
        if key in self._values:
            self._values[key] = value
            self._increment_frequency(key)
            return
        if len(self._values) >= self.capacity:
            bucket = self._keys_by_frequency[self._min_frequency]
            evicted, _ = bucket.popitem(last=False)      # старейший в мин. корзине
            del self._values[evicted]; del self._frequencies[evicted]
        self._values[key] = value
        self._frequencies[key] = 1
        self._keys_by_frequency.setdefault(1, OrderedDict())[key] = None
        self._min_frequency = 1                          # новый ключ сбрасывает минимум

    def _increment_frequency(self, key):
        f = self._frequencies[key]
        bucket = self._keys_by_frequency[f]
        del bucket[key]
        if not bucket:
            del self._keys_by_frequency[f]
            if self._min_frequency == f:
                self._min_frequency = f + 1              # только +1
        self._frequencies[key] = f + 1
        self._keys_by_frequency.setdefault(f + 1, OrderedDict())[key] = None
```

**Два инварианта, на которых всё держится:**

1. `_min_frequency` всегда равен наименьшей непустой корзине. Он
   восстанавливается ровно в двух местах: устанавливается в 1 при вставке
   нового ключа и увеличивается на 1, когда текущая минимальная корзина
   опустела. Никакого поиска.
2. Каждая корзина — `OrderedDict`, поэтому внутри одной частоты порядок
   совпадает с порядком вставки/свежести, и `popitem(last=False)` даёт
   разрешение ничьей по LRU за `O(1)`.

**Проблема старения на конкретном примере.** Пусть ключ был запрошен
10 000 раз во время запуска продукта, а затем — никогда. Его счётчик навсегда
остаётся равным 10 000, поэтому он бессрочно занимает ёмкость, а сегодняшние
горячие ключи, входящие со счётчиком 1, немедленно вытесняются. Смягчение:

- **Периодическое деление пополам** всех счётчиков (дешёвое экспоненциальное
  затухание).
- **Подсчёт в окне** — учитывать только обращения в недавнем окне.
- **Подход Redis** — 8-битный *логарифмический* счётчик (инкременты
  становятся всё более редкими по мере роста, что даёт большой динамический
  диапазон в одном байте) с **затуханием по времени** (`lfu-decay-time`) и
  выборкой вместо точного учёта.
- **W-TinyLFU** — см. ниже.

## B7. W-TinyLFU: современный уровень техники

Используется в **Caffeine** и является причиной того, что стандартная
библиотека кэширования в Java с большим отрывом обходит самописный LRU.

Три части:

1. **Частотный эскиз** — Count-Min Sketch с 4-битными счётчиками оценивает,
   как часто встречался ключ, тратя несколько байт на *слот кэша*, а не
   счётчик на каждый наблюдавшийся ключ. Счётчики **периодически делятся
   пополам**, что решает проблему старения по построению.
2. **Оконный кэш (~1 %)** — небольшой LRU, поглощающий всплески, чтобы
   совершенно новый горячий ключ не был отвергнут до того, как успел себя
   проявить.
3. **Основной кэш (~99 %)** — сегментированный LRU с испытательным и
   защищённым сегментами.

**Политика допуска:** когда окно вытесняет кандидата, его оценка частоты
сравнивается с оценкой жертвы вытеснения из основного кэша; кандидат
допускается, только если он предположительно ценнее. Идея «допуск вместо
вытеснения» — ключевая: она вообще не даёт разовому скану вытеснить рабочее
множество, обеспечивая близкие к оптимальным hit ratio при умеренной памяти.

## B8. Выбор и измерение кэша

**Руководство по выбору:**

| Ситуация | Политика |
| --- | --- |
| Сессии, недавняя работа, перезапуски (временна́я локальность) | LRU |
| Стабильное популярное подмножество на фоне разового шума | LFU (со старением) или TinyLFU |
| Смешанная/неизвестная, нужна самонастройка | ARC или W-TinyLFU |
| Масштаб ядра/страничного кэша, метаданные должны быть крошечными | CLOCK |
| Все записи равноценны, важна простота | FIFO/Random |

**Подбор размера.** Зависимость hit ratio от ёмкости — вогнутая кривая с
«коленом»: удвоение маленького кэша даёт много, удвоение большого — почти
ничего. Ищите колено, проигрывая реальную трассу обращений на кандидатах
размеров, — и сравнивайте с **OPT Белади** на той же трассе, чтобы понимать,
сколько запаса даёт улучшение *политики*, а не размера.

**Метрики для экспорта:** hit ratio, вытеснений в секунду, число записей,
потребление памяти и — что критично — та нижележащая метрика, которую кэш
призван улучшить (QPS бэкенда, задержка или стоимость). Кэш с 95 %
попаданий, не снижающий стоимость, кэширует не то.

**Когда не кэшировать:** когда данные обязаны быть строго свежими; когда
вычисление дешевле поиска; когда hit ratio будет близок к нулю (уникальные
ключи); когда сложность инвалидации перевесит выгоду. Инвалидация кэша
заслуженно считается одной из двух трудных задач информатики, и честный ответ
на многие вопросы о кэшировании звучит так: «сделайте ключ адресуемым по
содержимому, и инвалидация станет не нужна».

## B9. Как оба алгоритма используются в проекте

Оба реализованы с нуля (без `graphlib`, без `functools.lru_cache`), и каждый
решает реальную задачу конвейера — именно это делает их защитимыми, а не
академическими.

### Топологическая сортировка — `ai_test_assistant/import_graph.py`

**Проблема.** Pull request меняет и `models.py`, и `service.py`, причём
`service` импортирует `models`. Ассистент обрабатывает изменённые файлы по
одному, поэтому нужен порядок, который воспроизводим и что-то значит. Отчёт
должен показывать `models` раньше кода, который его использует. А `models`
стоит обработать до того, как появятся тесты для `service`: сгенерированные
тесты пишутся в `tests/generated/`, а поиск связанных тестов читает эту папку,
так что при обратном порядке свежие тесты `service` могли бы попасть в промпт
для `models`.

Чего порядок **не** делает: не меняет того, что промпт видит из исходного
кода. Каждый файл в любом случае читается из головы PR, поэтому ответ «порядок
защищает от тестов против устаревшей зависимости» был бы неверным.

**Решение.** Построить граф импортов **только по изменённым файлам** (внешние
и неизменённые модули для порядка нерелевантны) и выполнить алгоритм Кана:

```python
order = order_files_by_imports(changed_files, repo_root)
for changed_file in order.ordered_files:   # сначала зависимости
    ...
if order.cycle_files:                      # сообщаем, но не падаем
    ...
```

Решения, которые стоит процитировать на экзамене:

- **Импорты извлекаются через `ast`**, а не регулярными выражениями, включая
  относительные импорты (`from .operations import add`), разрешаемые
  относительно пакета импортирующего модуля, и форму
  `from package import module`, которая обязана создавать ребро на
  `package.module`, а не только на `package`. (Последний случай был реальным
  багом, найденным при ревью и закрытым регрессионным тестом.)
- **Ничьи разрешаются по исходному порядку файлов**, поэтому конвейер
  воспроизводим: готовые файлы лежат в min-куче с ключом «исходная позиция»
  (вариант с min-кучей из B2), `O((V + E) log V)`. Первая версия
  пересортировывала весь список готовых вершин на каждом шаге — это
  `O(V² log V)`; на размерах PR безвредно, но заявленная сложность была
  неверной, пока её не заменила куча.
- **Циклы деградируют штатно**: затронутые файлы сохраняют исходный порядок и
  перечисляются в JSON- и Markdown-отчётах как `import_cycle_files`. Цикл в
  анализируемом репозитории — «запах» кода *того* репозитория, а не повод
  падать инструменту.
- **Честно названные ограничения:** динамические импорты (`importlib`,
  `__import__`) невидимы статическому анализу, и строятся только рёбра
  *между изменёнными файлами*.

### LRU-кэш — `ai_test_assistant/cache.py` + `llm_client.py`

**Проблема.** Повторный запуск ассистента на pull request после rebase шлёт в
Gemini байт-в-байт одинаковые промпты. При `temperature = 0` ответ
детерминирован, поэтому второй вызов — чистая трата денег и времени.

**Решение.** Кэш, адресуемый по содержимому, перед вызовом модели:

```python
def _cache_key(self, system_instruction: str, prompt: str) -> str:
    material = "\x1f".join((self._config.gemini_model,
                            str(self._config.temperature),
                            system_instruction, prompt))
    return hashlib.sha256(material.encode()).hexdigest()
```

- **Всё, что влияет на ответ, входит в ключ** — модель, температура,
  системная инструкция, промпт. Измените любое — получите другую запись,
  поэтому **явная инвалидация не нужна никогда**. Это и есть приём адресации
  по содержимому из B8.
- **Ключом служит хеш, а не сырой промпт** — память ограничена, поиск дёшев.
- **Кэш внедряется, а не создаётся внутри.** CLI не передаёт его вовсе (в
  одном запуске промпты почти не повторяются); долгоживущий воркер владеет
  одним кэшем на 256 записей на весь процесс (`LRUCache` по умолчанию,
  `LFUCache` при `LLM_CACHE_POLICY=lfu`), поэтому кэш охватывает разные
  задания — именно это и делает возможным «отправь ветку заново и заплати
  ноль».
- **Предусловие корректности:** кэширование законно только потому, что
  `temperature = 0`. При ненулевой температуре вы подменили бы распределение
  ответов одной выборкой. Умение назвать это предусловие отличает «я добавил
  кэш» от «я понял кэш».

**Реальный баг, который стоит рассказать.** Сначала кэш вообще не срабатывал
между заданиями. Причина: в промпты попадали **абсолютные пути временного
каталога клона**, которые различаются в каждом задании, поэтому каждый ключ
был уникальным. Исправление — оставлять в промптах только путь модуля и имя
файла, плюс регрессионный тест (`test_prompt_stability.py`), утверждающий, что
два клона одного и того же кода дают идентичные промпты. **Общий урок: ключ
кэша обязан строиться из *нормализованных* данных; любая посторонняя
изменчивость молча уничтожает hit ratio — молча, потому что никогда не
попадающий кэш всё равно возвращает корректные результаты.**

**Измеренный эффект** (четыре одинаковых задания на локальном стенде
мониторинга): задание 1 дало 3 промаха и 3 реальных вызова модели; задания
2–4 дали 9 попаданий и **ноль** дополнительных вызовов. Экспортируется как
`llm_cache_hits_total` и `llm_cache_misses_total` (с меткой политики) и
отображается рядом с панелью расхода токенов в Grafana — оптимизация
измерена, а не постулирована.

### LFU — переключаемая альтернатива

`LFUCache` полностью реализован с операциями за `O(1)` и покрыт юнит-тестами,
и воркер работает с ним, если задать `LLM_CACHE_POLICY=lfu`; неизвестное
значение останавливает воркер при старте с понятной ошибкой. **LRU остаётся
политикой по умолчанию, потому что соответствует фактическому профилю
доступа** (всплесковые перезапуски одной ветки — временна́я локальность). LFU
выиграл бы в другом сценарии развёртывания: один воркер обслуживает много
репозиториев, и несколько общих модулей встречаются в большинстве pull
request'ов. Счётчики кэша несут метку `policy`, поэтому одни и те же задания
можно прогнать под каждой политикой и сравнить на панели hit ratio — выбор
между ними измеряется, а не доказывается словами.

## B10. План изучения и источники

**День 1 — графы.** Реализуйте обе топологические сортировки с чистого листа.
Затем реализуйте *сообщение* о цикле (не только обнаружение) через SCC
Тарьяна. Задачи: LeetCode 207/210 (Course Schedule I и II), 269 (Alien
Dictionary), 310 (Minimum Height Trees), 1136 (Parallel Courses — вариант с
уровнями).

**День 2 — динамическое программирование на DAG.** Длиннейший путь, подсчёт
путей, планирование по критическому пути. Прочитайте, как реальная система
сборки планирует работу.

**День 3 — LRU.** Реализуйте с нуля с часовыми (LeetCode 146), затем
перепишите через `OrderedDict` и сравните. Добавьте счётчики попаданий и
промахов и микробенчмарк.

**День 4 — LFU.** Реализуйте версию за `O(1)` (LeetCode 460). Затем добавьте
деление счётчиков пополам и измерьте hit ratio на синтетической трассе с
распределением Ципфа в сравнении с LRU.

**День 5 — реальные системы.** Прочитайте документацию Redis по вытеснению
(`maxmemory-policy`, выборка, счётчик LFU) и материалы по устройству
Caffeine/W-TinyLFU. Напишите по абзацу о том, когда выигрывает каждая
политика.

**Источники:** *Introduction to Algorithms* (CLRS), гл. 22 — DFS,
топологическая сортировка и SCC; Kahn (1962) — оригинальный алгоритм; Shah,
Mitra & Matani, *An O(1) algorithm for implementing the LFU cache eviction
scheme* (2010); Einziger, Friedman & Manes, *TinyLFU: A Highly Efficient
Cache Admission Policy* (2015); Megiddo & Modha, *ARC* (2003); Belady (1966) —
оптимальный алгоритм и аномалия; документация Redis и Caffeine — поведение в
продакшене.
