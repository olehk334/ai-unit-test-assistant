# Полное руководство по интегрированным возможностям (PDP 6–8)

Этот документ объясняет каждую возможность, добавленную в AI Unit Test
Assistant поверх базового MVP: что это такое в теории, как оно работает,
как встроено в проект, какие у него плюсы, минусы и подводные камни.
Цель — чтобы после прочтения вы могли уверенно рассказать о каждой теме
и ответить на вопросы «почему сделано именно так».

---

## 0. Каркас, в который всё встроено: базовый пайплайн ассистента

Прежде чем разбирать новые возможности, важно держать в голове базовый
поток данных (он не менялся):

```text
git diff (изменённые файлы)
   → AST-анализ (публичные функции/методы)
   → поиск связанных существующих тестов
   → генерация тестов через Gemini (Vertex AI)
   → запуск pytest
   → цикл починки при падении (repair loop)
   → отчёт (Markdown + JSON) и артефакты
```

Ключевое свойство: пайплайн — **библиотека** (`ai_test_assistant`), у
которой два «лица»: CLI (`ai-test-assistant run-pr-assistant`) и
облачный сервис (analysis worker). Все новые возможности встроены так,
что CLI-режим продолжает работать без изменений.

## 1. Топологическая сортировка изменённых файлов (PDP 8, часть 1)

### Что это такое (теория)

Топологическая сортировка — это упорядочивание вершин ориентированного
ациклического графа (DAG) так, чтобы каждое ребро вело «слева направо»:
если A → B (B зависит от A), то A в итоговом списке стоит раньше B.
Классические применения: порядок сборки модулей, разрешение зависимостей
пакетных менеджеров, планирование задач.

Мы используем **алгоритм Кана (Kahn's algorithm)**:

1. Для каждой вершины считаем «входящую степень» (in-degree) — сколько
   необработанных зависимостей у неё осталось.
2. Кладём в очередь все вершины со степенью 0 (ни от кого не зависят).
3. Достаём вершину, добавляем в результат, у всех её «потомков»
   уменьшаем степень на 1; кто дошёл до нуля — тоже в очередь.
4. Если в конце обработаны не все вершины — оставшиеся образуют **цикл**.

Сложность: **O(V + E)** — линейная по числу вершин и рёбер.

Альтернатива — сортировка через DFS (обход в глубину с выдачей вершин в
обратном порядке выхода). Мы выбрали Кана, потому что обнаружение цикла
получается «бесплатно» (остались необработанные вершины — значит цикл),
без отслеживания стека рекурсии.

### Зачем это проекту

Реальная проблема: PR меняет и `models.py`, и `service.py`, который
импортирует `models`. Если анализировать `service.py` первым, тесты для
него генерируются, пока его зависимость ещё «не осмыслена» — порядок
обработки произволен и нестабилен. Правильный порядок: сначала
зависимости, потом зависящие.

### Как это работает у нас

Код: `ai_test_assistant/import_graph.py`, функция
`order_files_by_imports()`.

1. Для каждого изменённого файла через `ast` извлекаются импорты:
   `import x`, `from x import y`, относительные импорты
   (`from .operations import add`) разрешаются относительно пакета
   импортирующего файла.
2. Граф строится **только между изменёнными файлами** — внешние
   зависимости (стандартная библиотека, сторонние пакеты, неизменённые
   модули) в граф не попадают: для порядка обработки они не важны.
3. Алгоритм Кана даёт порядок; при равенстве (несколько вершин готовы
   одновременно) берётся исходный порядок файлов — результат
   **детерминирован**, одинаковый на каждом запуске.
4. Цикл (`a` импортирует `b`, `b` импортирует `a`) не останавливает
   работу: файлы цикла обрабатываются в исходном порядке, а их список
   попадает в отчёт (`import_cycle_files` в JSON, строка в Markdown).
   Логика: цикл — это запах кода в анализируемом проекте, но не повод
   отказаться генерировать тесты.

Интеграция: одна строка в `pipeline.run_pr_assistant()` — файлы
проходят через `order_files_by_imports()` до основного цикла обработки.

### Плюсы

- Детерминированный, объяснимый порядок анализа.
- O(V+E) — накладные расходы незаметны (в PR обычно единицы файлов).
- Обнаружение циклов импортов — полезный сигнал сам по себе, попадает
  в отчёт.
- Реализация ~120 строк, без внешних зависимостей (никакого `graphlib`).

### Минусы и ограничения

- Порядок учитывает только импорты **между изменёнными файлами**; если
  зависимость не менялась в этом PR, ребро не строится (это осознанное
  упрощение — для порядка обработки только эти рёбра и важны).
- Динамические импорты (`importlib`, импорты внутри функций через
  `exec`) не видны AST-анализу верхнего уровня (импорты внутри функций
  видны — `ast.walk` обходит всё дерево, — но `__import__("x")` нет).
- Известный пробел (см. аудит): стиль `from calculator import
  operations` даёт ребро только на пакет `calculator`, а не на модуль
  `calculator.operations`.

### Вопросы, которые могут задать

- *Почему Кан, а не DFS?* Бесплатное обнаружение циклов, итеративность
  (нет риска глубокой рекурсии), проще объяснить.
- *Что при цикле?* Деградация до исходного порядка + запись в отчёт.
- *Почему не сортировать все файлы проекта?* Не нужно: порядок важен
  только внутри множества файлов, которые мы собираемся обрабатывать.

## 2. LRU/LFU-кеш и кеширование ответов LLM (PDP 8, часть 2)

### Что это такое (теория)

Кеш фиксированного размера должен решать: **кого выселить**, когда
место закончилось. Две классические политики:

- **LRU (Least Recently Used)** — выселяем того, кого дольше всех не
  трогали. Ставка на «временную локальность»: недавно использованное
  скоро понадобится снова.
- **LFU (Least Frequently Used)** — выселяем того, кого реже всех
  использовали. Ставка на «популярность»: горячие ключи важнее свежих.

#### Внутренности LRU — O(1) на обеих операциях

Код: `ai_test_assistant/cache.py`, класс `LRUCache`. Два инварианта:

- `dict` (ключ → узел) даёт мгновенный поиск;
- **двусвязный список** с двумя фиктивными узлами-«часовыми» (head и
  tail) хранит порядок использования: самый свежий сразу после head,
  самый старый перед tail.

`get`: найти узел через dict, **выдернуть** из списка (две перестановки
указателей) и **вставить** после head. `put` при переполнении: удалить
узел `tail.prev` (самый старый) из списка и из dict. Ни одна операция
не сканирует список — отсюда O(1). Часовые узлы избавляют от проверок
«а не пустой ли список / не край ли это» — код без ветвлений на краях.

Почему не `functools.lru_cache`? Он декорирует функцию и не даёт ни
доступ к статистике hits/misses как к данным, ни разделения кеша между
разными вызывающими; а главное — цель PDP-пункта именно «internals».

#### Внутренности LFU — частотные корзины

Класс `LFUCache`. Три структуры:

- `dict` ключ → значение;
- `dict` ключ → счётчик использований;
- `dict` счётчик → `OrderedDict` ключей с этим счётчиком (порядок
  вставки = порядок свежести), плюс указатель `_min_frequency` на самую
  низкую непустую корзину.

При использовании ключ переезжает из корзины *n* в корзину *n+1*.
Выселение: взять самый старый ключ из корзины `_min_frequency`
(`popitem(last=False)`), то есть **LFU с LRU-разрешением ничьих**. Все
операции O(1).

### Зачем это проекту

При `temperature = 0` ответ Gemini на одинаковый промпт детерминирован.
Значит, повторный запрос с байт-в-байт тем же промптом — чистая потеря
денег и времени. Такое случается постоянно: перезапуск PR после rebase,
повторная доставка сообщения очередью, два PR, задевшие один и тот же
неизменившийся файл.

### Как это встроено

1. `LlmClient.generate()` перед обращением к модели проверяет кеш.
   Ключ — **SHA-256 от (модель, температура, системная инструкция,
   промпт)**: смена любого из компонентов меняет ключ, коллизии
   практически исключены, а в памяти не хранятся сами промпты в
   качестве ключей.
2. Кеш **внедряется снаружи** (`LlmClient(config, response_cache=...)`):
   в CLI-режиме кеша по умолчанию нет (внутри одного запуска повторных
   промптов почти не бывает), а в analysis worker живёт один
   `RESPONSE_CACHE = LRUCache(256)` на весь процесс — он переживает
   отдельные задания, и повторный push той же ветки попадает в кеш.
3. Важная находка при интеграции (реальный баг): промпты содержали
   **абсолютные пути временной директории клона** — у каждого задания
   пути разные, поэтому кеш никогда не срабатывал между заданиями.
   Исправление: в промптах только модульный путь (`calculator.operations`)
   и имена файлов. Урок: ключ кеша обязан строиться из
   **нормализованных** данных; любая «случайная» переменность на входе
   убивает кеш молча. Регрессионный тест: `tests/unit/test_prompt_stability.py`.
4. Кеш считает `hits`/`misses` простыми целыми — worker экспортирует их
   в Prometheus (`llm_cache_hits_total` / `llm_cache_misses_total`), и
   на дашборде видно хитрейт рядом с расходом токенов.

Проверено вживую: два одинаковых задания подряд — первое даёт
3 обращения к LLM (3 промаха), второе — 3 попадания и **ноль** новых
обращений (`llm_calls_total` не растёт).

### LRU или LFU — почему в бою LRU

Паттерн доступа у нас — «всплесковый»: серия перезапусков одной и той
же ветки в течение часа. Это временная локальность → LRU. LFU выиграл
бы у LRU, если бы один воркер обслуживал десятки репозиториев и
несколько «горячих» общих модулей встречались в большинстве PR — тогда
LFU защищал бы их от вытеснения потоком одноразовых файлов. Такой
нагрузки сейчас нет, поэтому LFU реализован, протестирован и описан,
но **не подключён** — подключение без реальной потребности было бы
спекулятивной абстракцией (см. правила разработки).

### Плюсы

- Прямое сокращение затрат: повторное задание — 0 токенов, 0 секунд
  ожидания LLM.
- O(1) на операцию, ~150 строк кода, ноль зависимостей.
- Эффект измерим (метрики хитрейта на дашборде) — не «вера», а график.

### Минусы и ограничения

- Кеш **в памяти процесса**: рестарт воркера = холодный кеш; несколько
  воркеров не разделяют кеш (для распределённого кеша нужен Redis или
  аналог — осознанно вне рамок).
- Кеширование корректно **только при temperature = 0**; при ненулевой
  температуре кеш подменял бы распределение ответов одним образцом.
- Инвалидация не нужна по построению (контент в ключе), но это
  держится на дисциплине «весь значимый вход входит в ключ».

## 3. Событийно-ориентированная облачная архитектура (PDP 6)

### Что это такое (теория)

**Микросервисы** — разбиение системы на независимо разворачиваемые
сервисы. Правильный критерий разреза — не «по существительным», а по
**конфликту требований**: у нас приёмник вебхуков обязан отвечать за
секунды и быть публичным, а анализатор работает минуты и публичным быть
не должен. Это и есть линия разреза.

**Event-driven** — компоненты общаются событиями через брокер, а не
синхронными вызовами. Издатель не ждёт обработчика; обработчик может
падать и перезапускаться, события не теряются.

**Serverless** — платформа сама управляет серверами: масштабирование от
нуля (не платим за простой) до N инстансов под нагрузкой; расплата —
холодные старты и требование **stateless**-дизайна.

**Паттерны масштабируемости**, которые демонстрирует проект:

- *Queue-based load leveling* — очередь сглаживает всплески: десять PR
  одновременно не убивают воркер, а выстраиваются в очередь.
- *Идемпотентный потребитель* — Pub/Sub гарантирует доставку
  **at-least-once**, значит дубликаты неизбежны и обработчик обязан
  быть безопасным при повторе.
- *Retry + Dead-letter* — временные сбои лечатся повтором (до 5
  попыток), «ядовитые» сообщения после исчерпания попыток уходят в
  отдельную DLQ-тему для ручного разбора, не блокируя очередь.
- *Горизонтальное масштабирование* — воркер с concurrency=1: больше
  нагрузки → больше инстансов, а не больше потоков в одном. Ментальная
  модель «1 задание = 1 контейнер» проще, чем гонки потоков.

### Архитектура проекта

```text
GitHub PR (opened / synchronize / reopened)
      │  вебхук, подпись HMAC-SHA256
      ▼
[webhook-receiver]  Cloud Run, публичный, scale-to-zero
      │  проверил подпись → отфильтровал событие → опубликовал job → 202
      ▼
[Pub/Sub: pr-analysis-jobs]  push-подписка, ack deadline 600s,
      │                      5 попыток → dead-letter topic
      ▼
[analysis-worker]  Cloud Run, приватный (вызывает только Pub/Sub), concurrency 1
      │  идемпотентность → clone головы PR → пайплайн (библиотечный вызов)
      ├──▶ [GCS-бакет]        отчёты + сгенерированные тесты
      └──▶ [GitHub commit status]  success / failure со ссылкой
```

Контракт сообщения (JSON): `repo_full_name`, `clone_url`, `pr_number`,
`head_sha`, `base_ref`, `delivery_id`. **Ключ идемпотентности** =
`repo/PR/head_sha` — он же префикс артефактов в GCS: если JSON-отчёт по
этому префиксу уже лежит, задание подтверждаем (ack) без повторной
работы. Маркер пишется только при успехе, поэтому упавшее на середине
задание корректно переигрывается.

Семантика HTTP-ответов воркера — это и есть протокол очереди:
**200 = ack** (сделано или осознанно пропущено), **500 = retry**
(Pub/Sub доставит повторно, после 5 раз — в DLQ). Отдельный случай:
**некорректное сообщение подтверждается сразу** (повтор ему не поможет
— это защита от вечного «ядовитого» цикла).

### Как это встроено, не сломав простоту

- Сервисы — два маленьких FastAPI-приложения
  (`services/webhook_receiver/receiver_app.py`,
  `services/analysis_worker/worker_app.py`), воркер использует
  `ai_test_assistant` **как библиотеку** — бизнес-логика не
  дублируется.
- GCP-клиенты импортируются лениво внутри функций — юнит-тесты сервисов
  не требуют установленных SDK (та же конвенция, что и с `google-genai`
  в `llm_client`).
- Всё состояние — в очереди и бакете; сервисы stateless (кеш LLM — лишь
  оптимизация: потеря инстанса теряет только «прогретость»).
- Локальный режим без облака: воркер запускается с `DRY_RUN=true`, ему
  можно послать Pub/Sub-образный конверт (`monitoring/send_test_job.py`)
  — реальный clone, реальный pytest, заглушенный LLM.
- Развёртывание — один скрипт `infra/deploy.sh` (темы, DLQ, бакет, два
  Cloud Run-сервиса, push-подписка с dead-letter политикой). Скрипт
  создаёт платные ресурсы и **не запускался** — см. аудит: шаг сборки
  образов в нём требует правки.

### Таблица соответствий облаков (теория PDP «AWS, GCP, Azure»)

| Роль | GCP (у нас) | AWS | Azure |
| --- | --- | --- | --- |
| Контейнеры со scale-to-zero | Cloud Run | App Runner / Lambda | Container Apps |
| Очередь/шина событий | Pub/Sub | SNS+SQS | Service Bus |
| DLQ | dead-letter topic | SQS DLQ | Service Bus DLQ |
| Хранилище артефактов | GCS | S3 | Blob Storage |
| LLM API | Vertex AI | Bedrock | Azure OpenAI |

Смысл таблицы: архитектура **переносима** — меняются имена управляемых
сервисов, а паттерны (очередь, идемпотентность, DLQ, stateless) те же.

### Плюсы

- Пики нагрузки не роняют систему (очередь выравнивает).
- Сбой любого компонента не теряет работу (повторная доставка).
- Ноль затрат в простое (scale-to-zero) — идеально для демо/пет-проекта.
- Каждый сервис можно понять за один экран кода.

### Минусы и честные оговорки

- Сложность выросла: было «один CLI», стало «две службы + брокер +
  бакет + IAM». Для одного репозитория CLI/GitHub Actions-режима
  объективно достаточно — облачный контур оправдан, когда ассистент
  обслуживает **много** репозиториев организации (и как учебная цель).
- Отладка распределённой системы тяжелее (поэтому фаза 7 — мониторинг —
  обязательна, а не опциональна).
- At-least-once — это контракт «дубликаты будут»: идемпотентность не
  улучшение, а обязанность.
- Секреты в `--set-env-vars` видны в конфигурации сервиса; по-хорошему —
  Secret Manager (вне рамок демо).

## 4. Мониторинг: Prometheus + Grafana (PDP 7)

### Что это такое (теория)

**Prometheus** — система сбора метрик с **pull-моделью**: сервис просто
отдаёт текущие значения на HTTP-эндпоинте `/metrics`, а Prometheus сам
приходит и забирает их по расписанию (у нас каждые 5 секунд). Сервису
не нужно знать, куда слать метрики, и сбой мониторинга не влияет на
сервис.

Три типа метрик и правило выбора:

- **Counter** — только растёт (число заданий, токены). Абсолютное
  значение малоинтересно; смысл даёт `rate()` — скорость роста.
- **Gauge** — текущее значение, может убывать (глубина очереди, память).
- **Histogram** — распределение по «корзинам» (bucket'ам). Обязателен
  для латентности: среднее время скрывает хвосты, а
  `histogram_quantile(0.95, ...)` честно показывает p95. Гистограмма —
  это набор counters по корзинам, поэтому она корректно агрегируется
  между инстансами и переживает рестарты.

**PromQL** — язык запросов; ключевые конструкции, которые мы используем:

```promql
rate(jobs_processed_total[5m]) * 60          -- заданий в минуту по исходам
histogram_quantile(0.95, rate(job_duration_seconds_bucket[15m]))  -- p95
llm_cache_hits_total / clamp_min(llm_cache_hits_total + llm_cache_misses_total, 1)
```

**Grafana** — визуализация поверх Prometheus: дашборды описываются
JSON'ом и **провижинятся из файлов** (инфраструктура-как-код: дашборд
лежит в git, а не настроен кликами).

### Какие метрики мы собираем и почему именно эти

| Метрика | Тип | Что отвечает |
| --- | --- | --- |
| `jobs_processed_total{status}` | counter | Пропускная способность и доля ошибок (лейбл разрезает по исходам). |
| `job_duration_seconds` | histogram | p95 длительности — близость к ack deadline (600 с), сигнал к масштабированию. |
| `llm_calls_total`, `llm_seconds_total` | counter | Сколько и как долго ждём LLM; отношение = средняя латентность вызова. |
| `llm_prompt_tokens_total`, `llm_response_tokens_total` | counter | Токены = деньги; `rate()` = расход в минуту. |
| `llm_cache_hits_total`, `llm_cache_misses_total` | counter | Доказательство пользы кеша из фазы 8. |
| `generated_test_files_total{result}` | counter | Главный KPI качества: как часто сгенерированные тесты проходят. |

Два осознанных «не-решения», которые стоит уметь объяснить:

- **Глубину очереди не меряем сами**: Pub/Sub уже экспортирует
  `num_undelivered_messages` в Cloud Monitoring; собственный замер был
  бы хуже платформенного.
- **Приёмник не инструментирован**: у него одна дешёвая операция, и
  Cloud Run из коробки даёт счётчики запросов/латентность/ошибки.
  Кастомные метрики — там, где кастомная логика.

### Алерты

`monitoring/alerts.yml`, два правила — оба «про деньги и данные», а не
про красоту:

- **HighJobFailureRate** — >20% заданий падает 15 минут подряд (обычно
  Gemini-сбой или плохой деплой).
- **SlowAnalysisJobs** — p95 длительности >5 минут 10 минут подряд:
  приближение к ack deadline 600 с, за которым начинаются повторные
  доставки и двойная работа.

### Локальное демо (без облака и без затрат)

```bash
cd monitoring
docker compose up --build          # воркер (DRY_RUN) + Prometheus + Grafana
python send_test_job.py --repeat 5 # трафик
```

- http://localhost:8080/metrics — сырые метрики;
- http://localhost:9090 — Prometheus (запросы, алерты);
- http://localhost:3000 — Grafana, дашборд «AI Test Assistant»
  провижинится автоматически, вход анонимный.

Повторные одинаковые задания — наглядная демонстрация кеша: панель
хитрейта растёт, панель токенов остаётся плоской.

Облачный путь: тот же `/metrics` собирает Managed Service for
Prometheus (sidecar на Cloud Run), дашборд импортируется без изменений.
Код не отличает локальный сбор от облачного — в этом и смысл
pull-модели.

### Плюсы

- Полностью воспроизводимое демо одной командой, без учёток и затрат.
- Метрики отвечают на реальные вопросы: «сколько стоит», «успеваем ли до
  дедлайна», «окупается ли кеш», «какого качества тесты».
- Дашборд и алерты — файлы в git (инфраструктура-как-код).

### Минусы и ограничения

- Локальный Prometheus без Alertmanager: алерты видны в UI, но
  уведомления (Slack и т.п.) не рассылаются — вне рамок.
- Метрики в памяти процесса: рестарт воркера обнуляет counters (для
  `rate()` это штатно — PromQL понимает сбросы счётчиков).
- Дельта-учёт хитов кеша через глобальные переменные корректен только
  при concurrency=1 (см. аудит, пункт B3).

## 5. Как всё связано: сквозной демо-сценарий

1. Открываем PR в целевом репозитории → вебхук → receiver проверяет
   подпись → job в Pub/Sub.
2. Grafana: `jobs_processed_total` растёт, гистограмма длительности
   наполняется, токены тикают.
3. Воркер обрабатывает изменённые файлы **в порядке импортов**
   (топологическая сортировка), пишет артефакты в GCS, ставит commit
   status в PR.
4. Пушим ту же ветку ещё раз → повторное задание → кеш LLM: хитрейт
   вверх, `llm_calls_total` плоский. Экономия видна на графике.
5. Убиваем воркер посреди задания → сообщение не подтверждено → Pub/Sub
   доставляет повторно → маркера успеха в GCS нет → задание честно
   переигрывается; если бы было — идемпотентный пропуск. Ни дублей, ни
   потерь.

Этот сценарий покрывает все четыре темы разом: событийная архитектура
(шаги 1, 5), алгоритмы (3, 4), мониторинг (2, 4), и исходный ассистент
как полезная нагрузка.
